0. 摘要（先读这段）

现象（以用户实机体验为准）：

App eSIM 流量下 手机热点（Wi-Fi）下
高德地图 ✅ 正常 ✅ 正常
网易云音乐 ✅ 正常 ✅ 正常
喜马拉雅 ❌ 不可用 ✅ 正常
QQ 系列（QQ音乐 / 腾讯视频） ❌ 不可用 ✅ 正常

结论（分层，两者机制不同）：

  1. 腾讯系 = DNS 层被屏蔽（已确证）：eSIM 下发的 DNS 114.114.114.114 对 y.qq.com、wns.qq.com、music.qq.com、dl.stream.qqmusic.qq.com、v.qq.com 等音乐/接口域名静默丢弃——注意是卡到约 20 秒超时才失败，不是秒回 NXDOMAIN（这是过去”批量测域名总超时”的根因）。qq.com 裸域反而能解析 ⇒ 是精确的主机名白名单。
  2. 喜马拉雅 = 卡在 DNS 之上（未定论）：它的 21 个域名（含音频 CDN）在 eSIM 下全部解析正常、TCP 抽测也能建连 ⇒ 不是域名屏蔽。音频素材实际从 openaudio.cos.tx.xmcdn.com（腾讯云 COS）、aod.cos.tx.xmcdn.com 取（另有一路 audio.aliyun.xmcdn.com 在阿里云）。
  3. 首要嫌疑（待 USB 有线复测验证）：喜马拉雅把音频 CDN 解析成 IPv6（实测 240e:978:2608:d01:70::1e）并优先使用，而 eSIM 网卡 eth0 只有 fe80::、没有全球 IPv6（Wi-Fi 才有全球 IPv6）⇒ eSIM-only 时这条连接无路可走。次因：其 APK 内含”仅 WiFi”策略开关（IS_ENABLE_NETWORK_ONLY_WIFI），而 Android 把 eSIM 识别为 ETHERNET（既非 WiFi 也非 MOBILE）。

下一轮要回答的一句话：eSIM-only（USB 有线 + 车机不连任何 Wi-Fi）时，喜马拉雅播放失败是不是因为它去连了 IPv6？

项 值
平台 AC8317（AutoChips AC8227/AC8317，32-bit A7 / Mali-400），Android 6.0
分辨率 1024×600（所有 input tap 坐标都基于此）

eSIM 属性 gsm.sim.state=ABSENT（Android 认为无 SIM 卡）；sys.hk.tbox.connect=connected；persist.hk.tbox_switch=true

1.2 访问方式

方式 说明
① USB 有线 ADB（⭐ 下一轮主用） 车机默认开启 USB 调试（ro.adb.secure=0，无授权弹窗）。电脑插 USB 后 adb devices 应直接出现车机。macOS / Linux 免驱；Windows 需装 adb 驱动。
② WiFi ADB adb connect 10.73.250.186:5555（persist.adb.tcp.port=5555 已固化 ⇒ 重启后自动开）。缺点：与 eSIM 测试互相干扰（见 §6）。
③ root shell 2223 车机上有 busybox telnetd 监听 2223（root 身份），iptables 只放行 loopback + 10.73.250.0/24 ⇒ 只在车机连着热点时可用；USB 方案下用不到。

取得 root 的唯一正确姿势：adb shell su 0,0 <命令>（示例 adb shell su 0,0 id → uid=0(root)）。
⚠️ 绝不要执行 adb root —— 本 ROM 上它会把 adbd 卡死在 offline，只能重启车机恢复。

1.3 车机上可用的工具（实测，别再去装东西）

工具 路径 / 用法 备注
tcpdump /system/xbin/tcpdump ✅ 可用；busybox tcpdump 是 applet not found。参数用 -i <if> -n -l -s 512
iftop / lsof / netstat /system/bin/ ✅ 可用
busybox /system/xbin/busybox（354 applet） netstat/sed/grep/sort/head/tail/awk 建议都走 busybox
uiautomator dump ✅ 拿控件精确 bounds；dump 文件属 root，adb pull 会 Permission denied ⇒ 在车机上 cat 出来
在线分析（/proc/net/tcp{,6}） ✅ 看 App 连接：busybox cat /proc/net/tcp /proc/net/tcp6 \| busybox grep ' 10025 '

车机上的”缺手”清单（会踩）：
- 没有 timeout、没有 awk（系统版）、没有 killall、nc 不支持 -u（UDP）
- head -c 不支持 ⇒ 用 busybox head -c
- sed 建议一律加 busybox 前缀（su 环境 PATH 里裸 sed 曾报 sed: No such file or directory）
- /etc/resolv.conf 不存在；adb 输出带 \r ⇒ 一律 tr -d '\r'
- adb shell 单条命令长度上限约 2100 字符（超了报 shell command too long）；长脚本用 adb push 或”分两段 base64 拼接 + busybox base64 -d | sh”

2. 网络拓扑（实测）

2.1 两块网卡

默认网络选择：Score Wi-Fi(60) > eSIM(55) ⇒ 两者都在时走 Wi-Fi；Wi-Fi 一断，eSIM 才成为默认网络。
（这正是”必须让车机不连 Wi-Fi 才能测 eSIM”的原因。）

2.2 路由与策略路由（⭐ 理解 M1 的关键）

结论：App 的 socket 会被 netd 打上所属网络的 fwmark ⇒ 按 table <接口> 的路由出去；只有”未标记 socket”才落到 main 表（= eSIM）。这就是为什么改了 netd 默认网络也拦不住 App 走 Wi-Fi（§6 M1）。

2.3 IPv6（⭐ 首要嫌疑的物理基础）

⇒ eSIM（eth0）没有全球 IPv6、也没有 IPv6 默认路由；Wi-Fi 有。而喜马拉雅的音频 CDN 恰好优先解析出 IPv6（见 §5.3）。

3. 现象与分层结论

应用 eSIM 下 DNS eSIM 下 TCP 卡在哪层 定论性
腾讯系（QQ音乐 / 腾讯视频） ❌ 域名静默丢弃（~20 s 超时） —（域名都解不出） DNS 层 ✅ 已确证
喜马拉雅 ✅ 21 个域名全正常 ✅ 抽测 80/443 能建连 DNS 之上（未定） ❓ 待 USB 复测
网易云 / 酷狗 / 高德 ✅ ✅ eSIM 上 80/443 实测建连成功 全通 ✅ 已确证

喜马拉雅的失败链（QQ音乐是 DNS，喜马拉雅不是）——所以要查的是：
- 是连接层（IPv6 无路由 / 被 RST）？
- 还是应用层（“仅 WiFi”策略拒绝取流）？

要点：
1. 屏蔽按主机名精确做——qq.com 裸域能解析，y.qq.com/music.qq.com 全被丢。
2. 与连通性无关：eSIM 下 ping 百度 IP 直连 0% 丢包 ⇒ IP 层/路由通，问题只在 DNS。
3. DNS 名义是 114.114.114.114（南京信风公共 DNS），但行为不符合公共 DNS ⇒ 更像 T-Box 拦截了 53 端口查询并套用自己的域名策略。
4. ⚠️ 被挡的表现是”卡到 ~20 秒超时”（静默丢包），不是秒回 NXDOMAIN —— 所以逐个测、单个域名 5 秒无响应即判不可达，不要批量串测（这是过去”总超时”的根因）。
5. 官方口径推测：车联网 eSIM 的”定向流量 / 服务白名单”（只对白名单服务放行/免流）。

⭐ 两个要点：① 音频走 HTTP :80（不是 443）；② 解析结果是 IPv6（240e:…，中国电信 IPv6 段）。

5.4 APK 内的线索

  • 没有任何腾讯 SDK：com/tencent = 0、bugly = 0、beacon = 0、qcloud = 0、cos.tx = 0
    ⇒ 与 QQ音乐/腾讯视频（重度依赖 wns.qq.com 等）性质不同。
  • 有”仅 WiFi”痕迹：IS_ENABLE_NETWORK_ONLY_WIFI、is_enable_network_only_wifi、WIFIONLY、cdnNotWifiAlertRate、cdnWifiAlertRate、cdnNotWifiConnectTimeout、cdnWifiConnectTimeout
    ⇒ 存在”仅 WiFi”策略，且对非 WiFi 网络另有一套 CDN 超时/告警参数。
  • SharedPreferences 里没有 is_enable_network_only_wifi 键（说明未显式写过 ⇒ 用默认值）。

5.6 未决假设（按嫌疑排序，待 §7 验证）

  1. IPv6 优先级（首要嫌疑）
    喜马拉雅把音频 CDN 解析出 IPv6（240e:978:2608:d01:70::1e）并优先使用；而 eSIM(eth0) 只有 fe80::、无全球 IPv6 地址与默认路由 ⇒ eSIM-only 时这条连接无路可走；若 App 不迅速回退 IPv4，就会卡住/超时。
  2. “仅 WiFi”策略
    eSIM 被 Android 识别为 ETHERNET（非 WiFi、非 MOBILE）；若 App 判定”非 WiFi 不取流”，会直接拒绝播放（对应 §5.4 的开关）。
  3. 连接层过滤（可能性较低）
    音频 CDN 的具体 IP/端口在 eSIM 上被 RST/限速 —— 必须用 tcpdump 看到”长包媒体数据”才能证实，只看 SYN 不算。

6. 方法学更正与判据（血泪教训，动手前必读）

6.1 三条硬结论（M1/M2/M3）

# 结论 证据 / 后果
M1 ndc network default set 1000 只改「DNS 解析路径」，不改 App 数据 socket 的出口网络 ⇒ 用它做的”eSIM 测试”根本没测到 eSIM 数据面 ip rule 把 App 的 socket 按 fwmark 绑到 table wlan0；tcpdump 实测：切了 ndc 之后 App 新连接仍从 10.73.250.186(Wi-Fi) 发出。⇒ 过去据此得出的”某 App 能/不能走 eSIM”结论不可信
M2 svc wifi disable 是持久化写入（等价在设置里关 Wi-Fi，写 settings global wifi_on=0） 一旦期间车机重启，重启后 Wi-Fi 依旧是关的 ⇒ adb(5555) 与 2223 同时失联，只能人工到屏上开。本项目禁用此法
M3 做”App 走 eSIM”的无干扰测试，正解是：让 eSIM 成为唯一数据网络，且不碰车机 Wi-Fi 开关 ⇒ USB 有线 ADB + 车机不连任何 Wi-Fi 见 §7

仍然有效的旧方法：ip rule add to <目标IP> lookup eth0 pref 100（按目标 IP 强制走 eSIM；对 nc/ping 以及 App 对该 IP 的连接都生效）。它是”逐目标”的，只能做点状验证，不能代表整体。

6.2 判据：必须防”预缓存”造成的假阳性

音视频 App 会预缓冲，网络断开后仍能继续播放一段时间 ⇒ “有声音”不等于”网通”。
判定”这一阶段它真的取到了网”，必须同时满足 4 条：

  1. 该时间窗内出现新的 DNS 查询（logcat 的 getaddrinfo / tcpdump 的 A?、AAAA?）；
  2. 出现新的 TCP 连接（tcpdump Flags [S]）；
  3. 该连接收到应答（Flags [S.]）并且有长包（媒体数据，length 明显大于 0 的一串包）；
  4. 音源是新切换的曲目（不是旧缓冲）——用 uiautomator dump 读 title_tv 文本对比。

6.3 其它必知坑

坑 说明 / 对策
媒体键控不了喜马拉雅 它的 MusicService 媒体会话 active=false、无 mediaButtonReceiver ⇒ input keyevent 126/85 无效；媒体键会被”当时活跃”的其它 App（网易云/QQ音乐）接走。只能点 UI（坐标见 §10.4）
后台 App 污染抓包 网易云、酷狗、讯飞（conn1.txzing.com）会一直在跑；抓包里出现 music.126.net、kugou.com 多半不是喜马拉雅。分析时按域名/uid 过滤
别动媒体会话归属 settings get secure media_button_receiver 会被最后注册者改写（本轮后变成了喜马拉雅的 WireControlReceiver），重启才重算
uiautomator dump 权限 dump 文件属 root，adb pull 会 Permission denied ⇒ 在车机上读
车机无 awk/timeout 脚本里别用；用 busybox 版本
adb shell 命令长度 ~2100 字符上限；长脚本 adb push 上去再跑
别用 am force-stop 停系统 App 会写持久化 stopped="true"（重启也不清），App 从此收不到任何广播（含 BOOT_COMPLETED）。要停进程用 am kill
DNS 探测要”逐个 + 5 秒超时” 被屏蔽的域名是静默丢包，批量串测必然整体超时

8. 安全红线（务必遵守）

红线 原因
绝不执行 adb root 本 ROM 会把 adbd 卡死在 offline，只能重启车机恢复
绝不用 svc wifi disable 写持久化 wifi_on=0，重启后仍关 ⇒ adb/2223 双断（§6 M2）
不对系统/厂商应用用 am force-stop 写持久化 stopped="true"（重启不清），App 再也收不到广播。要停进程用 am kill
不 kill 系统进程（com.adayo.*、com.hk.*、SystemUI 等） 影响驾车相关功能
不动嘟嘟桌面（com.wow.carlauncher.mini） 用户要求用原版，不加任何修改
不禁用 QQ音乐 App 用户要求
不改 /system、/vendor、settings 持久化项 测试应零持久化改动。回滚备份在车机 /data/local/tmp/（hk_oem_init.sh.orig / su.orig / pr.xml.bak / pr.elite.bak）
root 一律走 su 0,0 <命令> shell uid 无 CHANGE_COMPONENT_ENABLED_STATE 等权限
改前备份、改后核对、先 pull 证据再清车机 上一轮在车机上直接删了原始日志，无法回溯

9. 可选修复方向（待验证）

腾讯系（DNS 层）与喜马拉雅（DNS 之上）要分开治：

方案 做法 适用 / 风险
改 eSIM 的 DNS ndc resolver setnetdns 1000 "" 223.5.5.5 119.29.29.29 对腾讯系有效（已实测：换 DNS 后 QQ域名立刻可解析）；但连接层若还有过滤就仍会失败
DNS 重定向 iptables -t nat -A OUTPUT -o eth0 -p udp --dport 53 -j DNAT --to 223.5.5.5 同上，且可做成开机生效
静态 hosts 往 /etc/hosts 写 IP IP 会变，需长期维护
DoH/DoT 应用级加密 DNS Android 6.0 原生不支持
喜马拉雅（若确认是 IPv6 问题） 让 eth0 只拿到 A 记录；或在系统侧禁用该网络的 IPv6 需先验证假设成立
不修 这些 App 继续走手机热点 零风险
