目标游戏：暴力风暴（viostorm, Violent Storm ver EAC, Konami 1993, Konami GX 主板）

目标：把我方三名可选角色（Wade / Boris / Kyle）的攻击力在原版基础上 +80%，让打小兵更快；敌方与其它数据保持原版。

核心结论：攻击值是一张按 角色 + 动作 索引的字节表，位于主程序 ROM 0x1E924。把表中 134 个有效字节全部 round(原值 × 1.8) 即可。但只改表会让游戏卡死在开机自检——本作的 ROM 校验和是致命的，必须同时绕过自检，这一步是本次真正的难点。

1. 背景与目标

《暴力风暴》（Violent Storm）是 Konami 1993 年的横版清版动作游戏，使用 Konami GX 硬件（MAME 驱动 mystwarr.cpp，与《变身忍者》《怪兽之王》同基板）。

MAME 驱动名 版本 说明
viostorm ver EAC（Europe） 本次目标
viostormeb / viostormu / viostormj / viostorma EAB / UAC / JAC / AAC 其它区域版
viostormbl / viostormubbl / viostormabbl bootleg 盗版转换

本文所有偏移针对 viostorm（ver EAC）。

主程序区域（ROM_START( viostorm )）：

两颗 512KB 的 ROM 交替拼成 1MB 主程序（CPU 视角 0x000000–0x0FFFFF），主 CPU 为 Motorola MC68000 @ 16MHz。

补丁地址换算：CPU 地址 A 若为偶数 → 在 168eac02.15f 中偏移 A/2；若为奇数 → 在 168eac01.15h 中偏移 A/2（取整）。

2. 参考资料（网上说明）

这次确实参考了网络上的逆向资料，主要是 zengfr/romhack 仓库的 viostorm 目录（中文 IDB 笔记）：

  • Violent Storm Memory Map.txt — 内存映射
  • viostorm ROM map.txt — ROM 结构
  • ID相关程序段（最新）.txt、VIO敌方程序查表说明.txt — 动作/程序查表
  • VIO我方动作ID表+wade.xls、VIO人物结构体200223+补充敌人英文名.xls — 我方动作 ID 与人物结构体
  • 该仓库里 没有 现成的”攻击 +N%“数值教程；网上的成品是 Violent Storm暴力风暴-繁荣版hack，属于代码注入式大改（往 ROM 空白区 0x76000+ 注入新代码、在三处打 JSR 钩子），并非简单的数值表修改。

所以本次的数值定位思路参考了上述资料，但攻击表装载公式的确认、按比例放大攻击值的可行性、尤其是自检校验和这一关，全部是自行反汇编 + MAME 内存观察得到的。下面按实际动手顺序写。

3. 攻击值是怎么用的

3.1 攻击表

攻击值存放在一张按角色和动作索引的字节表里，起始于 ROM 0x1E924：

  • roleId：0 = Wade，1 = Boris，2 = Kyle（选人代码 0x1E82C: cmpi.w #$2, $4c(a0) 处可印证角色号在对象 +0x4C）
  • actionId：动作号，有效攻击动作从 0xC0 起
  • 每字节即该”角色 + 动作”的攻击值；0xFF = 该角色无此动作（哨兵，不可改）

3.2 装载代码（关键证据）

在 ROM 0x1E84E 附近找到装载逻辑（capstone 反汇编）：

即：对象 +0xA0 就是攻击值，直接从 0x1E924 表按公式取出。只要改这张表，所有角色、所有攻击动作的伤害同步变化——这正是”打小兵更快”最省事、最干净的改点。

4. 打补丁：攻击值 ×1.8

把 0x1E924 表中所有非 0x00、非 0xFF 的字节改为 round(v * 1.8)（本作攻击值都很小，×1.8 后最大 76，不会溢出字节上限 255）：

  • 共修改 134 字节，全部落在 0x1E933–0x1EA73（表头几项本来就是 0x00/0xFF，不动）。
  • 换算回两颗 ROM 文件后重打包：偶数地址的改动落到 15f，奇数地址落到 15h。

5. 踩坑：改了表，游戏起不来

打完补丁后 mame viostorm 能开到自检，然后卡死：

  • 右上出现 PROGRAM 15H BAD C01A / PROGRAM 15F BAD 6D02
  • 之后无论怎么投币、按键都不进游戏

5.1 用 MAME Lua 插件观察内存，确认是”没跑起来”

ROM workram 0x200000–0x20FFFF 非零字节
官方原版 很快升到 ~7000+（正常进游戏）
只打攻击补丁 全程只有 1–5 个（卡死）
繁荣版（成品 hack） 正常升到 ~7000+

同时发现 -skip_gameinfo 跳过的是 MAME 自己的”已知问题”提示；本作游戏自身的自检屏需要按键才会继续。但光按键过不了 BAD 屏——补丁版一直卡着。所以问题确实出在 ROM 内容。

小技巧：read_u8 读 ROM 是准的（0x1E924 读回 0xFF、0x1E800 读回 0x11，与文件一致），但读 RAM 一开始总读成 0，是因为 MAME 还停在启动信息框、CPU 根本没执行（PC=0）。排除 MAME 陈情框/自检屏干扰后 RAM 才会动。

6. 逆向：自检校验和

6.1 定位自检例程

屏幕显示的 C01A / 6D02（+80% 补丁后算出的值）是突破口。搜索 ROM 里对期望值表 0x77000 的引用，命中 0x16ABE：

描述符表 0x78BD4：

所以算法就是：对两颗 512KB ROM 分别做 16 位字节累加和，再逐片与期望值比较，不等就置错误位。

6.2 印证算法

期望值表 0x77000：BE1B（15H）、6AEF（15F）。而实际算出：

ROM 算出 15H 算出 15F 与期望
官方原版 BE1B 6AEF ✅ 通过
只打攻击补丁（×1.8） C01A 6D02 ❌ 严格不符

C01A / 6D02 正好就是屏幕上显示的 BAD 值 —— 算法确认无误：屏幕打印的就是每片的字节和。

7. 为什么不能”顺手改期望值”

最直觉的修法是：把 0x77000/0x77002 的期望值改成新算出的 C01A/6D02。但做不到，原因是两颗 ROM 的字节交错：

  • 期望字 15H = 0xBE1B：高字节 0xBE 落在 0x77000（偶地址 → 15f），低字节 0x1B 落在 0x77001（奇地址 → 15h）
  • 期望字 15F = 0x6AEF：高字节 0x6A 落在 0x77002（→ 15f），低字节 0xEF 落在 0x77003（→ 15h）

也就是两个期望字的四个字节被拆到了两颗芯片里。设四字节未知，联立”改完后期望值必须等于芯片自身的新和”：

由 (1) 唯一定出 b、c，再代入 (2) 得到 d——(2) 左边是 255 的倍数、右边一般不是整数倍，方程组无解。即：期望值表和被校验数据在同一对（且交错的）芯片里，无法自洽。所以必须走”改代码绕过”。

8. 最终修法：一行分支绕过自检

把 0x16AD4 的 BEQ（校验相等才跳过）改成 BRA（无条件跳过），错误位永远不会被置：

文件落点：168eac02.15f 偏移 0xB56A，0x67 -> 0x60，仅 1 字节。

说明：这只是让游戏自带的自检不再报错、正常放行，不改变任何正常游戏逻辑。（这也解释了为什么网上的”繁荣版”能带着改过程序的 ROM 启动——它用注入代码绕过了同类检查。）

9. 最终补丁与验证

相对官方原版，viostorm.zip 只差 135 字节：

改动 位置 数量
攻击值 ×1.8 主程序 0x1E933–0x1EA73（表在 0x1E924） 134 字节
自检校验绕过 主程序 0x16AD4（15f 偏移 0xB56A） 1 字节

验证：

  • 静态：134 个攻击字节全部满足 round(原值 × 1.8)；0x00/0xFF 哨兵保持不变。
  • mame -verifyroms viostorm → viostorm is good。
  • 动态：mame viostorm -skip_gameinfo，按键过自检屏后正常进选人/游戏；实测三名角色打小兵明显更快（本次请求的验证者已确认 P1 攻击值比原版更大）。

11. 小结

  1. 攻击值是一张 角色 + 动作 索引的字节表（ROM 0x1E924），装载进对象 +0xA0；把有效字节 ×1.8 即可，改动小、覆盖全角色全招式。
  2. 真正的坑是自检：本作对两颗主程序 ROM 做 16 位字节和并与 0x77000 表比较，不符即置错误位并卡死。
  3. 因为期望值表和被校验数据交错在同一对芯片里，改期望值无解，只能改代码绕过（0x16AD4: BEQ→BRA）。
  4. 最终补丁仅 135 字节：数值表 +80%（134）+ 自检绕过（1），实测生效。

与其说是”改数值”，不如说是”改数值之后，得先把游戏自己设的门锁拆掉”——这也是这类 Konami 老游戏做数值 hack 时最容易忽略的一步。
