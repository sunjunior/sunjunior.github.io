Everything-Linux：从逆向分析到静态分发的完整实战

2026-11-22 更新（v0.3.1beta-fused）：GUI 已改为进程内 LocalEngine，发布包只含一个约 3.6 MB 的 everything-gtk；并新增结果实时刷新：索引变化后 250ms 防抖重跑当前关键词，文件新增、删除、原子替换都会自动反映到列表。

动机

voidtools 的 Everything 是 Windows 上公认的”秒搜”神器：百万文件输入即出结果。它的秘密不在搜索算法多神，而在于直接读 NTFS 的 MFT 拿全卷文件名，再用 USN Change Journal 做增量更新——把慢活全放在建索引阶段，查询时只在内存里的预排序数组上做一次线性过滤。

Linux 上没有 MFT，也没有 USN Journal 这种稳定、按卷、可持久读取的变更日志。能不能复刻？本文记录完整过程：逆向研究 → 可行性判断 → 技术选型 → 架构设计 → 分阶段实现 → 性能验证 → 静态分发 → 部署文档。

代码全部在 ~/work/everything-research/everything-linux/，研究过程文件在同目录。当前融合版产物是 dist/everything-gtk，Linux 三平台单文件包见 GitHub Release。

一、逆向研究：Everything 到底怎么工作

样本是 Everything-1.4.1.1032.x64.zip（x86-64 PE32+ GUI，主程序 2.27 MB，SHA-256 f191f756…512e36），配一个 1 MB 的 Everything.lng。用 Ghidra 12.1.2 做静态分析（REA 工具链）。

1.2 索引来源：MFT + USN

字符串证据非常直白：

结论：自己解析 NTFS MFT，每个文件/目录对应一个 FRN；后台线程持续读 USN 日志，按 CREATE/DELETE/RENAME 等 reason 增量更新内存库；同时支持 ReFS（FRN 是 128 位）。内容不建索引，搜索时走 Windows IFilter 按需读取。

1.3 查询引擎：反编译实锤

沿字符串 term %p, flags: %04x, next: %p, notnext: %p 找到 xref，定位到 FUN_1400175a0（0x1400175a0，7129 字节），反编译 1264 行伪代码。它不是分词器，而是搜索计划编译器：

  • 真正的分词由 FUN_140065870 完成，分别编译”搜索串”和”过滤串”；
  • 每个 term 是一个结构体：[0]=next、[1]=notnext、[3]=文件求值节点、[4]=目录求值节点、[5]=flags；
  • 节点通过 +8（next，AND 链）和 +0x10（notnext，NOT/OR 分支）接线，形成线程化布尔表达式图；
  • 不同 flag（大小写/路径/变音/全词/正则/通配符）映射到不同的数值 opcode，也就是”为每种匹配模式预编译专用求值器”；
  • 特殊函数前缀 root:、empty:、dupe:、sizedupe: 等各自对应 opcode。

最关键的一条旁证来自帮助文案：

说明默认按名称排序时不需要 sort，结果就是预排序数组的一次线性过滤；按其他属性排序才要额外收集信息并排序。这就是”输入即出结果”的工程本质：用建索引时的 O(n log n) 换查询时的 O(n) 顺序扫描。

二、可行性判断

Windows 机制 Linux 现状 结论
MFT（固定 1024B 记录） ext4/XFS/Btrfs 元数据布局各异且不稳定 无法等价，退化为并行目录树遍历
USN Journal（持久、按卷） inotify 非持久、每目录一个 watch、队列可溢出 用 inotify + 快照 + 周期对账组合替代
FRN 稳定标识 st_ino+st_dev 可用但不跨挂载/不保证持久 自建 slot 作为身份

能复刻的是价值最高的部分：查询引擎、数据模型、搜索语法、持久化 DB、IPC/HTTP 接口——这些与操作系统无关。代价转移到首次全量扫描时间和事件可靠性上。

三、技术选型

选 Rust 1.99（edition 2024），全部依赖离线缓存（本机 711 个 crate）：

领域 选择 理由
并行遍历/排序 ignore/rayon 8 核并行 par_sort_unstable
文件监听 裸 libc inotify 系统调用 inotify/notify crate 未缓存；裸调用可控 cookie/overflow/watch 管理
无锁查询 arc-swap + Arc<IndexSnapshot> 查询线程全程不持锁
并发映射 dashmap + parking_lot 增量更新查表
正则/预过滤 regex + aho-corasick 预编译求值器
持久化 自定义二进制 + zstd 比 bzip2 快，.tmp 原子替换
CLI 手写参数解析 clap derive 依赖的 clap_derive/anstream 未缓存（踩坑见后）
GUI GTK3（gtk 0.18） 本机 gtk+-3.0=3.24.52 稳定；Qt crate 未缓存；Tauri/webkit 太重

为什么不选 Go（未安装）、Python（内存/性能不适合百万级常驻索引）、C++（开发效率与内存安全代价大）。

4.1 工程结构

4.2 分层与数据流

关键点：索引用 ArcSwap 原子发布不可变快照，查询线程只持有 Arc<IndexSnapshot>，零锁扫描——这正是 Everything 速度的核心。融合 GUI 中，LocalEngine 在进程内持有 Engine，后台 tick 线程与 GTK 主线程通过轻量结果通道连接；CLI 仍可走可选的 daemon socket。

4.3 关键数据结构

IndexSnapshot 维护 by_name（折叠名排序）、by_name_cs（原名排序）、by_parent。路径不常驻，查询时沿 parent 链回溯 + 根路径前缀拼接并缓存——因此 path: 查询明显更慢，与 Everything 的观察一致。

五、核心实现

5.1 查询引擎

词法/语法分析把查询编译成 Expr::{Term, And, Or, Not}：空格 = AND、| = OR、! = NOT、支持括号；前缀 startwith: endwith: regex: path: file: folder: case: wholeword: 等。每个 term 编译为专用闭包 Fn(&Ctx)->bool（预编译 regex、通配符转 regex、折叠名字节匹配），在 by_name 上单次顺序扫描 + early-out。默认结果沿用索引顺序，所以”按名称排序”是免费的。

5.2 inotify 实时增量（替代 USN）

事件路径：

为什么是 inotify 而不是 fanotify：fanotify 需要 CAP_SYS_ADMIN，语义是访问审计，拿不到可靠的目录项增删流；inotify 直接给”父目录 + 名字 + cookie”，正好映射索引身份。但 inotify 非持久、每目录一个 watch、队列可溢出，所以用快照（重启秒开）+ 溢出全量重建 + watch 失败子树对账 + 600s 周期对账兜底。

5.3 增量内存优化

最初每次变更都全量重建：复制所有名字 + rayon 重排，10 万条目要几十毫秒，百万级更慢。改成：

  • IndexSnapshot 的名字池/条目数组用 Arc<Vec<...>> 在快照间共享；
  • 只保存变更条目的 entry_overrides 和追加的名字字节；
  • 二分定位旧位置、删除、按新 key 插入——不复制全量池。

复杂度从 O(n log n) 降到 O(k·log n + 插入位移)，k 为变更条目数。用 4 个测试对比”增量结果 == 全量重建结果”（插入/删除/改名/重名文件），保证正确性。

5.4 属性过滤与 statx

新增 size:、dm:/dc:/da:、ext:：大小支持 b/kb/mb/gb 单位和 >/</.. 范围；日期支持 YYYY-MM-DD、today、相对 3d/2w/1m/1y；created 通过 libc::statx 的 stx_btime 取得（不支持时回退 ctime）。快照格式升到 v2，并兼容 v1 旧文件。

5.5 融合 GUI：从 IPC 到进程内 LocalEngine

旧版是 daemon + CLI + GUI 三段式：GUI 通过 Unix socket 查询，启动时还要释放/内嵌 everythingd。v0.3 把 GUI 改成真正的融合进程：

  • 启动时直接构造 LocalEngine，内部 Engine 用 RwLock<Arc<Mutex<Engine>>> 持有；后台 tick 线程消费 inotify 事件并增量发布索引。
  • 搜索走 search_slots，只返回 (slot, generation)；GTK 的 ListStore 只存 u32 + u64，完整路径在 cell data func 里按可见行惰性渲染，5000 行结果不再预先生成 5000 个字符串。
  • 换根时 set_auto_root 在后台 Engine::open + scan + start_monitor，旧索引继续服务查询；新索引就绪后原子替换，generation 递增使旧行自动失效，GUI 再重跑当前查询。
  • 不再释放/内嵌 everythingd，不需要 --frontend-exe、socket 或 IPC；单文件约 3.6 MB，运行时只有一个进程。

CLI/daemon 仍保留为可选接口：everything --local 直接在 CLI 进程内跑 LocalEngine（zstd 快照启动约 160 ms）；everything --local --raw <file> 使用 70 MB 的 mmap raw 快照原型，冷启动约 21 ms，但宽结果查询与 daemon 热查询基本持平，小结果仍慢 3–6 ms。

结果列表现在会跟随索引刷新：GUI 每 250ms 检查一次索引 generation，只有关键词非空、窗口可见且右键菜单未打开时才重跑当前查询；新结果先比较 slot 序列，未变化时只重绘，变化时保留选中行和滚动位置后重建。编辑器“写临时文件再 rename”的原子保存会拿到新 slot，不会再把匹配文件留在列表里变成空行。

5.6 结果右键菜单

结果列表右键某项弹出三项菜单，对齐 Everything 的常用操作：打开（默认程序打开，等同双击）、打开路径（打开父目录并选中该项）、复制完整路径和文件名（写入系统剪贴板）。通过 TreeView 的 button-press-event 命中行、选中该行后弹出 GtkMenu；file:// URI 对空格和特殊字符做百分号编码。

六、踩坑记录

  1. clap 依赖缺失：离线环境 clap_derive/anstream 未缓存，改用手写参数解析，零依赖。
  2. 包名 core 冲突：crate 叫 core 会遮蔽 Rust 标准库 core，doctest 直接编译失败，改名为 everything_core。
  3. 防抖逻辑 bug：用”本次 tick 是否收到事件”的局部变量判断重建，导致事件后的后续 tick 永远不再重建。改用持久 dirty 标志。
  4. RwLock 自杀式死锁：match slot_for_path(&self.store.read(), …) { Some(s) => self.remove_subtree(s) } 中，scrutinee 的读锁在 arm 执行时仍存活，arm 内再申请写锁直接死锁。改成先绑定变量再匹配。
  5. 静态链接 proc-macro：整个 workspace 设 crt-static 会导致 proc-macro 无法构建；改为对最终二进制用 cargo rustc -- -C target-feature=+crt-static，只对 bin 生效。
  6. GUI 移到新目录后报 IPC error: connect /tmp/...sock: 没有那个文件或目录：用户只拷贝了 everything-gtk，同目录没有 everythingd，自动拉起逻辑找不到守护进程，GUI 随后仍继续查询、又叠了一条误导性的 connect 错误。修复：守护发现按”同目录 → PATH → 常见目录 → 内嵌二进制”顺序查找；启动失败时只报一条明确错误并停止查询线程；进一步把守护进程内嵌进 GUI，单文件即可运行。（v0.3 融合版已彻底移除 daemon，此修复只保留在旧版历史中。）
  7. 大目录首次索引导致客户端启动超时：原流程先全量扫描、后绑定 IPC socket；索引 ~/ 时扫描需要几十秒，GUI 等 socket 超时就报错。修复：daemon 先绑定 socket 并启动 server 线程，扫描放到后台线程执行；客户端等待时间从 10s 放宽到 30s。这样一启动就能连接，扫描在后台进行。
  8. 程序移动后默认索引根没跟着变：配置与快照都存在 ~/.config、~/.cache，与可执行文件位置无关，移动程序后仍索引旧目录。更隐蔽的是：GUI 启动守护时传的是 --root <GUI目录>，守护把它当成”用户手动指定”，于是 auto_root=false，跟随规则此后永远失效；而且托盘常驻/已运行的守护不会因双击新程序而改变根。
    修复：GUI/CLI 改用 --frontend-exe <自身路径> 告诉守护”默认根跟随哪个程序”，由守护据启动程序所在目录设定默认根；程序移动到新目录后再启动会自动切换并重建索引；托盘常驻实例通过单实例 socket 把新程序路径转发给旧实例，旧实例再让守护切根；配置记录 auto_root / exe_path，显式 roots 或 index add/remove 仍固定根目录。
  9. --root 被默认根覆盖：命令行显式传 --root 时仍要优先于默认根。修复：守护收到命令行 --root 后立即 mark_manual_roots()；独立运行 everythingd 时默认索引其当前工作目录。
  10. 重复双击打开多个窗口：用专用 Unix socket（daemon socket + ".gui"）实现单实例，第二个进程发送 SHOW 后以退出码 0 退出；已运行实例收到请求后 show_all() + present()，隐藏到托盘的窗口也会恢复。
  11. GTK3 任务栏图标：gtk crate 0.18 未包装 GtkStatusIcon，改用 gtk-sys FFI 调用；GDK3 的 GdkEventButton 没有 click_count，双击用”400ms 内 + 位移 <8px”自行判定；右键菜单含”打开界面/退出”，点窗口 X 只隐藏到托盘，app.hold() 保证主循环不退出。
  12. 搜索框拿不到输入焦点：从托盘恢复、单实例唤起或双击启动时机不同，搜索框可能没有焦点，导致输入法不生效。修复：窗口 show 后 set_focus + grab_focus，再用 idle_add_local_once 延迟补一次；窗口重新获得焦点（focus-in-event）时若搜索框未聚焦则重新抓取。
  13. 从 Thunar 双击启动后无法使用中文输入法：排查发现 GUI 进程环境里完全没有 GTK_IM_MODULE / XMODIFIERS——启动它的 Thunar 本身比输入法变量设置更早启动，子进程继承不到，GTK 因此不加载 im-fcitx5.so（so 库本身完好）。这不是缺库，而是启动链环境缺失，任何”老启动”的启动器都可能复现。
    修复做成与文件管理器无关的两层自愈：① GTK 初始化前，若 GTK_IM_MODULE 为空，扫描 /proc 探测运行中的 fcitx5/fcitx/ibus-daemon 并补全环境变量；② GTK 初始化后用 GtkIMMulticontext 检查实际上下文，若仍是 gtk-im-context-simple 说明模块未加载，则补全环境并重新 exec 自身一次（EVERYTHING_IM_REEXEC=1 防循环）。实测去掉全部 IM 环境变量、甚至故意设 gtk-im-context-simple，重启后都能正常输入中文。
  14. “打开路径”只打开目录、没有选中文件：最初只是用默认程序打开父目录，和 Windows Everything 的“打开文件所在位置”不一致。修复：优先调用标准 org.freedesktop.FileManager1.ShowItems（Nautilus/Dolphin/Nemo/Caja/Thunar 4.18+ 支持），打开父目录并高亮目标；不支持时回退到 nautilus/dolphin/nemo/caja --select，最后才仅打开目录。已用程序内同一调用路径验证 Thunar 正确打开目标目录。
  15. 换根持有引擎锁约 2.4 秒：set_auto_root 最初在锁内 Engine::open + scan，期间所有查询阻塞。修复：后台构建新 Engine，旧索引继续服务，完成后原子 swap；重建期间暂停旧 tick，并做好 monitor 交接和失败回滚。94 万文件实测重建 2378 ms，查询 P95 16.4 ms。
  16. 换根后旧结果行仍可见：ListStore 里保存的是旧索引 slot，新索引换入后这些 slot 可能指向别的文件。修复：每行带 generation，单元格渲染时校验；换根后重新执行当前查询。
  17. SDK 测试污染用户配置：LocalEngine::set_auto_root 最初会顺手保存全局配置，测试用临时根目录时把 ~/.config/everything-linux/config.toml 覆盖成测试路径。修复：SDK 不再写配置，GUI 在换根成功后显式 save_config()。
  18. 5000 行 ListStore 全存路径：旧实现每行一个 String，搜索时先构造全部路径再显示。改成 slot + generation 后，ListStore 只存 12 字节/行，路径按可见行生成，宽结果查询快约 30%。
  19. 融合版右键菜单突然消失：结果行最初存的是索引 generation，而 inotify 每处理一次变化就递增 generation，右键时校验 row_gen == engine.generation() 几乎必然失败，菜单直接不弹。修复：行 generation 改为只在整体换根时递增的 root_generation，普通增量不再使菜单失效；换根时旧行隐藏并自动重跑当前查询。
  20. 搜索后列表一直静止，编辑器保存后文件消失：GUI 最初只在输入框变化时查询，inotify 虽然更新了索引，但结果列表不重新查询；原子保存删除旧 slot 后，惰性渲染拿不到路径，行就变空了。修复：监听索引 generation，250ms 防抖重跑当前关键词；词不变时保留选中行和滚动位置，菜单打开或窗口隐藏时暂停，恢复后补刷新。

八、性能验证

环境：Arch Linux x86-64，内核 7.2.9，8 核，31 GiB；数据集 106 万条目（94 万文件 + 12 万目录）。

指标 结果
单进程 GUI RSS / PSS 186.3 MB / 125.7 MB
旧 daemon + GUI RSS / PSS 190.7 MB / 138.3 MB
GUI 可执行文件 3.6 MB（旧版 5.5 MB）
zstd 快照 约 25 MB
冷索引 2.4–2.7 s
换根后台重建 2378 ms，查询 P95 16.4 ms
子串 *.rs 8.9 ms（GUI 状态栏 10.6 ms）
文件名 main.rs 8.6 ms
按大小排序 7.5 ms
全路径 path: 51.1 ms
无命中 6.9 ms

融合后省掉 daemon 进程和 IPC，单进程比旧 daemon + GUI 的 RSS / PSS 分别低约 4 MB / 13 MB，窗口首次显示从 558 ms 降到 536 ms。宽结果查询受益于 slot + 惰性路径渲染，*.rs 从 14.8 ms 降到 8.9 ms，全路径从 58.9 ms 降到 51.1 ms。

换根实测：旧索引为 /home/sunjunior（94 万文件），后台重建同一根耗时 2378 ms；重建期间持续查询的中位数为 11.2 ms、P95 为 16.4 ms、最大 21.6 ms。对比修改前，换根会持有引擎锁约 2.4 s，期间查询全部阻塞。

raw mmap 原型：70 MB 文件，冷启动约 21 ms（daemon 路径约 896 ms），宽结果查询与热 daemon 基本持平；小结果/全路径仍慢 3–6 ms。由于磁盘占用和保存流程尚未接入，本轮不随发布包提供 raw 快照。

已完成：并行建索引、SoA 内存索引、查询引擎（布尔/通配符/正则/大小写/全词/路径/排序）、属性过滤、zstd 快照、inotify 实时增量 + 增量快照、可选 IPC/守护/CLI、融合 GTK3 GUI（进程内 LocalEngine / 托盘驻留 / 单实例 / 结果右键菜单 / 输入法自愈）、后台换根与原子切换、slot 惰性渲染 + Top-N、raw mmap 原型、Linux 三平台单文件发布、结果实时刷新、v0.3.1beta-fused Release。

结语

Everything 的”魔法”其实是可以拆解的工程取舍：把慢活前置到索引阶段，查询阶段只做内存里的顺序扫描。Linux 上没有 MFT/USN，但用「并行遍历 + inotify + 快照 + 周期对账」可以复刻出同数量级的体验。最终 GUI 把索引器、查询和界面收进一个约 3.6 MB 的进程，换根也不再阻塞查询——对”一个文件启动、升级只替换文件”这个目标来说，融合架构比 daemon + IPC 更简单，也更好维护。
