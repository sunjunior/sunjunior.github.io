一句话结论：把一台 2013 年的 ZTE Grand S（Android 4.1.2 / 内核 3.4 / ARMv7，触摸失灵）改造成常驻 Linux 小主机：
免提示 root、开机自动无线 adb 与 sshd、系统精简到 33 个包（停用 15）、
用 12.6 KB 的自写控制台 App 取代 149 MB 的定制桌面，屏幕实时显示日志（内存环形缓冲、不落盘），
并借 SSH / Tailscale 成为一台长期在线、低功耗的远程节点。
最后把 11.4 GB 的 sdcard 分区从 FAT32 改为 ext4，直接在整分区上跑 Arch Linux ARM
（Python 3.14 / Node.js 26 / Git 2.56 齐全），ssh zte-grand-s 登录即进入 Linux。

0.2 开机自动初始化链

开机时由 init 触发，已固化为自动执行，无需人工干预：

  1. /init.target.rc 调用 ext4check.sh mmcblk0p26 GROW —— 已修改该脚本的 GROW 分支为直接退出，
    避免把 ext4 分区重新格式化成 FAT32（详见 §5.22.5）。
  2. /system/etc/install-recovery.sh（init 的 flash_recovery service）自动
    mount -t ext4 /dev/block/mmcblk0p26 /storage/sdcard0，并以 -shell /data/local/tmp/sshd/chroot-shell.sh 启动 sshd。
  3. SSH 登录后由 chroot-shell.sh 自动进入 Arch。

验证方式：ssh zte-grand-s 'cat /etc/os-release; python --version; node --version; git --version'。

5.1 建立 ADB 通道

现象：adb devices 为空，USB 上只能看到一个 HD WebCam（另一个设备）。

根因：手机处于「安装驱动」的 UMS 模式，USB 描述符是 USB\Class_08（大容量存储），

5.2 root 免提示

设备已预装 SuperSU v0.99（eu.chainfire.supersu），su 为 /system/xbin/su（setuid root）。

现象：su -c id 卡住 240 秒直到超时。

1. 手机停在锁屏，SuperSU 授权框在锁屏下方，无人可点；
2. SuperSU 的 默认操作被设为「拒绝」。

处理：解锁后进入 SuperSU → 设置 → 默认操作 → 授权。

5.4 部署 sshd

  • 编译为 ELF32 ARM 静态链接（无 linker、无 libc），4.1 直接可跑；

5.7.6 CPU 数值的含义

显示的是当前在线核心的平均占用（0–100%）：

  • 不是每核相加（那样最大是 400%）；
  • 不是 loadavg（那是运行队列长度，4 核满载时约 4.0）；
  • 实现是逐核读 /proc/stat 的 cpuN 行，只累加“两次采样都在线、且 idle 增量合法”的核。

为什么不用汇总行（cpu）：这台机器的 mpdecision 会热插拔核心，离线核的计数会从汇总里消失。
实测汇总行的 idle 从 134122 掉到 133725（倒退），按汇总算会得到负值或假 100%。

5.13 USB 兜底通道与排查结论（2026-11-15）

架构定位：SSH 为日常主通道（不依赖 adbd），USB adb 为物理兜底。

4.1 的限制：adbd 一次只服务一种传输——设置 service.adb.tcp.port=5555 时，USB 侧不会接 adb。

自动兜底（guard.sh）：连续 5 分钟没有 IP →
setprop service.adb.tcp.port "" + stop/start adbd（切 USB）；网络恢复后自动切回 TCP。
代价只是 adb connect 不可用，SSH 不受影响。

实测枚举问题（同一根线、同一个口，四种功能组合都复现）：

sys.usb.config 手机侧 PC 侧
cdrom,adb state=CONNECTED，主机完成配置（config #1: android），无断开事件 出现约 5 s，事件日志显示枚举为 PROD_FILE-CD_GADGET 后消失

mass_storage,adb PID 1351，LUN 无后端文件 驱动全部 OK，15 s 仍消失

5.21.3 关键技术障碍与解法

障碍 1：sdcard 是 FAT32，单文件 ≤ 4 GB。

  • 误区纠正：noexec 只影响「直接执行 sdcard 上的文件」，不影响把镜像文件存在 sdcard 上。
    镜像经 loop 挂载后是 ext4（默认 exec），可以执行二进制。
  • FAT32 真正的限制是单文件上限（2³²−1 ≈ 4 GB）。所以镜像定为 3.5 GB（count=3500），
    足够装下完整 rootfs（解压 ~1.7 GB）+ python/nodejs/git（~0.5–1 GB）+ 余量。
  • FAT32 不支持稀疏文件：dd seek 建稀疏镜像报 Invalid argument，必须真实写入 3.5 GB。

障碍 2：手机端无法解 tar.gz。

  • 这台机器的 /system/bin/gzip 是精简版：支持 gzip 文件（压缩）和 gzip -d 文件（解压），
    但不支持 -dc（输出到 stdout），也不支持 --help。
  • busybox 1.8.1 的 tar 支持 -z，但内部调 gzip 失败 → tar xzf xxx.tar.gz 报 corrupted data。
  • 验证结论：
    • ✅ gzip -d 文件.gz（生成同目录的「文件」）可用
    • ✅ busybox tar xf 文件（解纯 tar）可用
    • ❌ busybox tar xzf xxx.tar.gz / gzip -dc 不可用
  • 所以解压链路固定为：先 gzip -d 得到纯 tar，再 tar xf（两步分开）。

障碍 3：电脑↔︎手机的 DERP 链路传大文件极不稳定。

  • SSH（scp/stdin 重定向）、adb push 传 >1 MB 频繁超时中断；手机同时下载时链路会被占满到 SSH/adb 都断。
  • 解法：让手机自己从公网下载（curl 稳定 ~320 KB/s，770 MB 约 37 分钟下完，MD5 校验一致）。
  • 镜像压缩文件（3.5 MB）的传输：Mac 起支持 Range 的 HTTP 服务（普通 python -m http.server
    不支持 Range，返回 200 而非 206，导致 curl -C - 无法续传），用自写 rangeserver.py 后
    curl -C - 断点续传成功，MD5 85bc97780cf04f9db7758d2d275c6bf8 一致。

关键坑：gzip 解压输出位置。 gzip -d /path/x.gz 输出到源文件同目录。
最初在 /data/local/tmp 解压 3.5 GB 镜像，/data 只剩 1.8 GB 直接写满到 98%；
应先把压缩包 mv 到 sdcard（10 GB 可用），在 sdcard 上 gzip -d，输出也落在 sdcard。

10. 安全边界

  • 5555 常开且 ro.adb.secure 未设置 → 同网段任何人都能控制设备；
  • SuperSU 默认「授权」 → 任何应用静默获得 root；
  • 登录口令（文中以 <password> 占位）本身是弱口令，离线爆破很快；仅用于可信内网；
  • /data/local/tmp 被放宽为 0755（为了 App 能读 FIFO），同网段 root 用户本来就能访问；
  • 建议：不用时 setprop service.adb.tcp.port "" + 重启 adbd，或直接在路由器上隔离该设备。
