0. 结论速览（先读这段，均为 2026-11-01 最终定论）

  1. eSIM 链路上存在一台”网络深处的中间盒”，对特定 App 流量做选择性过滤，过滤分三层：
    • DNS 域名级：.qq.com 子域静默丢弃（裸域放行），只影响腾讯系；
    • IP 级：对命中名单的 CDN 节点伪造 RST 强行拆链（TTL 恒 147、IP ID 照抄我方 SYN、PC 直连正常）——影响喜马拉雅 1.7.1 / 网易云的部分节点；
    • 传输层：明文 HTTP:80 被整体处理（按 Host/路径做内容 DPI，见 openaudio... 请求 ~30 分钟内节点被拉黑）；TLS/443 不可见 ⇒ 这是最终分水岭。
  2. 喜马拉雅 1.7.1 的失败是三层叠加：① 系统以太网状态卡 CONNECTING → isConnectNetwork 预检测判”无网”根本不发请求；② CDN 节点被伪造 RST；③ 音频走明文 HTTP:80，内容可被 DPI 并拉黑。换 CDN 节点/NAT 只能验证，不可持续（实测节点会被明文请求”烧”掉）。
  3. 最终处置：换 5.0.0 车机版（音频原生走 TLS/443）——已实测 eSIM 下正常播放，无需 NAT、无需补丁；1.7.1 走明文 HTTP，在当前链路不可持续，已停用。
  4. 网易云”当前网络不可用”与喜马拉雅无关：是系统以太网 DHCP 复触发超时后 NetworkInfo 卡死在 CONNECTING，App 按 isConnected() 判离线；临时修复 ifconfig eth0 down/up 已验证，离线补丁方案已设计、待上车验证。
  5. 早前”IPv6 无路由”“仅 WiFi 策略”“DNS 解析失败是喜马拉雅主因”“封禁按 IP 仓库、换节点可持续”等结论均已被实验证伪，正文中仅在所属阶段保留并标注。

1. 背景

一台别克英朗车机（AC8317，Android 6.0）通过内置 T-Box 的电信车联 eSIM 联网（T-Box 以 RNDIS 方式接到车机 eth0，Android 把它识别为 ETHERNET）。测试发现一个明显的”网络差异”：

App eSIM 流量下 手机热点（Wi-Fi）下
高德地图 ✅ 正常 ✅ 正常
网易云音乐 ⚠️ 大多正常，偶发连不上 ✅ 正常
喜马拉雅车机版 1.7.1 ❌ 放不出声 ✅ 正常
喜马拉雅车机版 5.0.0 ✅ 正常 ✅ 正常
QQ 音乐 / 腾讯视频 ❌ 不可用 ✅ 正常

同一个 App，只在 eSIM 下坏、切到 Wi-Fi 就好——说明不是服务器问题，而是eSIM 链路本身对部分应用的流量做了选择性过滤。早期猜测集中在”IPv6 无路由”“仅 WiFi 策略”“DNS 被劫持”等方向，经过五个阶段的实验，最终确认根因是链路上网络深处的中间盒（详见阶段二~四），并一并解决了网易云的”网络不可用”（阶段五，与 eSIM 过滤同源于”以太网状态机卡死”这一系统性问题）。

2. 目标

  1. 查明差异机制：对每个 App，定位它在 eSIM 链路上到底卡在哪一层（DNS / TCP 连接 / 明文内容过滤 / 应用层判定 / 系统状态字段）。
  2. 修复喜马拉雅：让喜马拉雅在 eSIM 下可以正常播放，且方案可长期使用。
  3. 查明网易云：解释”能加载内容但点卡片提示网络不可用”的矛盾现象，并给出修复。
  4. 方法学正确：保证每一轮测试真的走的是 eSIM 数据面（早期因此吃过亏）。
  5. 零持久化改动：全程不改 /system、/vendor、固件与 persistent settings；设备必须始终可回滚。

4. 阶段拆解：每个阶段的破解目标、方案与结果

整个过程按认识推进分为五个阶段。每个阶段写清楚：本阶段目标 → 采用的方案 → 关键结果 → 发现的问题。问题与闭环状态集中在第 5、6 章。

阶段一（10-23 ~ 10-24）：方法学建立与腾讯系 DNS 定论

目标：确认各 App 在 eSIM 下卡在哪一层，先拿最容易复现的 QQ 系开刀。

方案：同一台车机、同一批域名，eSIM（114.114.114.114）与 Wi-Fi 下分组 A/B 对比解析；logcat 看 QQ 音乐失败链。

结果（已定论）——腾讯系第一层：DNS 子域被静默丢弃：

域名 eSIM（DNS 114.114.114.114） Wi-Fi
y.qq.com / c.y.qq.com / music.qq.com ❌ 超时（~20s，无应答） ✅
wns.qq.com / dl.stream.qqmusic.qq.com ❌ 超时 ✅
v.qq.com / vv.video.qq.com / api.video.qq.com ❌ 超时 ✅
imgcache.qq.com / weixin.qq.com / 3g.qq.com ❌ 超时 ✅
qq.com（裸域） ✅ 113.108.81.189 ✅

特征：
- 按主机名后缀屏蔽（.qq.com 全丢，裸域放行），与连通性无关（eSIM 下直连百度 IP 0% 丢包）；
- 被挡是静默丢包（卡到 ~20s 超时，不是 NXDOMAIN）⇒ 测域名必须逐个 + 5 秒看门狗；
- DNS 名义是 114.114.114.114，但行为不符公共 DNS ⇒ 更像 T-Box 接管了 53 端口套用点到服务白名单；8.8.8.8 同样被接管，223.5.5.5 未被接管，换成它后域名立即解析成功。

QQ音乐失败链（logcat 实证）：

本阶段发现的问题（详见第 5 章 P3/P4）：
- M1：早期用 ndc network default set 1000 切”默认网络”做的 eSIM 测试根本没测到 eSIM 数据面（只改 DNS 路径）；
- M2：svc wifi disable 是持久化写入，导致一次 adb/2223 双断事故；
- 喜马拉雅留在”未定论”状态，理想嫌疑是 IPv6 优先、“仅 WiFi”策略 ⇒ 流入阶段二。

阶段二（10-24 晚 ~ 10-27）：USB 有线复测，排除 IPv6，确认伪造 RST

目标：在无干扰条件下（USB ADB + 车机不连任何 Wi-Fi，eSIM 成为唯一数据网络）补齐喜马拉雅结论；验证/证伪 IPv6 与”仅 WiFi”两个假设。

方案：
1. esim_test.sh 一键取证：eth0 抓包 + 触发换曲 + 汇总 DNS/SYN/长包/连接表/标题（脚本见附录 A.1）；
2. 逐域名分组对比（喜马拉雅 21 个域名 / 腾讯系 / 网易云 / 高德）；
3. 用 PC 侧 DoH 绕过本地假 DNS 复核 CDN 真实 IP；
4. 同 IP 换 Host / 同请求换链路的矩阵实验，定性过滤点。

结果：
1. 喜马拉雅 21 个域名全部解析正常、实际走 IPv4 明文 HTTP:80（/proc/net/tcp6 里是 v4-mapped 地址）⇒ IPv6 假设证伪、“不是 DNS 层屏蔽”。
2. 喜马拉雅的卡点是连接层：主音频 CDN（openaudio.cos.tx.xmcdn.com → 58.216.102.40 等”部分节点”）对 eSIM 出口 IP 回 RST/黑洞，TCP 握手建不起来；而同域名其它可达节点完全正常。素材归属：接口/封面/自有 CDN 全通，只有音频本体所在的一批（腾讯云 COS）节点被拦。
3. 伪造 RST 的取证特征（关键）：

特征 真实主机 被拦 IP 的 RST 含义
IP TTL 49–53 恒为 147 生成点固定、离车机很远
IP ID 各自独立递增 逐个照抄对应 SYN（6/6 一致） 无状态设备”照着请求造回包”
DF 位 按各自策略 被清掉 与发出的报文不一致
端口 — :80 与 :443 一样被 RST 与端口无关
同 IP 从 PC 连 6/6 OK — 过滤按源触发

⇒ 链路上有一台网络深处的中间盒，对「源=车机 eSIM 出口 IP，目的=命中名单的 IP」组合伪造 RST 强行拆链（不是 T-Box 瞬回、不是目的服务器）。
4. 腾讯系第二层：同 IP 只换 Host 明文请求（车机 → 106.11.28.122:80），Host: baidu → 404，Host: qq.com / music.163.com / sohu.com → 零响应；Wi-Fi 下同 IP 同请求全通。⇒ 过滤点在 eSIM 链路侧，按明文 Host 做 DPI；HTTPS 不受影响。车机本地 iptables 无规则、无系统代理 ⇒ 本地无法绕过。
5. 网易云：54/54 解析全成功，但同样有部分音频 CDN 节点被 RST（m7/m701 节点车机 0/4、PC 4/4）；抽到坏节点就失败 ⇒ “大多数时候能用”。
6. 高德：全通（:80/:443 均正常应答）。

小结：eSIM 链路是两张名单的选择性过滤——域名级（DNS，只影响腾讯系，改 DNS 可解）与 IP 级（伪造 RST，影响喜马拉雅/网易云的部分节点）。IP 级的”可达节点完全正常”当时被视为修复的突破口（后续被阶段四修正：可达节点只在 TLS 下持续成立，NAT 导流不可持续）；“仅 WiFi 策略”嫌疑本轮仍未拆 ⇒ 流入阶段三。

阶段三（10-31）：喜马拉雅专项诊断，证明”换 CDN 节点即可播”

目标：① 拆掉喜马拉雅失败链上的每个假设（反编译排除法）；② 版本间对比找规律；③ 用最小干预 A/B 证明根因，并产出一个可长期使用的修复。

方案与结果：

  1. 反编译排除法（1.7.1，com.ximalaya.ting.android.car，versionCode 11）——下列假设全部证伪：

    假设 验证方式 结果
    “仅 WiFi”策略拦截播放 反编译 + 补丁实测 ❌ isConnectToWifi() 全 dex 只有 1 个调用者 DownloadService.getErrorMessage()（仅下载错误文案）；改恒 true 后播放仍失败
    改网络类型上报即可 把 getNetWorkType 兜底改 3G/WIFI 后抓包 ❌ 播放地址仍是 openaudio...，CDN 主机不变
    1.7.1 的 ACCESS_TYPE_ETHERNET 可复用 字符串引用追踪 ❌ 只存在于友盟 SDK u/aly/ag，死代码
    Linkeye/HttpDNS 可注入”域名→IP” 反编译 HttpDNSLibManager + 调用点 ❌ getDomain() 只被下载模块使用
    HttpDNSInterceptor 可改请求目标 引用追踪 ❌ 死代码，全 dex 无实例化
    CdnConfigModel 可改选路 调用点分析 ❌ 仅用于 CDN 统计上报
    改 playUrl 常量即可 字符串检索 ❌ openaudio.cos.tx.xmcdn.com 不在 dex 中，是服务端动态下发

    喜马拉雅 APK 内没有任何腾讯 SDK，与 QQ 音乐重度依赖 wns.qq.com 性质不同。

  2. 版本对比（1.7.1 / 3.0.1 / 5.0.0）：

    1.7.1 3.0.1 5.0.0
    SDK 层网络判定 getTypeName() 只认 WIFI/MOBILE，其余 → NETWORKTYPE_INVALID 已有 NETWORKTYPE_ETHERNET 同 1.7.1（SDK 层仍判 no_network）
    车机层以太网识别 ❌ 无 ❌ 无 ✅ car.base.s.a.c()：getType()==9 → NETWORK_ETHERNET
    车机业务参数 无 networkMode 无 carbusiness.j.b → networkMode=ethernet
    eSIM 下表现 ❌ 播放失败 ❌ 首页显示”无网络连接”，零请求 ✅ 加载 + 播放正常

  3. CDN 节点矩阵（A/B 实测）：同域名下，部分节点 ❌（58.216.102.40 等），部分节点 ✅（122.193.250.53 等，TCP 通 + 200 OK）。⚠️ 名单会滚动，判定必须同一分钟、同一条链路上做 A/B。

  4. 关键 A/B 实验（iptables DNAT）：

    • 条件：WiFi 关闭、eSIM 为唯一网络、1.7.1 原版无任何补丁；
    • 干预：iptables -t nat -A OUTPUT -p tcp -d 58.216.102.40 --dport 80 -j DNAT --to-destination 122.193.250.53:80；
    • 结果：无重定向弹「发生网络错误」；有重定向 ✅ 正常播放（35 秒收到 331,980 字节 ≈76kbps，与码率吻合）。

    ⇒ 证明：换一个可达的 CDN 节点就能播，且与网络类型上报无关。当时据此把修复方向定为”把播放流量导向可达节点”——该方向随后被阶段四修正：明文 HTTP:80 的请求会暴露 Host/路径，使节点 ~30 分钟内被中间盒拉黑（“烧 IP”），NAT 导流只能作临时验证手段。

阶段四（11-01）：找到第一道闸门 isConnectNetwork，最终定论”明文 HTTP vs TLS”

本阶段是最终定论，优先级高于阶段三中”封禁按 IP、换节点可持续”的旧判断。CDN 节点封禁依然存在，但它们是第二层。

目标：解释 1.7.1”点击播放即弹网络错误、却几乎不发请求”的反常；把 1.7.1 补丁做到真实可用；给”长期正确”修复下结论。

1）真正的第一道闸门：系统”说”没网（应用层预检被拦）

1.7.1 点击播放后根本不发音频请求，因为它在取播放地址前就要过了 PlayerUtil.isConnectNetwork(Context) 这一关；而该函数拿到的 NetworkInfo 是错的——系统把以太网报成”未连接”：

  • 该代理被注册为 legacy type 0（MOBILE），30 秒采样 6 次状态恒定；
  • App 请求参数自证：...&network=no_network&operator=未知。

补丁落点：isConnectNetwork 只有 29 个代码单元、唯一调用方 AudioFileRequestHandler.readData（恰是播放数据读取循环），可等长改写、dex 布局不变。把”读 isConnected()“换成”真实探测 183.60.159.11:443（Socket+connect）“。

2）最终分水岭：明文 HTTP vs TLS

5.0.0 1.7.1
音频主机 aod.cos.tx.xmcdn.com openaudio / openaudiopay
协议/端口 TLS / 443 明文 HTTP / 80
抓包 684 包发往 117.92.139.39:443，0 个明文 Host 781 包发往 218.93.70.77:80，16 个明文 Host: openaudiopay...

三条独立验证：
1. 同一个 IP，两种命运：117.92.139.39 的 443 大量 TLS 流量正常；同 IP 的 80 端口连 www.baidu.com 都无响应——这条链路上的 80 明文被整体处理。
2. PC 侧直连：同一个 bucket 支持 HTTPS（https://openaudio.cos.tx.xmcdn.com/...mp3 → 122.193.250.53/443 返回 206），1.7.1 只是不用。
3. 换端口逃逸失败：被封 IP 的 8080/8443 同样 RST，不是”只封 80”。

⇒ 结论：5.0.0 能用不是”更抗封”，而是它全程走 TLS，中间盒看不到 Host/路径；1.7.1 每发一次明文 Host: *.xmcdn.com 就等于告诉中间盒这个 IP 是喜马拉雅节点——这也是为什么 DNAT 方案”自己把自己烧掉”：实测一次 DNAT 成功下载（32 次 206）后，约 30 分钟同一个节点从 206 变成全网被 RST。加上 DNS 多 IP + App 跨会话缓存旧 IP + 名单滚动，静态 DNAT 必然漏。NAT 只能作临时验证，不能作长期方案。

3）其它补充结论：
- CDN 按 bucket 分区，不能把 1.7.1 流量直接导到 aod 节点（aod Host → 206，openaudio Host → 403）；
- 直接改 App 走 https 不可行：base.apk 无硬编码 https://，音频 URL 是服务端下发的 http://；
- 1.7.1 若坚持要复活只剩两条路：车机端 HTTP→HTTPS 包装代理、加密隧道/VPS（本次不再投入）。

阶段五（11-01 晚）：网易云”当前网络不可用”的同源定位

目标：解释矛盾现象——eSIM 下网易云首页/推荐/缓存歌都正常，但点首页卡片弹「当前网络不可用」；开 Wi-Fi 同一操作就好。

  2. 正是这个字段被 App 当判据：反编译网易云 com.netease.cloudmusic.utils.c0.g(NetworkInfo)：

    isNetworkAvailable() 只看返回值是否为 0。
  3. 开 Wi-Fi 为何好：getActiveNetworkInfo() 变成 TYPE_WIFI + isConnected() → return 2，判断通过。与 eSIM 通不通无关，纯粹是状态字段问题。

验证与处置：
- ifconfig eth0 down ; sleep 2 ; ifconfig eth0 up → 2 秒内回 CONNECTED，点”每日推荐”直接进入播放页 ✅（临时修复：链路 up 事件后再触发会复发）。
- 加固尝试：开机看门狗（crond + down/up）逻辑可行但 /system 只读、remount 被拒 ⇒ 开机钩子写不进去，已全部撤除；静态 IP 属持久配置不采用。
- 选定方案（待验证，未闭环）：离线给网易云打补丁——目标 Lcom/netease/cloudmusic/utils/c0;->g(...)I，只改 1 条 if-eqz 跳转目标（“!isConnected() 就 return 0” 改为 fallback 到 return 4）；需重签 → 先卸载、备份 App 数据、回填并 chown 新 uid。原版 ne_base.apk（25.2MB）已备份。

3. dumpsys media.audio_flinger 客户端 A，AudioTrack: write 持续增长；
4. tcpdump 入站流量来自预期节点端口；
5. UI 无”发生网络错误”弹窗。

判据：网络正常时 2–3 秒内必须有响应，超过 3 秒即失败。

关键 dex 补丁技术要点：
1. 只做等长指令替换 / 零引用字符串槽覆写 ⇒ dex 布局零改动；
2. 覆写后重算：SHA-1 写 0x0C（覆盖 d[32:]）、Adler-32 写 0x08（覆盖 d[12:]）；
3. 重签：更新 MANIFEST.MF、CERT.SF 中 classes.dex 摘要 + SHA1-Digest-Manifest，对 CERT.SF 做 PKCS7 v1（SHA1） 签名写 META-INF/CERT.RSA；
4. VerifyError 报错在安装时 dex2oat 日志找，别只看运行时；
5. sget-object 操作码是 0x62，0x60 是 sget。

A.6 网易云补丁方案（阶段五，待验证）

  • 目标方法：Lcom/netease/cloudmusic/utils/c0;->g(Landroid/net/NetworkInfo;)I
  • 改法：把 “!isConnected() return 0” 分支的 1 条 if-eqz 跳转目标改变 fallback 条路——只要 getActiveNetworkInfo() 非 null 即按”有网”对待；真断网时对象为 null 仍返回 0。其余逻辑不动。
  • 部署注意：重签 → 先卸载（登录态丢，先 root 备份 App 数据回填并 chown 新 uid）；ABI armeabi-v7a。
  • 验证判据：点首页任意卡片正常跳转、无「当前网络不可用」提示。
