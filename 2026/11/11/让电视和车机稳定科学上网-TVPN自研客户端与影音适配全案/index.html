让电视和车机稳定科学上网：自研 TVPN 分流客户端、去广告治理与影音适配全案

1. 起点：网络不是「慢」，是被选择性过滤

一切源于一次故障排查：腾讯系电视/车机应用加载缓慢、CDN 解析异常。抓包后发现，网络链路上存在一台中间盒，对流量做了三层选择性过滤：

层 机制 表现
DNS 域名级 .qq.com 等子域被静默丢弃（裸域放行） 解析不到正确 CDN
IP 级 命中名单的 CDN 节点伪造 RST TCP 握手失败
传输层 明文 HTTP:80 按 Host 做 DPI 请求被识别、限速或拉黑

关键判断：腾讯系电视/车机应用大量使用明文 HTTP（tv.t002.ottcn.com 之类），App 内无法改 HTTPS，不在本地建隧道就无法绕过。一旦流量被封装进 VPN 隧道，中间盒看到的只是一条到出口的加密连接，上述三层过滤全部失效。

另一个环境事实：电视端没有 GMS，YouTube 官方客户端装不上 → 只能找无 GMS 依赖的第三方播放器（选定 SmartTube）；车机端则需要一个能按应用分流、不给整机流量加密的通用出口。

于是「自研客户端」和「影音适配」被合并成同一个需求。

2. 两台设备，两套权限边界

机顶盒 创维 Q6011（eros-p1） 车机 AutoChips AC8317
Android 10（userdebug） 6.0
内存 979 MB，紧张 1.8 GB，宽裕
adb root ❌ 厂商改写 adbd，返回自定义错误 ✅ 默认支持，adb shell 即 uid 0
su（setuid） ✅ /system/xbin/usrchan（口令可由 ro.serialno 推导，11-10 逆向还原） ❌ 无
App 级 root ❌ ❌
厂商管控 后台白名单 / 广告包自恢复 / pm 拦截 无

两端共同点是都没有 App 级 root，所以客户端架构不分叉：只能走官方 VpnService。adb shell 级 root 的差异只影响调测手段。机顶盒的 usrchan 提权是后期逆向出来的——全志方案的 /system/xbin/usrchan 是 setuid root:shell，口令由序列号经 HMAC 推导，等于一条内置提权通道（细节不展开）。

3. TVPN：一个 240KB 的自研 VPN 客户端

选型对比：sing-box/通用内核 30MB+ 在 1GB 内存设备上压力太大，放弃；纯 Java 协议栈风险高，放弃。最终方案：

  • 按应用分流：白名单模式，VpnService.Builder.addAllowedApplication() 只把目标 UID 拉进 tun，其余应用完全不受影响；
  • DNS 进隧道（26.26.26.2），DNS over TCP 到节点侧 resolver；
  • 上游自动切换：4G ↔︎ WiFi 热点 rebinding，切换瞬间断流自动重连；
  • 体积：APK 约 240KB；内存：运行期 RSS 约 34MB；
  • 单 APK 同时兼容 Android 6.0 与 Android 10（minSdk 21），两端共用。

一个典型的静默失败坑：白名单包名拼错（xbrowse vs xbrowser）代理不报错，但应用不走 VPN——只能靠 ip rule show | grep uidrange 核对 UID 是否注册。另外 UID 只在「启动代理」时注册，重装应用换了 UID 后必须重启代理，否则分流悄悄失效。

4. 电视端治理：广告包与开机守卫

4.1 反弹与自恢复链

首轮用 Binder 事务绕过厂商对 shell pm disable 的拦截，禁掉 8 个广告/统计包，60 秒后复查全部失效。反编译定位到自恢复链：com.skyworthdigital.skycommonpropertymanager 的 dex 里同时包含广告包名和 setApplicationEnabledSetting 调用，开机广播里把自己和同簇包一起拉起；DNS 拦控制名单下载有效，但本地 setApplicationEnabledSetting 不走网络，挡不住。

结论：只能「持续压」——设备端常驻守卫脚本每 120 秒重新压制。

4.2 只禁 receiver，不整包禁用

这里踩过两个大坑：

  1. 整包禁用 ott.advert.app → 全应用打不开。它负责「应用启动管线」（force-stop 目标 → 播启动广告 → 再拉起），包被禁后广告放不了、目标应用也永远拉不起来，所有应用弹「应用无法使用 / 该应用是由root所管理」。修正：包保持可用，只禁它的 ACTION_APP_OPEN 广播接收器。下图就是系统设置里这个包的应用信息页（小湃通，版本 2.17.24）：

  2. 压制 ottstatsv2 → 开机崩溃循环。它是 PERSISTENT + sharedUserId=android.uid.system，pm hide 后 Resources 为 null，2 分钟 NPE 崩溃 691 次。结论：保持启用。

  3. 不要对任何 Skyworth 系统包用 pm suspend。全部系统包共享 uid 1000，suspend 任一包会让 AppOps 报 Audio disabled for suspended package=...，AudioFlinger 把其它 uid 1000 应用（含桌面视频）一起静音——表现为全机无声且无任何报错。disable-user 单独用就够。

4.3 真正的开机钩子

让守卫开机自启走了不少弯路：/system 曾 100% 满（写 1KB 都 ENOSPC）、init 里厂商服务带 seclabel 会触发 SELinux bounded transition 拒绝 execve、App 的 BOOT_COMPLETED 被厂商杀。也一度把守卫写进 /data/xpclouddrive/run_clouddrive.sh——后来实测发现它根本不是开机钩子（init 的 start_clouddrive 是 disabled，无任何触发者）。

最终方案利用两个特性：

  1. 符号链接只占元数据不占数据块——写满的 /system 上也能创建；
  2. init 的 sky_check 服务：root、无 seclabel、sys.boot_completed=1 时启动。

boot.sh 后台运行原脚本 + 拉起广告守卫与广告拦截守卫，最后 wait 常驻（oneshot 服务结束时子进程可能被回收）。整机重启验证通过。

5. 前贴片广告：从「不可行」到运行时 hook

极光免费专区的前贴片广告 60–120 秒，无跳过按钮。这是全案里翻案最漂亮的一个问题：

先证明「网络层全部不可行」：

  • 广告决策与正片 API 同域（tv.t002.ottcn.com），素材与正片共用 CDN（ugc*.gtimg.com），域名/IP 无法区分广告与正片；
  • 黑洞实验：对 8 个广告域名全部 403，广告仍完整播放（本地预缓存 + 主域通道）；
  • App 内置 HTTPDNS3 且 native hook libc DNS，改 DNS 无效；
  • iptables 封 SNI、改配置 XML（scenePreRollDisabled）、改 shared_prefs 开关（实际被接管成 MMKV）全部无效；
  • 重打包更不行：sharedUserId=android.uid.system + 平台签名，重签丢系统特权。

然后抓调用链（Frida 挂广告 SDK 打印 Throwable）：

PlayerAdView.a() 拿到非空 ErrorCode 就走 fireFailedEvent() 直接开播正片——而且源码里还有「小窗 121」「悟空 120」两条同款早退分支，说明返回 ErrorCode 跳过广告是官方设计路径，不是硬改逻辑。

落地：hook com.tencent.ads.view.c.a()，adType == 1（前贴片）时返回 ErrorCode(143)。长期运行用 frida 官方 frida-inject 设备端自持注入（不需要 frida-server、不需要 PC），-e（eternalize）让脚本常驻；守卫脚本轮询 pidof com.ktcp.launcher，新 pid 自动重新注入，开机钩子拉起。

实测：起播 4–6 秒直接进剧情，无倒计时、无水印、无黑屏等待；暂停广告、中插、角标等其它广告位不受影响；整机重启、进程重启均自动恢复；进程 RSS 无可见增长。

一个验证陷阱：SDK 自带频次控制（看完一条广告后窗口期内后续视频不出广告）。连续试 2–3 个视频都没广告不能证明拦截生效——必须按「单次起播 4–6 秒内是否已在正片」或 hook 日志 [preroll] blocked #N 判断。本次排查早期就吃过这个亏。

6. 桌面与内存治理

腾讯极光桌面常驻约 195MB，是电视上最大的内存块。方案分两个阶段：

第一阶段：换开源轻量桌面 FLauncher（59.5MB，homewhitelist + HMAC 签名持久化），再做入口 App（壳应用跳极光桌面）+「退出即释放」守卫（logcat 事件触发 + dumpsys 复核 + force-stop），实测退出极光后 MemAvailable 273→397MB。这期间还顺带移除了预装的「小湃桌面」（内容推荐型桌面，RSS 296MB），删 APK 释放 16MB——更关键的收益是 /system 从 0 恢复到 24MB 可写，空闲块位图异常消失。

第二阶段（11-11 回摆）：前贴片拦截落地后，极光桌面的「内容入口」价值回升；内存实测（1GB 机型，三件套同跑）：

场景 MemAvailable 备注
FLauncher 为桌面（基线） 437 MB 极光未运行
极光后台 + SmartTube + TVPN 295 MB 极光 264 / SmartTube 241 / TVPN 57 MB
极光作默认 HOME（重启后） 393 MB FLauncher 不再运行

全程没有 LowMemoryKiller 主动杀进程——1GB 内存可以承受极光常驻。最终决定：极光改回默认 HOME 并常驻，入口 App 与释放守卫下线，日志全部加自动截断长期运行不占存储。

8. 车机端

同一套 APK 部署到 AC8317 车机（Android 6.0，armeabi-v7a），白名单 com.mmbox.xbrowser,org.smarttube.stable：

  • X 浏览器访问 Google 正常；SmartTube itag 136（720p AVC）+ itag 140（AAC）硬解正常；
  • 内置 4G ↔︎ WiFi 热点上游自动切换实测通过：切换日志 upstream changed ... rebinding，8 秒内 wlan0 RX 513KB、eth0 RX 0KB，确认全部走 WiFi；
  • 车机 adb root 开箱即用，调测自由度比机顶盒高（可直接 ip rule add 补注册 UID），但不改变客户端架构。

9. 结论与遗留

已经跑通的闭环：自研 240KB 客户端 + 按应用分流 + 节点接入 + 开机自启/保活/UID 重注册；广告包持久压制；前贴片运行时拦截；桌面/内存治理；SmartTube 与 IG 适配；车机部署与上游切换。

仍未覆盖：

  • 节点故障切换靠人工固定节点，未做自动降级；
  • 极光 App 升级若改广告 SDK 类名，hook 会静默失效（表现只是广告回来，不崩溃），需跟随版本维护；
  • ottstatsv2 判定不可压制，保持启用；
  • 厂商 OTA 可能重置 homewhitelist、覆盖 /system 下的开机钩子符号链接，升级后需复查。

10. 安全红线

  • 车机 adb root 开箱即用——任何能连上 adb 的人直接就是 uid 0，不用的关掉 USB 调试；
  • 机顶盒 WiFi ADB 无认证（ro.adb.secure=0），同一局域网内任何人可控制设备，只在可信网络开启；
  • usrchan 口令可由序列号推导，等同厂商后门，不要把设备放到不可信网络；
  • 订阅地址、节点域名即等同凭据，一律不写入文档与仓库。
