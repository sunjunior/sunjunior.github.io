目标软件：MAME 0.149（2013 年发布的模拟器版本）
目标平台：Arch Linux / x86_64，GCC 16.2.1，系统 SDL2 2.32.72
交付物：可运行的 mame64、mame.ini、源码补丁清单；恐龙快打等街机可正常游玩
日期：2026-09-14

1. 背景与目标

1.1 为什么要编译一个 13 年前的 MAME

街机模拟器 MAME（Multiple Arcade Machine Emulator） 版本众多。手头有一套 MAME 0.149 时代的 ROM 包（共 28,510 个 zip，打包备份约 45.8GB）。这里有一个容易被忽略的版本配套问题：

MAME 的 ROM 校验与加载机制是版本绑定的。新版 MAME 对 ROM 的字节序、合并方式（parent/clone、CHD 分离、qsound 存放位置等）做了大量调整，直接拿 0.149 的 ROM 包去跑新版 MAME，会大量报错甚至拒绝加载。反过来，0.149 官方二进制在国内网络环境下也不易获取、且未必能在新版系统依赖上直接跑起来。

因此最稳妥的方案是：拿到 MAME 0.149 的源码，在本地系统上从零编译一份，与手中的 ROM 包配对使用。这既解决”版本配套”问题，也是一次很好的源码级编译调试训练。

1.2 目标

  1. 在 Arch Linux 上从源码编译出可用的 mame64。
  2. 能正常启动并游玩 恐龙快打（Cadillacs & Dinosaurs，驱动名 dino，1993 Capcom，CPS1.5 基板）。
  3. 顺带验证 CPS1 / CPS2 / NeoGeo / IREM / Toaplan / Psikyo 等多基板机种。
  4. 输出可复现的构建步骤、遇到的所有问题与解决思路、以及最终交付件。

2. 软硬件环境（依赖软件）

2.1 硬件环境

项目 说明
主机 x86_64 桌面 PC，有 X11 显示器（1920x1080）
外设 普通键鼠；无手柄（摇杆路径顺带适配了 SDL2，见 4.3）

注意：当前登录用户没有免密 sudo，后台长任务无法用 sudo systemd-run 起服务。本机恰好有用户级 systemd，于是所有耗时编译都用 systemd-run --user --unit=xxx 放入用户级服务单元后台执行，用 systemctl --user show 轮询状态，规避了权限问题。这是本文大量使用的一个技巧。

2.2 软件环境（编译执行时实测版本）

软件 版本 备注

3. 整体编译流程

3.1 明确构建参数

MAME 0.149 的 makefile 通过变量控制构建内容，本轮使用的关键参数：

参数含义：

参数 作用
TARGET=mame 构建标准街机模拟器
SDL_LIBVER=sdl2 链接系统的 SDL2（而不是依赖自带的旧 SDL1）
NOWERROR=1 大量老代码在新 GCC 下会产生新告警，关闭 -Werror 避免当错误
NO_DEBUGGER=1 不带内置调试器（自用不需要）
NO_USE_QTDEBUG=1 不依赖 Qt（避免引入额外依赖）
OPTIMIZE=2 优化级别 O2（这一项在后续调测中极为关键，见 4.5）

零散补充：-j8 是 8 核并行；SYMBOLS=1 与 OPTIMIZE 组合改变 strip 与优化级别，调试专用，最后交付用不带 SYMBOLS 的配置。

3.2 构建前的源码预处理（针对新版工具链）

0.149 源码是在 2013 年、用当时工具链写的，放在 2026 年的 Arch 上会有一批”历史遗留”不兼容。本轮共打了 3 处编译期补丁 + 1 处构建期顺手修复（详见第 4 章）：Python 生成器移植、simple_set.h 类型笔误、input.c 摇杆 API、m68kmake.c 的 memcpy 重叠。另外有 17 个 .inc 文件需要由生成器产出（mcs96 系 3 个、m6502 系 10 个、m6809 系 3 个、tms57002 1 个）。由于这些生成器当初是 python2 写的，我们直接按 makefile 里 cpu.mak 的配方用移植后的 py3 脚本手工预生成到 obj/sdl64/emu/cpu/...。

3.3 首次构建通过进度的现象

完整的干净构建会编译约 3,300 个目标文件，链接产物约 107 MB。全程用用户级 systemd 后台跑，日志落盘便于失败排查：

3.4 生成配置文件

一个坑：MAME 默认优先加载 $HOME/.mame/mame.ini（此前装过新版 MAME，留下的旧配置指向已搬走的 rom 目录）。为了新旧两个 MAME 的配置互不干扰，0.149 统一用 -inipath ~/mame 强制加载我们自己的 mame.ini。后续所有命令都带该参数。

3.5 冒烟验证

dino 报 qsound.bin ROM NEEDS REDUMP 属正常：0.149 驱动里把 qsound.bin 标成”已知坏 dump，需要重抓”，缺失只警告、不阻断运行（后文在 4.6 会解释它为什么没有继续把游戏搞崩）。

4. 编译与调测过程中遇到的问题及解决思路

这一章是全文核心。问题可以分成两类：编译期不兼容（4.14.4）和运行期段错误（4.54.6）。运行期问题占了绝大多数精力，也最有价值。

4.1 Python2 生成器在 Python3 上无法运行

现象：构建到 CPU 模块时报错，生成 .inc 的脚本（mcs96make.py / m6502make.py / m6809make.py / tmsmake.py）是 2013 年的 python2 代码，而系统只有 Python 3.14。

解决思路：逐文件移植为 python3 语法（print 函数化、iteritems→items、编码处理等），并逐个验证能生成与预期一致的 .inc。其中 m6809make.py 移植后仍有 \: 的 SyntaxWarning，无害，忽略。之后按 makefile 里 cpu.mak 的原始 recipe 显式运行生成器，一次性预生成全部 17 个 .inc。

4.2 simple_set.h 类型笔误导致编译失败（上游自己就写错了）

现象：编译 src/lib/util/simple_set.h 报”指针类型不匹配”类错误。

4.5 主战役：任何游戏启动即段错误（启动期堆损坏）

这是耗时最长、最有含金量的一段。先说结论，再讲推理链。

症状：编译成功的 mame64，CLI（-showusage、-listfull、-verifyroms）全部正常；但只要真正启动一个游戏（如 dino），几乎必然 SIGSEGV（退出码 139），且崩溃点每次不同：

  • 有时崩在 sdlvideo_init() 里遍历显示器链表（比较 "auto" 与 monitor_device 的 strcmp）；
  • 有时崩在 sdlinput_init() 遍历键盘设备链表；
  • 有时崩在 window 创建路径。

同一份代码，崩的地方漂移——这正是 heap 已被写坏的典型特征（不是某一行逻辑错误，而是内存被提前污染，随后在任意一处读取脏指针才炸）。

排查过程（推理链）：

  1. 用带符号的二进制反编译。交付用的二进制被 -s strip 了，先 touch drivlist.o && make SYMBOLS=1 只重链不去符号（不影响 .o 的优化级别，几十秒就好），再用 gdb 反汇编、断点、看寄存器。
  2. 打点缩小范围。在 sdlvideo_init 的 init_monitors() 之后、sdlwindow_init() 之后各加一行临时 fprintf，打印显示器单链表 sdl_monitor_list 的头节点指针和 ->next。结果发现：global_alloc_clear(sdl_monitor_info) 分配的节点，->next 字段直接就是垃圾值（一个悬空指针），而该字段本应被清零。
  3. 对照实验给出方向。-O0（ASan 构建恰好会因为 SYMBOLS=1 退到默认 OPTIMIZE=0）构建不崩，-O2/-O3 必崩。这就把问题锁定在”优化级别相关”——高度怀疑是编译器优化引入的问题而非纯逻辑 bug。
  4. 反汇编实锤。对 -O2 未剥离二进制反汇编 sdlvideo_init，盯着 global_alloc_clear 内联后的指令看：

monitor 结构体的 next 字段从没被写过零——也就是说，global_alloc_clear 里那个 memset 被 GCC 16 在 -O2 下整段”死代码消除”了。

  1. 为什么能合法消除：global_alloc_clear(T) 展开成 pool.add_object(new(__FILE__,__LINE__,zeromem) T)。编译器内联后认为：这个块是由 malloc 刚搞出来的，而紧随其后的代码（snprintf 等）把所有”会被读到”的字段都写了；next 这类暂时只写不读的字段，其初始值”永远不会被观察到”，于是 memset 就成了可删除的死代码。编译器甚至不关心”下次遍历链表时 next 会被读出来当指针用”——在它眼里那属于”读取未初始化内存”的 UB，怎么处理都不违约。-O0 不做这类优化，所以老代码在旧工具链上活得好好的，在新 GCC 上集体翻车。

  2. 修复：让清零变得不可优化。把 operator new(..., zeromem) 里的 memset 换成用 volatile 指针逐字节写零：

两个 zeromem operator new（普通 + 数组）都改用它。改动集中在 src/emu/emualloc.h，影响所有翻译单元，需要一次全量重编（约 35~45 分钟）。

修复效果：监视器链表、键盘链表等节点的字段终于正确清零，启动崩溃消失；随后崩溃点后移到真正的历史 bug 上（4.6）。

4.6 掩盖清零问题后的”历史遗留炸雷”（判空顺序 bug）

清零问题修复（-O2）后，dino 能一路跑到 ROM 加载与第一帧渲染，然后又开始崩。逐个 gdb 回栈，发现全是同一类代码模式：memregion("<tag>")->base() 先解引用、后判空。当某个驱动确实没有这个 region 时，memregion() 返回 NULL，再 ->base() 必然段错误。

5.4 遗留提示

  1. 恐龙快打启动时 qsound.bin ROM NEEDS REDUMP 的警告是 0.149 驱动本身把该 ROM 标记为”已知坏 dump”所致，不影响游玩。
  2. MAME 0.149 没有 -skip_gameinfo 等较新参数；配合本 ROM 包使用，勿改用新版 MAME。
  3. 若日后要换回 -O3 或换工具链版本，建议先重跑一次本轮的回归矩阵（4.7），防止新的编译器行为再次”合法销毁”初始化。

6. 小结

这次”编译老 MAME”最有价值的收获不是”能跑恐龙快打”这个结果，而是完整的调测闭环：

症状（崩溃点漂移的启动段错误）→ 打点缩小范围 → 对照实验（-O0 不崩 / -O2 必崩）→ 反汇编实锤（GCC16 死代码消除 memset）→ 根治（volatile 清零）→ 暴露并修复两个历史判空 bug → 全矩阵回归。

一句话总结：博览时代的老 C++ 代码最大的敌人不是旧依赖，而是”现代编译器是否更严格地践行了标准允许的未定义行为”。 -O0 侥幸能跑，恰恰证明了问题真实存在，只是旧工具链替你装修好了裂缝。
