目标：基于上游 v0.14 的个人分支，完成三件事——①界面中文汉化收尾；②从零实现文件编码功能（ANSI/UTF-8/UTF-8 BOM/UTF-16 LE/BE、转换与按编码重新打开）；③打出 Release 包并发布 AppImage

1. 背景

NotepadNext（上游 dail8859/NotepadNext v0.14）是 Qt 重写的 Notepad++ 风格编辑器，但在中文使用场景下有两个明显缺口：

  1. 本地化不完整：偏好设置对话框、视图/搜索菜单里大量英文残留（Show menu bar、Fold All、Mark All Occurrences……），连保存确认框的按钮都是英文；
  2. 编码功能缺失：Encoding 菜单里只有一个占位项 This is not currently implemented（作者原话）。实测：UTF-8（含 BOM）正常；UTF-16 文件打开是乱码、保存直接损坏文件；GBK/ANSI 完全不识别。

本文按”汉化 → 编码功能 → AppImage 打包 → 发布”四步记录整个落地过程。最终成品主界面：

2. 第一部分：中文汉化收尾

2.1 偏好设置对话框（23 条）

系统语言 zh_CN 加载的是 NotepadNext_zh_CN.qm。该文件 PreferencesDialog 上下文有 23 条 unfinished，直接在 .ts 里补齐，同时同步到 NotepadNext_zh.ts（两者此前缺失项完全一致）：

英文 中文
Show menu bar / toolbar / status bar 显示菜单栏/工具栏/状态栏
Restore previous session / Temporary files 恢复上次会话 / 临时文件
Translation: 语言：
Exit on last tab closed 关闭最后一个标签页时退出
Default Font / Font Size 默认字体 / 字号
Default Line Endings 默认行尾格式
Follow Current Document / Last Used Directory 跟随当前文档 / 上次使用的目录
An application restart is required… 应用某些设置需要重启程序。

其中 Windows (CR LF)、Linux (LF)、Macintosh (CR) 按已有风格保留英文原文，仅去掉 unfinished 标记。.ts 改完后构建时 qt_add_translations 自动跑 lrelease 生成 .qm 打进 :/i18n 资源，无需手工操作（.qm 内字符串是 UTF-16BE 存储，直接 grep UTF-8 会误判为缺失，要用 bytes.decode('utf-16-be') in open(qm,'rb').read() 验证）。

2.2 视图/搜索菜单（术语参照 Notepad++）

从 MainWindow.ui 提取视图/搜索两菜单全部 action，逐个查 .ts 翻译状态，未翻译的集中补上。术语以 Notepad++ 官方 chineseSimplified.xml 为准：

  • Fold All → 折叠所有层级（NPP：折叠所有层次；本仓库已有”折叠层级”译法，统一用”层级”）
  • Unfold All → 展开所有层级，Fold/Unfold Level N → 折叠/展开层级 N（1–9）
  • Cut/Copy/Delete Bookmarked Lines → 剪切/复制/删除书签行
  • Mark All Occurrences → 用格式标记全部，Mark Style N → 使用格式 N，Clear Marks → 清除格式标记
  • 缩放指示器 Zoom: %1% → 缩放：%1%

2.3 保存确认框按钮：加载系统 Qt 翻译

文件保存/另存为对话框里”保存/取消/打开”是 Qt 标准对话框的按钮，NotepadNext 自己的 .qm 管不到。解决：TranslationManager 在加载应用翻译后，回退加载系统 Qt 翻译目录（QLibraryInfo::translationsPath）的 qtbase_zh_CN.qm，按钮随之汉化（commit 90211dbe）。

2.4 界面细节

  • 查找对话框 Search Mode/Transparency 组标题贴首选项：QGroupBox 的 topMargin 给小了（16→26、10→18），逐像素复测标题→首项与项间距均一致 17px；
  • 给查找/偏好对话框补浅色主题 QSS：复选框真实对勾、单选框实心圆点（QPainter 运行时生成 glyph）；
  • 帮助菜单移除 Debug Info...。

2.5 脚本化全局菜单审计：把汉化残留清零

零敲碎打地”发现一条补一条”永远补不完，索性写个审计脚本：解析 MainWindow.ui 全部 241 条 <string> 源文本，逐条对照 zh_CN.ts 的 MainWindow 上下文（缺失/空译文/type="unfinished" 三种形态都算未汉化），排除快捷键后一次性列出清单：

  • 编辑 → 行操作：Remove Duplicate Lines（移除重复行）、Remove Consecutive Duplicate Lines（移除连续重复行）、Reverse Line Order（反转行顺序）、六种 Sort Lines …（行升序/降序排序、忽略大小写、按行长）——这些在 ts 里原本就是空译文占位；
  • Next Tab/Previous Tab（下一个/上一个标签页）、Toggle Overtype（切换改写模式）、Open %1 Here（在此打开 %1，终端项）；
  • 文件被外部修改的重载确认提示（含 <b> 富文本）与全部 15 条文件 IO 错误标题（读取/写入/重命名/权限错误…）——这类错误框平时不弹，弹的时候全英文最扎眼；
  • 工作区”按文件名排序”、搜索结果面板”将结果复制到剪贴板”。

批量回填两个 .ts 后复跑审计，剩余未译项只有两类：快捷键串（Ctrl+N 等，本就不该译）和快捷查找面板的符号按钮（Aa、|A|、. *）。两个小坑：译文里的 <b> 标签必须转义成 &lt;b&gt;，否则 lrelease 直接报错中断构建；往 .ts 插新条目时要顺手删掉同源的旧空条目，不然会出现”一份空译文 + 一份译文”的重复 <message>。

2.6 「列选模式」提示项与矩形选择的真相

编辑菜单”列编辑模式…“上方新增「列选模式」只读提示项（QMessageBox::about 风格），弹窗标题”列模式提示”，正文写明两种操作方法：

  1. （键盘和鼠标）按住 Alt 键，同时鼠标左键拖动；
  2. （只需键盘）按住 Alt+Shift 键，并使用方向键。

功能实现上反而没写多少代码——查证过程很有意思：先给 ScintillaNext 写了 keyPressEvent 拦截 Alt+Shift+方向键去调 RECTEXTEND 命令，随后翻 Scintilla 源码发现跨平台默认键表 KeyMap.cxx 的 MapDefault 里本来就绑了全方向（上下左右 + Home/End/PageUp/PageDown），鼠标法也是 Qt 端口自带（rectangularSelectionModifier = SCMOD_ALT，且工程开启了 SCVS_RECTANGULARSELECTION）——我写的是纯冗余代码，回滚后整个功能收敛到 +50 行（菜单项+提示框+翻译）。实测 Alt+Shift+↓×3 一次插入四个行，键盘列选完全可用。

Alt+拖拽的一个环境坑：xdotool 模拟 Alt+左键拖拽时，整个窗口跟着鼠标跑了——被 Xfce 的 xfwm4”按住 Alt 拖动移动窗口”全局劫持，事件根本到不了编辑器。这是桌面设置问题不是应用问题（Notepad++ 装在同一桌面同样中招）；释放方法：设置 → 窗口管理器 → 高级 → “移动窗口快捷键”改为”无”。顺带还踩到”编辑器不会自动重载被外部脚本改写的文件”导致两轮测试对着旧缓冲白测——自动化测试前务必重启应用。

3. 第二部分：文件编码功能增强（本次核心）

3.1 上游现状盘点

功能 上游状态 证据
UTF-8（含 BOM）读写 ✅ 正常 加载剥 BOM、保存回写
UTF-16 LE/BE 读取 ❌ 乱码 ScintillaNext.cpp 检测到 UTF-16 BOM 后注释 // Um...ignore this for now?，原始 UTF-16 字节直接塞进 UTF-8 缓冲
UTF-16 保存 ❌ 损坏文件 保存写”UTF-16 BOM + UTF-8 正文”
ANSI（GBK） ❌ 不存在 全工程无一处 codec 转换
转换菜单 ❌ 空壳 只有一个禁用的占位 action

好消息是工程链接了 Qt6Core5Compat，QTextCodec 开箱即用，无需新增依赖。

3.2 设计要点

  1. 文档内部缓冲不动：Scintilla 缓冲维持 UTF-8，转码只发生在加载/保存两端；
  2. 打开自动识别，判定顺序：UTF-16 BOM → UTF-8 BOM → 严格 UTF-8 校验（QTextCodec::ConverterState.invalidChars == 0）→ GB18030 兜底。这样”文档打开以默认识别的编码为准”，常见乱码场景（GBK 文件、UTF-16 文件）在打开这一步就被消灭；
  3. “ANSI” 映射为 GB18030（GBK 超集）：Linux 上没有 Windows 系统代码页，用 codecForLocale() 的话 zh_CN.UTF-8 下 ANSI≡UTF-8 形同虚设，直接定 GB18030 最实用；
  4. 菜单两组、职责严格分离（对齐 Notepad++）：“转为 X” 只更换保存编码，内存文本不动、标脏——刻意不让它重新解码，否则最常见的”GBK 文档转为 UTF-8”会变成双重转码事故（先错解再保存，内容全毁）；“X 编码”（最前 5 项）负责重解读：文档未编辑时直接拿盘上原始字节用新编码重新解码，且解读后仍是干净状态（选错一键切回、Ctrl+S 空操作、关标签不弹保存），有未保存修改时则把当前文本按原编码还原成字节视图再重解读。救援乱码、验证”这文件到底是什么编码”全靠这一组；
  5. 标脏机制：转换后 Scintilla 的 modify() 可能仍为 false（文本没变），加了 encodingDirty 标志并入 canSaveToDisk()，保证标题出现未保存星号、关标签页会提醒。

3.4 验证

  • 单元测试：把静态助手原样抽出编成独立可执行文件，22 项断言全过——五种编码逐一”编码→检测→解码”往返一致、纯 ASCII 字节不变、GB18030 四字节 ✓、emoji 代理对、空文件判 UTF-8；
  • GUI 端到端（转换组）：xdotool 操作真实界面，把同一个文件 UTF-8 BOM → ANSI → UTF-16LE 连转两次、每步 Ctrl+S 后 hexdump 落盘字节：GB18030 的 b2 e2 ca d4（测试）、81 37 bd 37（✓）、UTF-16LE 的 6d 4b d5 8b 全部正确；

3.5 自动化测试踩坑三则

  1. 悬浮窗劫持点击：桌面上一个”OC 提醒”小窗恰好压在菜单栏上，xdotool click 全部石沉大海。xdotool getmouselocation 输出坐标下的真实窗口 ID 一查便知，windowlower 后恢复；
  2. pkill -f NotepadNext 会杀掉执行它的 shell 自己——命令行本身匹配 pattern。用 pkill -x 精确进程名，或 Notepa[d] 写法；
  3. QT_LOGGING_RULES='*.debug=true' 直接让 NotepadNext 启动即 std::bad_alloc 崩溃（Qt 全量 debug 日志打爆），排查”应用崩溃”前先怀疑自己的环境变量。

4. 第三部分：AppImage 打包：三个坑

仓库自带 appimage target（自动下载 linuxdeploy），但在本机 Arch 上连踩三坑：

坑 1：Qt 插件误用 Qt5 的 qmake。linuxdeploy-plugin-qt 默认找到 /usr/bin/qmake-qt5，报 Could not find Qt modules to deploy。解决：

坑 2：自带 strip 太老。Arch 新工具链接出的库含 .relr.dyn 节，linuxdeploy 内置 strip 不认识，大量 Strip call failed 后以 Failed to execute deferred operations 失败。解决：把两个 AppImage 用 --appimage-extract 解包，用系统 binutils 2.47 的 strip 替换 squashfs-root*/usr/bin/strip，再手动跑解包后的 AppRun（参数照抄 cmake/PackagingLinux.cmake 里 appimage target 的那一行，另需给插件写个 PATH 垫片）。

坑 3：单实例旧锁导致”静默退出”。凡是”一点反应没有、退出码 0”，先查 /dev/shm。之前 kill 掉的进程留下 NQd7ehOB… 锁文件，新实例误判自己是第二个实例直接 exit(0)，控制台没有任何输出，看起来就是”打不开”。删掉锁文件再启动即正常：

7. 小结

NotepadNext 的编码缺失本质是”只写了 BOM 检测，没写转码层”。补齐这层之后：UTF-16 文件从”打开乱码、保存损坏”变成开箱即用；GBK/ANSI 文件自动识别；Encoding 菜单从占位符变成”重解读 + 转换”两组十个真正可用的项，Notepad++ 里”以 X 编码打开救乱码、转为 X 换保存编码”的完整工作流在 Linux 上也成立了。汉化侧则用脚本审计把行操作、错误提示等最后的残留清零，并补上「列选模式」提示项——查证过程还顺带确认了矩形列选本就是 Scintilla 原生能力。这套个人分支现在对中文用户基本没有硬伤了。下一步可考虑：支持 Big5/Shift-JIS 等更多传统编码、状态栏编码标签点击直接弹出编码菜单。
