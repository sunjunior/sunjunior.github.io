西游释厄传（PGM / ARC）无限放宝 Hack 技术文档

目标游戏：西游释厄传（Oriental Legend / Xiyou Shi E Zhuan, PGM, 1997 IGS）
目标：使所有角色的法宝（宝）数量无限（无限放宝 / Infinite Items）
交付物：MAME 插件（每 5 tick 写回 0x81118b = 3，已确认有效）
日期：2026-09-08

1. 背景与目标

《西游释厄传》是 IGS 于 1997 年推出的 PGM 街机横版清关动作游戏。每位角色默认携带 3 个法宝（如孙悟空的天罡火、龙马的突木桩、小龙女的无影刀），每次放宝消耗 1 个，3 个用完即无法再放。

本次任务的破解目标：

  1. 找到控制”能否放宝”的 RAM 地址（逻辑计数器）。
  2. 定位修改该计数的代码位置。
  3. 修改 ROM，使宝数量永不减少（无限放宝）。
  4. 提供可用的交付物。

最终成果：插件版无限放宝已生效，玩家放宝后宝数量永远保持 3 个。

2. ROM 与游戏信息

项目 值
ROM 集 orlegend.zip（World, ver. 126）
父集 pgm.zip（PGM 系统 BIOS）
主板 PGM（Poly Game Master, pgm_asic3）
主 CPU Motorola MC68000（maincpu，16MHz）
程序 ROM p0103.rom（2MB, CRC d5e93543）
程序加载位置 maincpu 地址空间 0x100000（ROM_LOAD16_WORD_SWAP）
主 RAM 0x800000-0x81ffff（128KB）
保护 ASIC3（0xc04000 I/O 设备，pgmprot_orlegend.cpp），代码本身未加密

关键地址约定

  • CPU 地址：MAME 调试器 / Lua 看到的主 CPU 地址（如 0x10224A）。
  • 文件偏移：p0103.rom 内字节位置。由于 ROM_LOAD16_WORD_SWAP，文件内每个 16 位字的字节序与 CPU 视图相反：CPU 看到的 23 6F，在文件里是 6F 23。反汇编与打补丁都必须按字交换后的字节处理。

3. 分析环境与工具

用途 工具
模拟器 MAME 0.289（Arch Linux 官方包，-bios v2）
内存读取 MAME Lua API：space:read_range(first, last, width)、read_u8()
调试器 MAME 内置调试器（-debug）+ Lua machine.debugger:command()
反汇编 Python + capstone（68000）
插件机制 自定义 MAME 插件（plugin.json + init.lua，加载于 -pluginspath）
转储/差分 Python 全量 RAM 转储 + 快照对比

注：本项目的核心难点在于 MAME 的 frame notifier 在 PGM BIOS 进入游戏时失效，以及 read_range/write_range 的 width 参数单位是位而非字节。这两点占据了大量调试时间，详见 §7。

4. 破解总体思路

核心思想：先用内存差分定位计数器，再用监视点把”谁在写”抓出来。这比纯静态扫描精准得多——68000 程序通过基址寄存器+偏移访问 RAM，直接搜 0x8082c2 绝对地址是搜不到的。

5. 详细分析过程

5.1 定位宝计数地址（差分 + 平台期检测）

玩家手动进入关卡，先把宝攒满到 3，然后停手不攻击，依次放宝（3→2→1→0），每步停顿 ≥2 秒。同时 Lua 插件每隔 5 帧转储 128KB 主 RAM。

分析全部转储，找出满足”完整 3→2→1→0 链 + 每段平台期 ≥3 帧”的字节：

0x082c2（绝对 0x8082c2）有多段干净、长平台期的 3→2→1→0，初判为宝计数。

教训：这是”显示用”计数器（HUD 图标），不是”逻辑”计数器。 后面用它做写入测试（每 tick 写回 3），宝确实能在 HUD 上保持 3 个，但游戏仍然只能放 3 次——因为判定能否放宝读的是另一份副本。

5.2 用写监视点抓”写宝计数”的 PC

5.3 尝试 ROM 补丁（失败并复盘）

把 0x10224A 的 move.l $18(a7), $e(a1)（6 字节）改成 move.w #$0300, $e(a1)（恒写 3，长度正好 6 字节）：

结果：进关卡后黑屏，能听到受击音效、主角会死并出 continue 界面，但画面不渲染。

根因： 这条 move.l 是 4 字节写入，除了宝计数（$e(a1)）还写相邻字段（$f/$10/$11，即 0x8082c3-05），其中包含角色渲染所需的状态。强制写 3 把结构体破坏了，游戏画面无法正常渲染。

教训：不能只改”落地写入”这条指令，必须定位”递减计算”本身，或找到仅属于宝计数的独立字段。

5.4 定位真正的逻辑计数器（快照差分）

由于 0x8082c2 只是显示副本，用受控快照差分重新定位真正的逻辑计数器：

  1. 进入关卡（宝 = 3）→ 取快照 A；
  2. 放宝一次（3→2）→ 取快照 B；

逐一剥离测试 4 个候选地址，最终确认唯一逻辑计数器为 0x81118b：

测试地址 效果
仅 0x80c627 = 3 仍只能放 3 次
仅 0x81cb4e = 3 仍只能放 3 次

5.6 定位递减指令（subq 代码）

通过监视点（watchpoint）抓取对 0x81118b 的写入 PC，发现递减由 subq.b #1, $1(a3) 指令执行，共 5 处：

地址 指令 值
0x13D9D4 subq.b #1, $1(a3) 2（递减）
0x13D9E2 subq.b #1, $1(a3) 2
0x13D9F0 subq.b #1, $1(a3) 2
0x13D9FC subq.b #1, $1(a3) 2
0x13DA08 subq.b #1, $1(a3) 2

这些指令位于一个跳转表/状态机函数中（0x13D920 区域），对应角色技能系统的不同槽位。$1(a3) 中的 A3 指向角色结构体，偏移 1 即为 0x81118b（当 A3 = 0x81118a 时）。

5.7 ROM 补丁尝试（受阻）

修改 subq → tst（不递减但保留标志位）后 patch 到 ROM 文件，尝试三种方式：

方式 结果
全部 22 处 subq → NOP 破坏启动流程 → MAIN MENU
仅 5 处 subq → tst 仍进 MAIN MENU
仅改 ROM 最末 1 个无关字节 也进 MAIN MENU

结论：游戏/BIOS 对 ROM 内容有完整性校验，任何字节修改都会触发，跳转维修测试菜单。 运行时 write_u8 写入 ROM 地址被静默忽略（ROM 只读），因此 ROM 固化补丁方案受阻。插件方案为最终可行方案。

7. 踩坑与经验总结

  1. read_range / write_range 的 width 参数单位是”位”（8/16/32/64），不是字节！ 传 1 会报 Invalid width. Must be 8/16/32/64。读单个字节要么用 read_u8(addr)，要么 read_range(a, a, 8)。这是排查”插件没生效”时耗时最久的坑。

  2. PGM BIOS 进入游戏后，MAME 的 frame notifier 会失效。 通过 -autoboot_script 或插件注册的 emu.add_machine_frame_notifier 在 BIOS 引导阶段正常计数，但进游戏后（机器发生重建/重置）回调被”孤儿化”，心跳停在 ~120-360 帧，而画面仍在渲染。改用 emu.register_periodic（OSD 级，不受机器帧限制）即可稳定工作。

  3. “显示计数器” ≠ “逻辑计数器”。 0x8082c2 是 HUD 图标对应的显示副本，写回 3 只会让图标保持 3，判定放宝读的是另一份副本。定位必须用”放宝前后快照差分”而非”看起来像 3→2→1→0 的地址”。

  4. 68000 程序多用基址寄存器 + 偏移访问 RAM，直接搜绝对地址搜不到。 监视点（watchpoint）+ 抓 PC 才是正解；而抓到的 PC 往往落在”通用 store 函数”上，真正的递减在调用方，需继续向上找调用点（BSR/JSR 搜索、栈上返回地址回溯）。

  5. MAME 调试器命令 / Lua 字符串转义坑： machine.debugger:command() 传含 printf "..." 的 action 时，Lua 里的 \" 会被调试器解析为 unbalanced quotes。用 Lua 长括号 [[ ... ]] 包裹命令字符串即可避免。

  6. manager.machine.paused 检查要谨慎。 游戏在信息/警告屏时会暂停，periodic 回调里若先 if m.paused then return 会漏掉关键时刻；应先判断机器是否真正在跑。

  7. 插件路径： -pluginspath 会整体替换默认插件目录。若还需要系统插件（如 data），要用 ; 连接两个路径；-noplugin data 在 data 不在扫描列表时会报 Unknown plugin: data。

  8. /tmp 会被系统定时清理！ 工作区、转储、插件放在临时目录会在系统 tmpfiles 清理时全部消失（曾导致”dumps 神秘消失”的假象）。务必把工作区放到持久目录（如用户目录下）。

  9. ROM 区是只读的，Lua 写入被静默忽略。 尝试运行时 patch p0103.rom 所在地址（0x13D9D4 等）改 subq→tst，写入后读回仍是原值 0x53，write_u8 无报错但无效。MAME 中 ROM 内存不可写，必须改 ROM 文件本身。

  10. -skip_gameinfo 会破坏 PGM 启动流程。 加上该参数后，游戏跳过信息屏直接进”已知问题”确认屏，按任意键后误入维修测试菜单（MAIN MENU），无法进入投币界面。去掉 -skip_gameinfo 恢复两次确认屏后正常。PGM 机板必须保留完整启动序列。

8. 最终结论与后续方向

8.1 最终结论

项目 状态 说明
显示计数器 0x8082c2 ✅ 已定位 HUD 图标副本
逻辑计数器 0x81118b ✅ 已定位 判定放宝的唯一地址（插件写 3 即无限宝）
写计数器的 store 指令 0x10224A ✅ 已定位 move.l $18(a7), $e(a1)
递减指令 ✅ 已定位 subq.b #1, $1(a3) 共 5 处（0x13D9D4、0x13D9E2、0x13D9F0、0x13D9FC、0x13DA08）
插件版无限放宝 ✅ 已生效 最终交付方案
ROM 文件补丁固化 ❌ 受阻 任何字节修改都触发启动自检 → MAIN MENU

8.2 ROM 补丁为何受阻

尝试过多种 ROM 修改方式，全部导致进 MAIN MENU：

  • NOP 全部 22 处 subq.b #1, $1(a3)（破坏启动流程）
  • 只改监视点确认的 5 处 subq → tst（保留标志位）
  • 只改 ROM 最末 1 个无关字节（0x00→0x01）

结论：游戏/BIOS 存在对 ROM 内容的完整性校验，任何字节修改都会触发，跳转维修测试菜单。校验的具体实现（可能是 PGM 主板上 ASIC3 保护芯片对 ROM 的映射/加密，或启动时的 checksum）尚未定位。PGM 的 ASIC3 保护（pgmprot_orlegend.cpp）负责提供 region 标识与加密握手，修改 ROM 可能导致校验失败。

8.3 后续方向

  1. 定位 ROM 完整性校验：结合 MAME 源码 pgm.cpp / pgmprot_orlegend.cpp 与调试器断点，找到校验点并 NOP 掉，即可实现 ROM 固化。
  2. 扩展到其他角色：验证龙马、小龙女等其他角色的放宝逻辑是否共用 0x81118b（同 22 处 subq 结构，很可能共用）。
  3. 发布 IPS 补丁：若 ROM 固化成功，输出标准 IPS 补丁供分享。
