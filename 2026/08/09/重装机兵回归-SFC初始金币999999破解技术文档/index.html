重装机兵：回归（SFC/SNES）初始金币 999999 破解技术文档

逆向工程 2026/08/09

目标游戏：重装机兵：回归（Metal Max Return，SFC/SNES，1995 Data East）
日期：2026-08-09
破解目标：新游戏初始金币从 0 改为 999999，并且与存档/读档保持数值一致（存档后读档金币不变）

1. 背景

《重装机兵：回归》是 FC《重装机兵》在 SFC 上的完全重制版。游戏采用开放式地图 + 赏金猎人的玩法，金钱是核心资源：买车、买装备、补弹药、改武器都需要花钱。前期最大的痛点是起步金币为 0，连修理费都付不起，需要靠打小怪和捡箱子一点点攒。

本次破解的目标：让新游戏开局直接拥有 999999 金币（32 位上限以内），同时不破坏存档/读档机制——即玩家存盘时的金币是多少，读档后就是多少。

2. 分析环境

用途 工具
模拟器 Mesen2（支持命令行加载 ROM + Lua 脚本）
内存监控 addMemoryCallback 写回调 + emu.getState（取 PC）
内存搜索 Mesen2 内存搜索（Write 搜索）
反汇编 自写 65816 反汇编脚本（Python，按 LoROM 映射换算文件偏移）

Mesen2 的 Lua 脚本在本项目中不仅是”验证工具”，更是定位工具——靠写回调把所有金币写入点（含 PC）一网打尽，避免了纯静态分析的盲目性。

3. ROM 结构

原版 ROM 信息：

  • 文件：Metal Max Return.SMC
  • 大小：4194816 字节 = 0x200（无磁碟机头）+ 0x400000（4MB）
  • 型号：LoROM 4MB（CPU 高速库 $80-$BF 与慢速库 $00-$3F 镜像同一批 ROM 库，$C0-$FD 与 $40-$7D 镜像另一批）
  • 存档：SRAM 2KB（CPU 库 $70，映射为 snesSaveRam）

CPU 总线地址与 ROM 文件偏移的换算关系：

这个公式是本项目最容易踩的坑：CPU 库 $96 属于高速库组（$80-$BF），镜像到文件第 $16 个 8KB 库（偏移 0xB0000 附近），而不是文件偏移 0x96*0x8000。详见”遇到的问题”第 3 条。

金币数据位于 WRAM $7E9102-$7E9105，32 位小端存储：

地址 含义
$7E9102 金币低 8 位
$7E9103 金币次低 8 位
$7E9104 金币次高 8 位
$7E9105 金币高 8 位

999999 = 0x000F423F，即低字 0x423F、高字 0x000F。

4. 金币地址的定位

4.1 内存搜索

金币是典型的”可精确验证的数值变量”，先用内存搜索：

  1. 打开 Mesen2 内存搜索，初始全量快照；
  2. 游戏内捡一个箱子里的道具（金币 +7），对变化的值做过滤；
  3. 反复捡拾几次，收敛到唯一地址。

结果收敛到 $7E9102-$7E9105 这一组 4 字节（小端）。

插曲：初次搜索时发现该地址上有一个巨大的随机数（如 1457251158），而不是 0。原因在于：新游戏的开场初始化在复位后并不会立刻清零该块 WRAM，启动瞬间读到的是上一次运行残留的脏数据。这给”用内存值定位初始化写入”带来干扰，详见”遇到的问题”第 1 条。

5.3 关键结论

  • 新游戏初始化中，金币最后一次被写为 0 是在帧 10580（$96:F98E，即零填充指令 STA [$44],Y 所在例程）；
  • 此后直到玩家捡金币（帧 14652）之间，没有任何写入；
  • 因此在初始化例程末尾注入”设置金币=999999”，不会被后续代码覆盖。

6.2 反汇编 $96:F8B9

6.3 最终处理 $96:FB2F

$96FB2F 是钩子点调用的原始函数。反汇编确认它只重算 WRAM 中的派生结构（道具列表、角色状态显示等，写 $7E801A/$7E8026/$7E8300/$7E8328 等），不写 SRAM。真正的存盘写入在别处，以 WRAM 中实时的金币为准。这保证了”钩子只影响初始值，不影响存盘流程”。

7. 补丁实现

7.1 目标

把 $96:F9C9 的 JSL $96FB2F 改成跳转到空闲区的 stub：stub 先用 16 位模式写入金币=999999，再调回原来的 $96FB2F，最后 RTL 返回原流程。

7.2 空闲区

文件末尾前仍有大段 $FF 空闲，选 $73:CCA0（文件偏移 0x39CEA0） 作为 stub 落点。$73 属慢速库组（$40-$7D），LoROM 下正常映射且空闲。

8. 存档/读档一致性分析

这是本破解最关键的工程问题：读档路径也会执行 $96:F8B9（含钩子），如果不处理，读档时金币会被强写成 999999，破坏存档值。化解的关键是两条路径的调用顺序：

8.2 读档路径

反汇编 $96:F305 确认它是读档例程：

  1. 用”补码法”校验存档块：把校验字节取反写回再比对，匹配则有效（$F31C-$F337）；
  2. 通过 MVN $7E,$70 把 SRAM（bank $70）整块复制到 WRAM（bank $7E）（$F343-$F361 循环，按 $F84D/$F84F 表分片复制）。

关键点：钩子所在的 $96:F8B9 在读档复制之前执行。钩子写下的 999999 随后被 $96:F305 复制的存档真实金币覆盖。因此：

  • 读档结果 = 存档中的金币；✅
  • 存盘写 SRAM 用的是 WRAM 实时金币（我们只改初始化，不改增/减金逻辑），所以存进去的就是玩家当前金币；✅
  • 结论：存档 → 读档，金币保持一致，钩子不影响读档数值。

10. 遇到的问题

10.1 初始内存残留脏数据

新游戏复位后金币地址上不是 0，而是上次运行的残留值（如 1457251158）。这误导了最初的判断——差点把残留值当成”游戏内实际金币”去追来源。解决：先完整跑一遍新游戏流程，看金币何时归 0，再追写入。

10.2 写回调去重漏掉”重复写 0”

第一次写监控只记录”值变化”，初始化零填充写 0 时金币本来就是 0，被直接跳过，导致找不到初始化写入点。解决：改为记录窗口内所有写入（不判变化），虽然日志量大，但完整无遗漏。

10.3 LoROM 高速库/慢速库镜像换算

一开始用 文件偏移 = CPU库 * 0x8000 换算，把 $96:F9C9 算到了 4MB 文件之外，报 IndexError。实际 LoROM 4MB 下 CPU 库 $80-$BF 镜像文件前 64 库，正确公式是 (CPU库 & 0x3F) * 0x8000 + 0x200 + (地址 - 0x8000)。

10.4 误以为要改”加金币”例程

捡箱子加金币的 $82:D7F1/$82:D7FA 看起来是修改点，但那是加法例程，改它会影响所有金币增减逻辑（买卖、赏金、修理），副作用巨大。真正的修改点应是”初始化清零”那一处。

10.5 读档路径共用初始化例程的隐患

发现新游戏和读档都调用 $96:F8B9（含钩子）时，一度以为读档金币会被强制改成 999999。通过反汇编 $96:F305 确认读档顺序是”先建模板（钩子）→ 再读存档覆盖”，隐患自然化解——同一条钩子代码在两条路径下的行为由调用顺序决定。

11. 总结与心得

  1. “值变化”不等于”写入”：初始化写 0 是最容易被去重逻辑漏掉的写入，全量捕获才能建立完整的写入时间线。

  2. 先摸清写入时间线，再选补丁点：金币在帧 10580 被初始化归零、帧 14652 才被玩家拾取，这中间是安全窗口。选”最后一次初始化写入之后、玩家操作之前”的点位，补丁才不会被覆盖。

  3. 函数复用是破解的双刃剑：新游戏/读档共用 $96:F8B9，既是”打一处补丁即可”的幸运，也是”读档也会触发”的隐患。判断清调用顺序，隐患就变成特性。

  4. LoROM 映射是 SFC 破解的入场券：高速库/慢速库、文件库与 CPU 库的换算关系必须一次算对，否则后面全盘皆错。

  5. 最小改动 + 空闲区 stub：只改了 4 字节跳转 + 在空闲区放 23 字节 stub，不破坏任何原有指令；stub 内 REP/SEP 配对，保证 CPU 模式与原流程一致。

  6. 存读档一致性靠”复制覆盖”而非”绕过”：没有试图阻止读档路径执行钩子，而是利用读档例程 MVN $7E,$70 的整块覆盖，让存档数据天然压过模板值。
