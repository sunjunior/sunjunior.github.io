1. 背景与目标（三阶段破解演进总览）

《兔八哥疯狂城堡》是 Kemco 于 1989 年推出的 FC/NES 迷宫动作游戏。玩家操控兔八哥在城堡中收集胡萝卜并躲避敌人，每死亡一次扣 1 条生命，生命归零则游戏结束（GAME OVER）回到标题。

本次破解分为三个阶段，一步步从”不死”推进到”死了也当没死”：

阶段 需求 行为 交付物
① 无限生命 遇敌死亡不减少命 死后仍需过关卡牌、重开本关（敌人/胡萝卜重置） (Infinite Lives).nes
② 原地复活 遇敌不死 + 原地复活 死亡后在当前画面原地复活，约 4 秒无敌，不重开本关 (Respawn In Place).nes
③ BGM 修复 复活后背景音乐恢复 原地复活补丁此前会让 BGM 永久消失，本阶段补齐 (Respawn Music FIXED).nes

三阶段逻辑脉络：① 解决”扣命与 Game Over”；② 解决”死后要重打本关”的体验；③ 解决 ② 引入的 BGM 副作用。每一阶段都在前一阶段基础上验证、演进。

2. ROM 与游戏信息

项目 值
文件名 The Bugs Bunny Crazy Castle.nes
文件大小 98,320 字节
文件 CRC32 DB0C3656
PRG CRC32 B10429AA
格式 iNES，Mapper 1（MMC1），水平镜像
PRG ROM 0x04 × 16KB = 64KB（4 个 bank）
CHR ROM 0x04 × 8KB = 32KB
Board / Chip NES-SBROM / MMC1B1-H，NTSC

关键地址约定

  • 文件偏移：含 16 字节 iNES 头，补丁落点以它为基准。
  • MMC1 采用 bank 切换，64KB PRG 分成 4×16KB。最后一个 bank（bank 3）固定映射在 CPU $C000-$FFFF，因此 CPU 地址 $C000-$FFFF = PRG bank 3，永远参与不了 bank 切换（这是 hacker 代码唯一安全落点）。
  • 生命数：零页 $007C，初始值 5，显示于 HUD。
  • 音乐轨道表：CPU $9E00（零页 $3D/$3E 指向），只存在于 PRG bank 2（详见 §12.2）。

核心思想是两条腿走路：

  • ROM 层：从源头掐断扣命写操作（改补丁，对任何模拟器/烧录卡都有效）。

5. 详细分析过程

5.1 无头进入真实可玩关卡（本次最大的坑）

本作没有”生命值”概念，只有”命数”，且标题→菜单→关卡牌→游戏有复杂的输入状态机，必须先在无头脚本里稳定进入真实关卡，后续一切分析才有意义。

最终方案（enter_game.lua / in_game3.lua）：

  1. 标题画面：每 120 帧按一次 START，直到 $007C == 5。
  2. 菜单确认：$007C == 5 标志着菜单 START 确认已执行 $C032 STA $7C（LDA #$05），此时进入关卡牌流程。
  3. 关卡牌：ofs_000_91F9_02_load_stage 显示关卡牌后进入等待循环 $9216-$922C，条件是 ram_btn_press AND #con_btns_SAB（$D0，即 Select/A/B 任一）后 BNE 跳出。约 90 帧后按 START 进入。
  4. 游戏开始判定：RAM 判定而非 PC 采样（原因见 §5.4）——玩家对象 $0500 的第 7 位置位即代表角色生成、游戏真正开始。

仅靠静态扫描仍要排除”静态存在但实际不执行”。用 Mesen Lua 的写内存回调抓每次写 $007C 的时机，再配合强制死亡注入：

  • 未补丁：清零 $0500 强制死亡 → 约 30 帧后 $C11C 执行 → $7C 5→4，与反汇编一致。
  • 死亡后回到关卡牌，START 重进，$7C 延续 4 → 完整验证”死亡→扣命→再战”闭环。

为什么用 RAM 判定而不是 PC 采样：在 endFrame 回调里采样 CPU 的 PC，结果恒为 NMI 等待点 $EED5（中断服务例程），拿不到游戏主循环的真实 PC；改为观测 $7C==5（菜单确认标记）与 $0500 bit7（玩家生成标记）两个 RAM 状态即可 100% 判定当前所处阶段。

6. 阶段一：无限生命补丁（遇敌死亡不减少命，但仍需重开本关）

破解的难点不在”改哪”，而在”找到哪”。本阶段按真实排查顺序展开：现象 → 定位生命数据 → 定位扣命代码 → 动态验证 → 方案选型 → 落补丁 → 复验。

6.1 现象与破解思路

现象：遇敌死亡后 HUD 命数 -1，减到 0 即 GAME OVER 回标题。

思路：所谓”扣命”在 6502 上就是一段确定的数据操作——某条指令把”生命数”这一内存字节减 1。因此破解拆成两步，缺一不可：

  1. 数据定位：生命数存在哪个内存地址？（找出”什么在变”）
  2. 代码定位：是谁把它减 1？（找出”谁在改”）

只用静态手段不够：反汇编能列出”所有可能改这个地址的指令”，但静态存在 ≠ 实际执行；只用动态手段也不够：内存监听要先知道听哪个地址。所以是静态扫描 + 动态验证双管齐下，互相印证。

6.2 数据定位：快照差分锁定 $007C

进入真实可玩关卡（进入方法见 §5.1，这是本作最坑的一步）后，先快照全 RAM，再人为触发一次死亡，再快照，对两张快照做差分——变化的字节就是”死亡事件相关状态”。

差分结果：生命数 = 零页 $007C（初始 5，死亡后 5→4）。同时顺带摸清了玩家实体布局：

RAM 含义
$007C 生命数（初始 5）
$0500 玩家对象，bit7=存在（$80）
$0501 / $0502 玩家 X 低 / 高
$0503 玩家 Y

死亡时序（实测）：清零 $0500 强制死亡 → 约 30 帧后扣命才执行 → $7C 5→4。扣命不是瞬时的，说明死亡有一个”结算阶段”。

6.3 代码定位：全 ROM 扫描 $007C 的访问指令

反汇编 64KB PRG，列出所有读写 $007C 的指令——全 ROM 仅 5 处（写 4、读 1）：

文件偏移 CPU 地址 机器码 语义 判定
0xC042 $C032 85 7C 新游戏初始化生命 = 5（前一条 A9 05） 保留
0xC12C $C11C C6 7C ★ 扣命（DEC） 唯一扣命点
0xC155 $C145 E6 7C 吃 +1 命道具 保留
0xC16C $C15C 85 7C 奖励关结算 +3 命写回 保留
0x93B6 $93A6 A5 7C HUD 显示生命数（读） 保留

全 ROM 只有一处 DEC $7C（C6 7C），这就是嫌疑最大的扣命点。但它到底在不在”死亡”路径上？看它的上下文：

语义已经很清楚：每次重进一关（关卡结算）先判是否奖励关，非奖励关就 DEC 扣命；扣到 0 走 $C129 GAME OVER，否则继续。这就是死亡结算例程。

6.4 动态验证：确认 $C11C 确实在死亡后执行

静态扫描证明”这条指令存在且看起来合理”，但要排除”静态存在但实际不执行”。用 Mesen 写内存回调监听 $007C，配合强制死亡注入（细节与”为什么用 RAM 判定而非 PC 采样”见 §5.4）：

  • 未补丁：清零 $0500 强制死亡 → 约 30 帧后 $C11C 执行 → $7C 5→4，与反汇编一致；
  • 死亡后回到关卡牌，START 重进，$7C 延续 4 → 完整验证”死亡→扣命→再战”闭环。

6.5 方案选型：为什么是 NOP 掉 DEC，而不是改别的

候选方案对比：

方案 改动 效果 评价
a. 改 $C120 BEQ 跳转 永远跳过 GAME OVER 不 GAME OVER，但命照扣 不彻底
b. DEC $7C → EA EA 扣命失效 $7C 恒 5，GAME OVER 天然不可达 ★ 采用
c. 初始生命设很大 改 $C032 的 A9 05 治标不治本，早晚扣光 不干净

选 b 的三个理由：

  • 同位替换、无需搬移：C6 7C（DEC 零页）是 2 字节，EA EA（NOP NOP）也是 2 字节，同长度原位替换，不改变后续任何跳转目标；
  • 保留后续判定、逻辑最干净：$C11E LDA / $C120 BEQ 原样保留——因为 $7C 恒等于 5，BEQ（判 0）永不成立，GAME OVER 分支（$C129）静态上还在、运行上永远不可达，误伤最小；
  • 只掐”扣”不碰”加”：初始化（$C032）、+1 道具（$C145）、奖励关 +3（$C15C）全部保留，正常奖励机制不受影响。
文件偏移 PRG 偏移 CPU 地址 原字节 新字节 效果
0xC12C 0xC11C $C11C C6 7C EA EA 扣命失效，生命恒为 $05

补丁后 ROM：The Bugs Bunny Crazy Castle (Infinite Lives).nes，98,320 字节不变，文件 CRC32 D21C2AE1、PRG CRC32 BB666A4B。

6.7 验证结果与行为边界

验证（详见 §9）：补丁 ROM 三轮死亡周期 $7C 恒 5（对照原版 5→4→3）；IPS 回环逐字节一致；作弊码双保险下游戏读恒 5、永不 GAME OVER。

7. 双保险：Mesen 作弊码

7.1 原理

Mesen 的 NesCustom 作弊码格式为 AAAA:VV（地址:值），实现方式是拦截对指定地址的读取，一律返回设定值。配合”从源头 NOP 掉扣命写”的 ROM 补丁，即便将来发现漏网的分支，作弊码也能兜底。

作弊码：007C:05（生命数读取恒为 5）。

7.2 读取路径的坑（重要）

Mesen Lua 对同一地址存在两条读取路径，结果可能不同：

API 路径 是否经过作弊码
emu.read(addr, emu.memType.nesInternalRam) 直接读 RAM 缓冲 否（绕过）
emu.read(addr, emu.memType.nesMemory) (= 8) 走 DebugRead → 内存管理器 是

实测：作弊码生效时，游戏读 $7C 恒为 $05，而 nesInternalRam 读到的是真实 RAM 值（被扣到 $04）。因此：

  • 验证作弊码是否生效要用 nesMemory；
  • 观察真实生命要用 nesInternalRam（两者对照即知”作弊层是否真的在兜底”）。

7.3 作弊码文件格式

Mesen2 会在 GUI 加载 ROM 时自动应用 ~/.config/Mesen2/Cheats/<RomName>.json（RomName = ROM 文件名去掉扩展名，由 GetRomName() 得到）。JSON 字段为 PascalCase，枚举以字符串保存，序列化器启用了 UseStringEnumConverter：

11. 阶段二：优化为遇敌不死 + 原地复活（Respawn In Place，4 秒无敌）

阶段一解决了”命”，但暴露了新体验问题：死后要重打本关。本阶段换了一种破解思路——不再改”数据”，而是改”控制流”：拦截死亡流程的终结点，把”清除对象”改成”原地复活”。按”目标 → 找钩子 → 设计 → 踩坑 → 修复 → 验证”展开。

11.1 目标与破解思路

§9.5 已确认阶段一的补丁行为是”死后重开本关”。本阶段实现更友好的玩法：玩家阵亡后不重开本关，在当前画面原地复活（保留死亡时的位置与关卡状态），并给予约 4 秒无敌时间（复活瞬间的敌人不会立刻再杀死你）。

阶段一 vs 阶段二的思路对比：

阶段一 阶段二
破解对象 改数据（扣命指令） 改控制流（死亡流程）
核心问题 生命数被谁减 1 死亡后代码流向哪里
手段 扫描 $007C 访问点 追死亡动画的流程终点

要拦截一切死亡，必须找到死亡流程的终结点——玩家死后动画播完，最终一定有一段代码”把玩家对象清除”。接管这段代码，把”清除”换成”复活”，就等价于”死了也当没死”。

同时因为不再重载关卡，扣命代码 $C11C 根本执行不到，天然自带”不扣命”效果（详见 §11.7）。

11.2 钩子定位：找到死亡流程的唯一终结点 bra_D1B6

死亡动画由 sub_D012 处理，按 $0510 相位分帧播放”击退 → 下坠 → 清除”三个阶段。无论从哪一阶段结束，最终都会落到同一段代码（$D1A0 与 $D1AB 两处计数归零后都会走到）：

即”死亡动画结束 → 把该对象状态清零（对象被移除）”。

如何确认这是”唯一”终结点？ 反汇编列出所有 STA $0500,X（对象清除型写），再逐个追调用链：只有 $D1B6 这一处位于”死亡动画结束”路径上，其余是初始化/切换等正常流程。再结合动态验证（真实碰撞死亡后，写回调命中 $D1B6），锁定它就是死亡流程的汇聚点——整个死亡流程中”对象移除”只发生在这一处，玩家与敌人共用（敌人走 X≠0 分支），接管它就能拦截一切死亡。

顺带说明：本作没有”玩家掉出屏幕”这类独立死亡路径，敌人的碰撞（sub_CCF6 → sub_CE5E）与强制死亡最后都进 $D1B6，接管它是唯一且充分的死亡钩子。

11.3 补丁设计与 Handler 逻辑

  • Hook：CPU $D1B6（文件偏移 0xD1C6）6 字节改为 4C 71 EB EA EA EA（JMP $EB71 + 3×NOP）。
  • Handler：43 字节，放在固定 bank 3 的 $EB71（文件偏移 0xEB81），该区原本是 MMC1 bank 3 的 $FF 空闲区，永不参与 bank 切换（这是选它的关键原因，见 §11.4 坑 1）。

Handler 逻辑（X = 对象索引，来自 $D1B6 进入时的 LDX）：

玩家分支共 37 字节，敌人分支 6 字节，总计 43 字节。

各步的设计理由：

  • CPX #$00 区分玩家与敌人：$D1B6 进入时 X = 对象索引（0=玩家）。玩家分支恢复”存在”，敌人分支保留”清除”——否则敌人也会原地复活、永远打不死；
  • $0500 = $80：把对象状态从”死亡（被清零）”恢复为”存在（bit7）”，这是”复活”的实质；
  • 清 $050C-$0511：死亡动画残留的相位/位移数据在复活后无意义，统一清零，避免脏状态（$0510 是死亡相位计数器）；
  • $0512 = $20：坑 2 的修复，见 §11.4；
  • $0515 = $FF：无敌计时器 ≈ 4.27 秒，见 §11.5。

11.4 两个关键坑（都靠真实复现逼出来的）

坑 1：handler 必须放在固定 bank 3。 最初把 handler 塞进当前代码区尾部（会参与 bank 切换的 bank），结果是：玩家死亡 → JMP 进 handler → 途中 MMC1 切换 PRG bank → handler 字节立刻变成另一 bank 的数据 → 直接花屏/崩溃。改成固定 bank 3 的 $FF 区后消失。同理 hook 本身必须落在 bank 3（$D1B6 天然在 bank 3，$C000-$FFFF），所以 JMP $EB71 两段都永不被切走。

坑 2：复活后无法移动（输入被丢弃）。 首次接通”真实碰撞 → 死亡 → 原地复活”后，玩家能站住、能闪烁，但按方向键完全不动。逐帧对比（respawn_input.dat）：$F7 方向输入正确送达（=01），但移动缓存 $050B 恒为 0。根因在移动输入门控 sub_C1A8：

死亡击退（sub_E343 的 X-=8）与复活后，玩家 X 常落在非 16px 对齐的位置（如 85、60），$050B 永远为 0 → 方向输入被丢弃 → 玩家冻结。修复：复活分支把 $0512 置为 $20（bit5，”移动中”标记）→ sub_C1A8 无条件放行 → 复活后立即能动。对照实验：未打该修复时复活后按住右键 X 纹丝不动；打上后 X 28→58、85→115 均正常。

11.5 无敌计时器与死亡判定

  • 复活时写 $0515 = $FF（约 4.27 秒），期间 sub_CCF6 会跳过玩家的敌人碰撞判定（$CD05-$CD28 的 invinc 分支），并闪烁显示。
  • 死亡判定统一写作 (state & $A0) == $A0：本作死亡态是 $A0 或 $A4（bit7=存在 + bit5=死亡，bit2 视掉落/击退方向），不能只判 == $A0，否则 $A4 死亡帧会漏检。

11.7 一个意外福利：生命自动恒为 5

补丁 ROM 的 0xC12C（$C11C）没有打无限生命补丁（仍是 C6 7C），但实测三轮死亡 $7C 恒为 5。原因：扣命 DEC $7C 只在关卡重载循环 $C11C 里执行（每重进一关扣一次），而原地复活根本不重载关卡——死亡 → $D1B6 → handler → 原地复活，完全绕过了 loc_C04B_loop。所以”原地复活”天然自带”不扣命”效果，无需再叠无限生命补丁。

11.9 设计边界

  • 复活点 = 死亡动画结束时的坐标，若玩家在贴墙位置死亡，击退/动画可能把尸体顶进障碍区，复活后可能卡住（与 sub_E343 的 X-=8 击退方向有关）。测试中出现的 X=60/56/52 落点经 walkability 探测均可行走，暂未复现卡死；极端贴墙场景未做专项处理。
  • 无敌 255 帧结束后才恢复可被伤害状态，期间无法再次死亡，故本验证的”连续死亡”用强制死亡初始化触发（§11.5 的死亡态写法）完成第 2、3 周期。
  • BGM 缺失是进入阶段三的原因：本阶段验证中已经观察到复活后背景音乐消失（§12）。

12. 阶段三：修复复活后 BGM 缺失

阶段二引入了新 bug：复活后 BGM 永久消失。这是三阶段里最难的一环——它逼着我们真正吃透这个游戏的 MMC1 bank 切换与音乐子系统。按”现象 → 音乐系统逆向 → 失败实验复盘 → 自动续播为何不可行 → 最终方案 → 验证”展开。

12.1 现象与破解思路

现象：阶段二的”原地复活”补丁让 BGM 在复活后永远消失。

为什么消失：原版只在”Game Over → 重新加载当前关”的流程里才会重启 BGM（$C01A → $F185 #26 → 切到 bank 2 的 $8DEA → JSR $F7A2 播放 9 号轨道），而原地复活完全绕过关卡重载，自然没有重启音乐的地方。

思路：在 handler 里主动补一次”播放 BGM”。但”JSR 一个播放函数”看似简单，其实踩了两个雷：bank 映射与bank 栈平衡。要做得对，必须先逆向清楚三件事：

  1. 9 号轨道（BGM）的数据在哪、怎么指向它；
  2. 播放入口是哪个、内部做了什么；
  3. 为什么从主循环上下文直接调用会坏。

12.2 音乐系统逆向：关键地址约定

项目 值 说明
轨道表 CPU $9E00（零页 $3D/$3E 指向） 每项 2 字节 = 轨道数据指针
9 号轨道（BGM） 表项 [8] = $9E10 → $ADB4 数据首字节 01 → init_song
init_song $F87A $3A = $44 + 1（正在播放的曲目号）
play_music 完整入口 $F7A2 带 bank 切换的平衡入口（最终修复用）
play_music 半截入口 $F7AF 假设 bank 已切好（失败实验的坑）
自动续播 $F7CC 仅由活动槽位步进完成路径调用
播放单轨 $F7E6 用 $44 查轨道表 → 播放数据

两条必须记住的事实：

  • 轨道表只存在于 bank 2（PRG bank 2，CPU $8000-$BFFF 映射时）。银行 0/1/3 在该地址全是垃圾字节。所以任何读轨道表的代码执行时，bank 2 必须正在 $8000。
  • 游戏主循环上下文里 bank 2 并不在 $8000。NMI 帧驱动确实会临时映射 bank 2（$F8D1 → $F8E2: JSR $F138，其中 $F138 = LDA #$02; JSR $ECCA），但跑完 $F8EC 的槽位处理后会 $F13E 从 $0C 恢复原 bank。因此从我们的 handler（主循环上下文）触发音乐，必须自己做 bank 2 映射。

12.4 失败实验：为什么 JSR $F7AF 会崩

第一次尝试在 handler 里写 LDA #$09; JSR $F7AF（48 字节版 “Respawn Music”），结果复活流程陷入无限循环（Mesen 实测：f15046 之后一直 RESPAWN，无法继续）。复盘有两条根因，一条是 bank 映射，一条是 bank 栈：

  1. 读错 bank：$F7E6 用 $3D/$3E=$9E00 查轨道表时，bank 2 没有映射在 $8000（游戏主循环跑的是 bank 0/1 的数据），读到的是垃圾 → $45=$0000（正常应为 $ADB4）。
  2. bank 栈失衡：$F7AF 尾部的 $F146 pop 了一个没人 push 过的 bank 栈槽位，把垃圾写进 CPU 栈返回地址 → 返回后 PC 跑到未知位置 → 崩溃/循环。

调测证据（slot_trace2.lua 逐帧采样，TBL[] 读的是 $9E00 表内容）：

TBL 全 0 正是”bank 2 没映射，读出来是银行 0 的垃圾”的铁证。

12.5 为什么”只设 $3A“也救不了（自动续播不可达）

或许有人会想：直接写 $3A = 9 让”正在播放曲目号”等于 9，游戏会不会自动续播？答案是不会。全 ROM 搜索证实：$F7CC 的 3 个调用点（$F9A4 / $FA29 / $FB17）全部来自活动槽位的步进完成路径（$F93D / $F9DF / $FACC 的 BCS）。槽位全空时这 3 个点根本执行不到。所以原地复活时只把 $3A=09 设为”想播 9 号”，永远不会触发播放——必须显式调用播放入口。

12.6 最终修复：换对入口 $F7A2（共 2 字节）

核心改动：JSR $F7AF → JSR $F7A2

handler 的”播放音乐”段从 LDA #$09; JSR $F7AF 改成 LDA #$09; JSR $F7A2。$F7A2 内部会替我们完成：

  1. push 当前 bank → 切到 bank 2；
  2. 播放 9 号轨道（$44=9，因 $3A!=9 故 DEC $44→8 → $F7E6 查表得到 $ADB4）；
  3. 轨道数据首字节 01 → init_song → $3A=$44+1=9；
  4. pop bank 栈 + 恢复原 bank → 干净地返回。

整条链自洽，无需手工设 $3A。

顺带修复前作遗留的 BNE 目标错误

前作 48B handler 的敌人分支 BNE $28 目标是 9D 00 05（STA $0500,X 的操作数），没落在预期的 A9 00（LDA #$00）上。后果：X≠0（玩家 2 / 敌人）走该分支时，会拿错误的 A 值写入 $0500,X。正确偏移应为 $26。

13. 综合关键技术结论

阶段一（无限生命）：

  1. 生命地址 $007C：零页一字节，初始 5，死亡递减，归零进 GAME OVER。
  2. 唯一扣命点 $C11C：全 64KB PRG 仅 1 处 DEC $7C（比蝙蝠侠的 5 处简单得多），NOP 掉即无限生命。初始化/奖励写点全部保留。
  3. NOP 的粒度：只 NOP 掉 DEC 一条，保留其后 LDA/BEQ 判定——生命恒 5，GAME OVER 分支天然不可达。
  4. 进入真实关卡是最难的环节：本作标题/菜单/关卡牌是多级输入状态机，需要 $7C==5（菜单确认）+ $0500 bit7（玩家生成）双 RAM 状态判定，逐级注入输入。
  5. endFrame 里 PC 采样不可用：恒为 NMI 等待点 $EED5，必须改用 RAM 状态判定。
  6. 输入注入必须放 inputPolled 回调，直接 setInput 会被每帧覆盖。
  7. 作弊码读取路径分叉：验证作弊必须走 nesMemory，原始 RAM 读取会绕过。
  8. testRunner 不自动加载作弊文件：无头验证用 emu.addCheat 显式注入。
  9. --timeout=0 会瞬间停模拟器，脚本根本跑不起来，这是最常见的假”失败”。

阶段二（原地复活）：

  1. 死亡会重开本关而非原地续命（阶段一行为）：死亡 → $C11C DEC → JMP loc_C04B_loop → 关卡牌脚本 → 重新加载当前关；阶段一只消除 Game Over 与扣命，不改变”死后重打本关”机制。
  2. 死亡终结点只有一个 $D1B6：玩家与敌人的”死亡动画结束 → 对象清除”都汇聚于此，接管它即可拦截一切死亡。
  3. hack 代码必须放固定 bank 3：MMC1 bank 切换会把”散落在可切换 bank 里的 handler”瞬间换成别的字节，必须占用 $C000-$FFFF（固定 bank）的空闲区。
  4. 复活后不能动 = 输入门控问题：sub_C1A8 只在 16px 对齐或 $0512 bit5 置位时才把方向输入写进 $050B；死亡击退会打破对齐，复活 handler 必须显式置 $0512=$20，否则玩家冻结。
  5. 原地复活自带无限生命：扣命只发生在关卡重载循环 $C11C，原地复活不重载关卡 → 永不扣命，无需叠无限生命补丁。
  6. 死亡判定要写 (state & $A0) == $A0：本作死亡态可能是 $A0 或 $A4，只判 == $A0 会漏检。
  7. 无头模式下截图用 emu.getScreenBuffer()：emu.takeScreenshot() 在 --testRunner 下无视频渲染器会静默失效；getScreenBuffer() 返回 ARGB 缓冲可正常 dump（respawn_screen.lua）。

阶段三（BGM 修复）：

  1. bank 映射是 MMC1 游戏改动的第一前提：任何跨 bank 调用都要先确认目标 bank 在不在 $8000。本次 TBL[0000,...] 即”bank 2 没映射”的直接证据。
  2. $F7A2 才是 play_music 的完整入口，$F7AF 只是半截——它依赖调用方已经做过 $F129（push + 切 bank）。直接 JSR $F7AF 会 bank 栈失衡，$F146 把垃圾写进 CPU 返回地址 → 复活循环崩溃。
  3. 自动续播 $F7CC 救不了原地复活：它的 3 个调用点全在”活动槽位步进完成”路径，槽位全空时永远执行不到。想播歌必须显式调播放入口。
  4. NMI 音乐处理自带 bank 2 映射（$F8E2 JSR $F138），但游戏主循环上下文没有——handler 里的音乐调用必须自己负责 push/pop。
  5. $F7A2 用 A=9 播放 9 号轨道：$3A!=9 → $44=9 DEC→8 → $F7E6 查表得 $ADB4 → 数据首字节 01 → init_song 设置 $3A=9。整条链自洽，无需手工设 $3A。
  6. 修复共 2 字节：0xEBA8: AF→A2（换入口）+ 0xEB84: 28→26（修 BNE 目标）。
  7. 验证签名与”原版死亡→重开”完全一致：$3A=09/$44=08/$45=$ADB4/p1bgm=80，BGM 复活后持续播放至 AFTER+100，无崩溃。
  8. 写回调里拿不到 PC（emu.getCpuState() 返回 nil），必须用 RAM 状态判定；APU 写入时间线（music_trace2.lua）则可在 endFrame 里配合 getCpuState 记录。
