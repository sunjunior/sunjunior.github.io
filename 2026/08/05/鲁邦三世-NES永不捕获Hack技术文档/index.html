鲁邦三世（NES / FC 汉化版）永不捕获 Hack 技术文档

逆向工程 2026/08/05

目标游戏：鲁邦三世：潘多拉的遗产（Lupin III: Pandora’s Legacy，汉化版）
目标：修改 NES ROM，使角色永远不会被捕获（不触发剧情中的”逮捕”结局）
交付物：已打补丁的 ROM、标准 IPS 补丁（V15）
日期：2026-08-05

1. 背景与目标

本作是鲁邦三世主题的 FC/NES 游戏，按”选人 → 关卡（剧情叙事屏）→ 捕获（该角色被逮捕，可用角色 -1）→ 选人”的循环自动推进。游戏里敌人靠近并接触主角时，会弹出一个约 8 秒的”逮捕”过场，结束后该角色被判定捕获。

本次任务的破解目标：

  1. 找到”捕获”这一判定在内存中的落点。
  2. 定位触发捕获提交的代码位置。
  3. 修改 ROM，使捕获提交永远不发生（永不捕获）。
  4. 提供可直接使用的交付物：已打补丁的 ROM、标准 IPS 补丁。

最终成果：捕获弹窗彻底消失（V15），但敌人靠近后游戏仍会刷新画面（捕获结算仍在执行，见 §7）。

2. ROM 与游戏信息

项目 值
文件名 鲁邦三世-潘多拉的遗产.nes
文件大小 524,304 字节
MD5 018c2bb15d2fe159014cb14b7889c70b
iNES Header 4E 45 53 1A 10 20 41 00 ...
格式 iNES，Mapper 4（MMC3），垂直镜像
PRG ROM 0x10 × 16KB = 256KB（0x40000 字节）
CHR ROM 0x20 × 8KB = 256KB（0x40000 字节）
汉化 基于日版汉化，关卡文字为中文叙事文本

关键地址约定

  • PRG 偏移：指相对 PRG 数据起始（文件偏移 = PRG 偏移 + 16 字节 iNES 头）。
  • MMC3 采用银行切换（bank switching），同一段代码可能映射在不同 CPU 地址。本文以文件偏移为唯一基准，CPU 地址仅作辅助引用。
  • 关卡逻辑所在的 bank15 半体 30 映射到 CPU $C000-$DFFF（文件 0x3C010-0x3DFFF），故 CPU 地址 = 文件偏移 − 0x30010。该公式已被实机 exec 回调逐字节验证。
  • 捕获相关零页：$3B 捕获/指令代码、$3D 捕获状态机、$5F 敌属性/角色可用掩码、$24 关卡编号、$AD 敌位号、$46 关卡代码、$37 门开关、$D4 当前选人。

关键前提：真实捕获必须交互游玩才能触发，而本作的交互触发只能靠人工撞敌人。因此这一轮的所有决定性证据都来自 GUI 里用 Lua 控制台跑实机追踪，无头脚本只用来覆盖演示/回放路径（详见 §8）。

4. 破解总体思路

核心思想：先做静态扫描缩小嫌疑范围，再用实机执行 + 写跟踪把”真凶”从”长得很像”的代码里挑出来。本作的教训就是——候选触发点多达三个，肉眼和静态分析根本无法区分，必须靠实机证据一锤定音。

5. 详细分析过程

5.1 两套”捕获”系统：演示模式 vs 真实游戏

本作存在两套互不相干的捕获路径，这是整个破解最大的坑：

路径 触发条件 关键地址 标志
演示模式 无输入自动演示（attract / 剧情屏） CPU $C53C 状态机（文件 0x3C54C） $3D: 0→1→2→$FF，写 $3B=91
真实游戏 玩家主动撞敌人 CPU $C6B4（文件 0x3C6C4） 写 $3B=0x10（捕获界面）

5.2 第一轮尝试（V1–V4）：盯错了状态机

最早用无头脚本追踪 $3D，发现 $3D: 0→1→2→$FF 的状态机（CPU $C53C），$FF 被视为”提交捕获”。据此把状态机里写 $3D=$FF 的指令（文件 0x3C56B，85 3D→EA EA）NOP 掉。

结果：演示模式的捕获被消灭，但真实游戏依然会弹窗。V2–V4 继续在 $3D 周围的”死代码链”上打补丁（$5F、$6A、$C0），全部无效——因为这些地址根本不参与真实游戏的捕获触发。

5.3 第二轮尝试（V5–V14）：又盯错了提交点

静态扫描全 ROM 找对 $3B 的写入，发现三处 A9 10 85 3B（LDA #$10; STA $3B）：

文件偏移 CPU 归属 真实路径？
0x1B9C4 bank13 $B9B4 另一个 PRG bank，独立小例程（...60 即返回） 否（V5–V14 反复改这里，实机仍弹）
0x3C6C2 $C6B2（bank15） 捕获例程 $C672 内 是（最终命中的就是它）
0x3CC68 $CC58（bank15） 另一个跳转表命令 否（trace 从未命中）

V5 把 bank13 的 85 3B→EA EA（文件 0x1B9C6），单次实机游玩”通过”，曾一度被认为是最终方案。但随后 V6–V14 连续多轮实机游玩仍复现弹窗——V5 的”通过”是假阳性（那一局恰好没触发真实捕获路径）。V11–V14 反复在 bank13 提交点附近做变体（NOP 提交写、改立即数、改跳转绕过、NOP $D6 写入），全部无效。

5.4 实机执行 + 写追踪：锁定真实触发点

决定性的一步：写 Lua 脚本对 $3B/$3D/$5F/$AD/$D4/$6A 挂写回调，对候选地址挂 exec 回调，并在 exec 命中时抓取 6502 栈区还原调用链。在 GUI 里实机撞敌人，日志直接给出了真凶：

  • $C6B4 就是真实捕获触发点：STA $3B 写入 0x10，打开捕获界面。
  • 栈顶 C0 9B = 主循环 JSR $C672 压入的返回地址（调用点位于文件 0x3C0A9，CPU $C099-$C09B）。
  • 栈内 C6 B1 = JSR $C853（$C6AF）的返回地址，确认执行顺序与静态反汇编一致。

第二次捕获（f=3290）同样命中 EXEC $C6B4，栈顶同样 C0 9B。至此根因闭环：弹窗 = $C672 例程内 $C6B4 把 $3B 写成 0x10，与 bank13 那个 V5 目标毫无关系。

5.5 捕获例程逐指令分析

$C672 例程（文件 0x3C682 起，CPU 地址 = 文件偏移 − 0x30010）反汇编：

$5F 的 4 个 bit 是”当前在场敌人”的位掩码。$5F=FC（二进制 1111 1100，低 4 位全 1）时，ROR 第一轮就产生进位，X 停在 0，直接 STX $AD 后进入捕获——所以只要敌人在场，$C6A2 的扫描几乎必然落到 $C6B4 的写。

5.6 触发模型总结

JSR $C672 共有 3 个调用点，全部汇入同一个 $C6B4 写：

文件偏移 CPU 场景
0x3C0A9 $C099 主循环（栈证据 C0 9B）
0x3C168 $C158 门处理
0x3C1CD $C1BD 提交链

V15 的改动（15 字节 NOP）：不再写 $3B=0x10、不调 $C51E 界面初始化、跳过 $3D 忙等，直接落到 $C6C1/$C6C4 收尾 → $C6DA STX $3B（0 或 1）→ RTS。这样既不打开界面，又不会因跳过了 $3D 写入而在 $C6B9/$C6BD 死等。

7. V15 验证结果与当前结论

7.1 结果

  • 捕获弹窗彻底消失：实机游玩中敌人靠近/接触主角，不再弹出约 8 秒的”逮捕”过场。根因确认——弹窗确实由 $C6B4 写 $3B=0x10 触发，NOP 掉整块后该写不再发生。
  • 配合 V2/V3/V14 的遗留补丁（$5F 掩码保留、$6A 短路、$D6 不写），角色可用性不再被清除。

7.2 当前遗留问题（未解决）

  • 敌人靠近主角之后，游戏画面会被刷新（回到选择/标题或重载关卡）。这说明捕获的“结算”逻辑在 $C672 之外仍会执行，V15 只是跳过了界面动画，并没有真正取消”这次接触 = 捕获”的事件本身。
  • 要做成真正的”永不捕获、停留当前关卡”，还需要处理结算路径：追踪 $C672 RTS 之后主循环对 $37/$5F/$AD 的消费逻辑，或在 $C672 内把结算一并短路。这属于下一步工作，本版暂以”弹窗消除”为交付结论。

8. 无头测试的局限（重要踩坑）

Mesen2 的 --testRunner 无头模式在本项目上踩了一个大坑：

  1. exec 回调从不触发：无头模式下 write/endFrame 回调正常（实测 600 帧内 write 回调 27648 次），但exec 回调一条都不触发（对候选地址的探测日志为 0 字节）。
  2. 真实捕获无法无头触发：真实捕获必须交互游玩（主动撞敌人），无头脚本只能通过 setInput 驱动到 f=1186 附近的”回合准备”（37:FF->00），永远到不了 3B=0x10。
  3. 因此，本作的验证必须依赖 GUI + Lua 控制台实机追踪；无头只适合演示模式 / 状态机级别的粗验证（这正是 V1 阶段”看着通过、实则无效”的原因之一）。

10. 踩坑与经验总结

  1. 静态分析必须配动态验证：三个 A9 10 85 3B 长得一模一样，只有 exec + 写回调能分出谁是”真实执行过的”。V5 就是反例。
  2. “验证通过”要有对照、要多轮：V5 单次实测通过是假阳性，V6–V14 连续复现才把它推翻。实机验证应固定操作序列重复多局。
  3. 演示路径 ≠ 真实路径：$3D 状态机只是演示模式的捕获，改它不影响真实游戏。要先分清”你抓到的是哪条路径”。
  4. 无头 exec 回调不触发：--testRunner 下 write/endFrame 正常、exec 从不触发，关键验证必须 GUI 实机。
  5. MMC3 半体映射不能混用：$C000 窗口 = 半体 30（文件 0x3C010），CPU = 文件 − 0x30010；bank13 的 $A000 窗口则是 CPU = 文件 − 0x10010。
  6. 栈返回地址 = JSR 第三字节：本模拟器压栈的是指令第三字节（返回地址 − 1），解析栈帧时返回点要 +1（如 JSR $C853 压 $C6B1，真实返回 $C6B2）。
  7. NOP 的粒度：整块 NOP 触发块（含 $3D 忙等）比只 NOP STA $3B 更安全——后者会留下 8 秒的空转死等。
