VoltTrack：给电动自行车做一款电耗记账 App 的完整实践

Flutter 软件技术 2026/08/30

背景：电驴版「小熊油耗」的空白

家里那台电动自行车，平时在小区充电桩充电——桩是按时长计费的（比如 2 元/3 小时），回老家在插座上充是包月，商场快充又按度数计费。同样是「充满一次电」，三种场景的成本差异巨大，而我完全说不清自己的车每公里到底花多少钱、百公里耗几度电、电池用了两年还剩几分健康度。

油车的油耗记录有「小熊油耗」这样成熟的应用，但电动自行车领域一直没有趁手的工具。市面上的充电类 App 要么绑定特定运营商的桩，要么只有记金额没有算电耗。于是决定自己写一个：VoltTrack，一款纯本地的电动自行车电耗记账 App。本文记录从需求梳理、算法设计到工程实现、发布安装的完整过程。

项目已开源：github.com/sunjunior/volttrack，本文全部代码与交付件（含可下载的签名 APK）均可在仓库及其 Releases 页面获取，协议 MIT。

需求梳理：MVP 只做核心闭环

先明确用户故事：记录每一次充电（金额、时长、电量），自动算出百公里电耗、每公里成本、续航预测和电池健康度。据此划定 MVP 四个模块：

  1. 车辆与电池档案——车辆信息 + 电池组（支持更换历史，同一时刻只有一块「生效电池」）；
  2. 充电记账与日志——三种计费模式的记账向导 + 记录列表（可删除）；
  3. 电耗分析与算账——百公里电耗、每公里成本、续航预测、SOH 电池健康度、续航达成率；
  4. 辅助工具——充电费用计算器（对比「按时长档位」与「按度计费」两种桩，算出哪种更省）。

社区分享、云同步、保养提醒这些后置——MVP 阶段它们只会稀释核心价值。

核心算法：把「充电」变成「事件流」

这是整个应用最有技术含量的部分。难点在于：充电记录里往往没有度数（小区桩按时长计费，你只知道充了 2 小时花了 4 块钱），而且不是每次充电都骑到没电，「这一箱电骑了多远」没有天然的边界。

事件流 + 里程窗口

设计上把每次充电当作事件流中的一条记录，其中带里程的记录（顺手记一下当前里程表读数）充当锚点。相邻两个锚点 A→B 构成一个「窗口」：

几个容易忽略的口径细节（都踩过坑）：

  • 区间取 [t_A, t_B)：起点 A 的充电归属本段骑行，终点 B 的充电归属下一段，保证每条记录只归属一个窗口、不重不漏；
  • SOC 取「到达电量」（即各记录的 socBeforePct），而不是「充后电量」；
  • 两锚点都填了到达电量才启用 ΔSOC 校正，否则退化为 E_ride = Σ充入度数——数据不完整时宁可用粗口径，也不拒绝服务。

用设计文档里的样例验证一下：48V20Ah 电池（0.96 kWh），在里程 1000km 处充 0.72 度（SOC 30%→100%），骑到 1060km 处剩 45%：

0.96 度/百公里，正好在电动自行车 0.8～1.5 的合理区间——公式闭环。

三种模式的度数推算

「充电充了多少度」按模式各有推算优先级：

模式 推算优先级
按度/金额 手输度数 → 金额 ÷ 单价
按时长 功率(W) × 时长(h) ÷ 1000 × 效率系数（默认 0.85）
家用插座 有前后 SOC → ΔSOC × 容量 ÷ 效率（反推）→ 手输估算

其中充电效率系数 0.85 是关键参数：充电器不可能把市电 100% 灌进电池，发热、浮充都有损耗。按时长模式下 300W 充 2 小时，实际入电池的是 0.51 度而不是 0.6 度。

SOH 与续航预测

  • 电池健康度 SOH：只取「低电量（≤10%）→ 充满（≥95%）」的完整充电事件，实际充入 ÷ 理论容量。随用随充的碎片化补电会污染估算，必须设门槛；
  • 续航预测：当前SOC × 容量 × 0.9（保守系数） ÷ 加权平均电耗；
  • 续航达成率：满电→低电窗口的平均实际续航 ÷ 电池档案里的官方续航——这是感受电池衰减最直观的指标。

技术选型与架构

技术栈：Flutter + Riverpod + drift(SQLite) + fl_chart + intl，纯本地存储，不依赖任何服务端。

架构上刻意做成了四层，让算法与 UI、存储完全解耦：

core/engine 是 TDD 的主战场：窗口构建、ΔSOC 校正、度数推算、SOH、达成率全部是纯函数，输入输出明确，测试不需要任何 mock。UI 层只做两件事——从 provider 读数据、把用户输入交给引擎。数据层用 drift 的响应式流（watch），数据库一变 UI 自动刷新。

工程实践：子代理驱动开发（SDD）

这次实现采用了一种有意思的工作流：计划先行 + 子代理驱动。先把 15 个任务写成带完整代码骨架的实现计划（每个任务都有失败测试→实现→提交的 TDD 步骤），然后每个任务派给一个全新的 AI 子代理执行，任务完成后由另一个独立子代理做「规格合规性 + 代码质量」双维度审查。

几个数据点：

  • 15 个任务全部通过任务级审查，其中 3 个任务审查发现了测试缺口，由修复子代理补齐（还做了变异测试验证——故意把实现改错，确认新测试真的能抓到）；
  • 全部任务完成后做了一次整分支宽范围审查，这一步抓到了任务级审查漏掉的规格缺口：记录列表没做、车辆建档没有入口、续航预测因子恒为 null 不工作等 2 个关键 + 6 个重要问题，分两批修复后复审通过；
  • 最终 55 个测试全绿、analyzer 0 告警、release 包构建成功。

体验下来，这种模式的价值在于「每个任务一个全新上下文」——子代理不会被历史对话污染，而审查者与实现者相互独立，避免了自己查自己的盲区。

踩坑记录

  • flutter doctor 报 license status unknown：新版 Android cmdline-tools 的 sdkmanager --licenses 输出变了，flutter 解析不到期望的确认文案。换装旧版 cmdline-tools 12.0 后正常；
  • drift 内存库测试挂起：addTearDown(db.close) 会因 drift 内部的 pending timer 让 widget 测试超时，把 await db.close() 挪到测试体内即可；
  • riverpod 2.6 的 AsyncValue.guard 返回 Future：不能同步 return 进 Provider 体，需改用 try/catch 手工构造 AsyncValue；
  • drift 生成类遮蔽核心模型：Batteries 表生成的数据类叫 Battery，和 core 里的领域模型 Battery 同名，消费方一律用 drift 类型，容量计算收敛到一个 extension 上避免五处复制；
  • 荣耀手机 adb 连不上：荣耀新机型 USB 厂商 ID 是 339b，不在 android-udev 包的规则表里（只收录了老华为 12d1），需要自定义 udev 规则授权；另外荣耀在「仅充电」模式下不暴露 ADB 接口，要切到「传输文件」模式。

交付件

全部代码与交付件已作为 v0.1 开源发布在 github.com/sunjunior/volttrack（MIT 协议）：

  • 代码：仓库根目录即 Flutter 工程（四层架构：core/models 领域模型、core/engine 纯函数计算引擎、data drift 数据层、features 页面 UI），55 个测试，flutter analyze 0 issues；
  • 构建产物：正式签名 release APK 已挂载在 v0.1 Release——arm64 包 20.4MB（主流机型推荐）、armeabi-v7a 17.8MB（32 位老设备）、x86_64 21.9MB（模拟器），release + split-per-abi 相比 debug 包瘦身约 8 倍；
  • 构建与签名说明：见仓库 docs/BUILD.md——keystore 存放在仓库外，key.properties 由 gitignore 排除，构建脚本在缺失配置时自动回退 debug 签名。

真机验证：adb 安装 → 启动 → 走完「建档 → 记账 → 统计」全流程，数据全部落在本地 SQLite。

后记

一个周末级别的个人项目，从「电费糊涂账」的抱怨出发，最终产出一个测试齐全、算法有据可依的完整应用。最大的收获不是 App 本身，而是验证了两件事：一是把领域算法做成纯函数引擎，测试和演进都会非常轻松；二是审查环节独立于实现环节时，规格缺口几乎没有漏网——哪怕是 AI 子代理写的代码，把关逻辑同样成立。

云同步与社区功能留待后续，先把每一度电都记明白。
