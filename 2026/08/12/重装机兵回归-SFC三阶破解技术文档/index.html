1. 背景

《重装机兵：回归》是 FC《重装机兵》在 SFC 上的完全重制版。游戏采用开放式地图 + 赏金猎人的玩法，金钱是核心资源：买车、买装备、补弹药、改武器都需要花钱；角色的 LV / 战斗 / 运转 / 修理等技能等级则决定强度。

本次破解共三阶，难度递增，每阶都建立在前一阶对游戏机制理解的基础上：

3. ROM 结构

原版 ROM 信息：

  • 文件：Metal Max Return_original.SMC（参照），补丁版为 Metal Max Returns0.6.SMC
  • 大小：4194816 字节 = 0x200（磁碟机头）+ 0x400000（4MB）
  • 型号：LoROM 4MB（CPU 高速库 $80-$BF 与慢速库 $00-$3F 镜像同一批 ROM 库，$C0-$FD 与 $40-$7D 镜像另一批）
  • 存档：SRAM 2KB（CPU 库 $70，映射为 snesSaveRam）

关键结论 1：文件带 512 字节磁碟机头。

文件开头是 GAME DOCTOR SF 3（磁碟机/博士机格式），真正的 ROM 数据从偏移 0x200 开始。因此：

这个公式是本项目最容易踩的坑：CPU 库 $96 属于高速库组（$80-$BF），镜像到文件第 $16 个 8KB 库（偏移 0xB0000 附近），而不是文件偏移 0x96*0x8000。详见”遇到的问题”。

金币数据位于 WRAM $7E9102-$7E9105，32 位小端存储。999999 = 0x000F423F，即低字 0x423F、高字 0x000F。

4. 第一阶：初始金币 999999

4.1 金币地址的定位

金币是典型的”可精确验证的数值变量”，先用内存搜索：捡箱子金币 +7，反复过滤，收敛到 $7E9102-$7E9105 这一组 4 字节（小端）。

插曲：初次搜索时发现该地址上是一个巨大的随机数（如 1457251158），而不是 0。原因在于：新游戏的开场初始化在复位后并不会立刻清零该块 WRAM，启动瞬间读到的是上一次运行残留的脏数据。这给”用内存值定位初始化写入”带来干扰，详见”遇到的问题”。

HUD 验证：每帧读取该地址拼出 32 位数值，与游戏内金币 HUD 完全一致，捡箱子后两者同步 +7，地址确认无误。

4.2 写入来源追踪（踩坑与修正）

第一次写监控脚本只记录值变化的写入，结果只捕获到两条写入（开场清零、捡金币），漏掉了初始化例程的零填充——因为初始化时金币本来就是 0，反复写 0 不触发”值变化”。这直接误导了补丁点位的选择。

改为记录窗口内每一次写入（每地址最多 200 条防刷屏）后，完整跑一次”新游戏”流程，金币字节的全部写入如下：

帧 地址 值 PC 来源
2 9102-9105 00 $80:80B3 引导清零（WRAM 全清）
36 9102-9105 00 $87:FE94 早期初始化
9671 9102-9105 00 $96:F359 起名/建号阶段清零
10580 9102-9105 00 $96:F98E 新游戏初始化零填充（最后一个初始化写入）
14652 9102 07 $82:D7F1 捡箱子加金币（+7）
14652 9103-9105 00 $82:D7FA 进位字节

关键结论 2： 新游戏初始化中，金币最后一次被写为 0 是在帧 10580（$96:F98E）；此后直到玩家捡金币（帧 14652）之间没有任何写入。因此在初始化例程末尾注入”设置金币=999999”，不会被后续代码覆盖。

4.4 补丁实现

把 $96:F9C9 的 JSL $96FB2F 改成跳转到空闲区 stub：stub 先用 16 位模式写入金币=999999，再调回原来的 $96FB2F，最后 RTL 返回原流程。

空闲区选 $73:CCA0（文件偏移 0x39CEA0）——文件末尾前仍有大段 $FF 空闲，$73 属慢速库组（$40-$7D），LoROM 下正常映射。

修改一（文件 0xB7BC9 = CPU $96:F9C9）：22 2F FB 96 → 22 A0 CC 73
修改二（文件 0x39CEA0 = CPU $73:CCA0）：写入上表 23 字节 stub。

4.5 存读档一致性

新游戏/读档两条路径都执行 $96:F8B9（含钩子），读档时钩子写的 999999 会在 $96:F305 里被 SRAM 存档的整块复制（MVN $7E,$70）覆盖。因此：

  • 新游戏 → 金币 = 999999 ✅
  • 读档 → 金币 = 存档中的真实金币（钩子值被覆盖）✅
  • 存盘写 SRAM 用的是 WRAM 实时金币 → 存进去的就是玩家当前金币 ✅

关键结论 3：存读档一致性靠”复制覆盖”而非”绕过”。 没有试图阻止读档路径执行钩子，而是利用读档例程的整块覆盖，让存档数据天然压过模板值。

5.3 第一次尝试：修改模板数据（踩坑）

最初尝试直接修改模板1（主角模板 0xB7C2B）为最大值：

主角建号后显示满值，短期运行正常。但推进到红坦克剧情（游戏早期”收集第一辆坦克”事件）时，游戏黑屏死机（背景音乐仍在播放）。经模拟器调试，发现 CPU 卡死在 $96:F246——一个存档/亮度闪烁的死循环。

根因分析：红坦克剧情的事件脚本会从 ROM 模板表重新读取数据，主角模板的满值（LV99/HP9999/属性255）导致计算溢出或表越界，最终进入不可退出的亮度控制循环。

5.4 正确方案：改代码不改模板

既然模板数据被剧情脚本重读，就不能修改模板表。改为修改代码：在角色初始化例程末尾注入新代码，在模板数据被读入 WRAM 之后，强制覆盖 WRAM 中的角色属性为最大值。这样模板表始终保持原版安全值，剧情脚本重读时读到的是正常数据。

7. 三阶破解的递进关系

每一阶突破都建立在前一阶对游戏机制理解的基础上：

  • 一阶的核心是写入时间线（addMemoryCallback 全量捕获 + 时间线比对）与 LoROM 映射换算；
  • 二阶的核心是识别”改模板”方案的陷阱——模板数据被剧情脚本重读，修改模板会导致后续事件崩溃，解决方法是改代码而非改数据；
  • 三阶的核心是用运行时快照对比定位正确槽位——通过 Lua 脚本监控角色加入前后的 WRAM 变化，避免了错误推测。

8. 遇到的问题

8.1 初始内存残留脏数据

新游戏复位后金币地址上不是 0，而是上次运行的残留值（如 1457251158），差点把残留值当成”游戏内实际金币”去追来源。解决：先完整跑一遍新游戏流程，看金币何时归 0，再追写入。

8.2 写回调去重漏掉”重复写 0”

第一次写监控只记录”值变化”，初始化零填充写 0 时金币本来就是 0，被直接跳过，导致找不到初始化写入点。解决：改为记录窗口内所有写入（不判变化），虽然日志量大，但完整无遗漏。

8.3 LoROM 高速库/慢速库镜像换算

一开始用 文件偏移 = CPU库 * 0x8000 换算，把 $96:F9C9 算到了 4MB 文件之外，报 IndexError。实际 LoROM 4MB 下正确公式是 (CPU库 & 0x3F) * 0x8000 + 0x200 + (地址 - 0x8000)。

8.4 磁碟机头偏移

发现文件带 512 字节 GAME DOCTOR SF 3 头后，所有 file offset 都要再加 0x200。初期的地址换算错误正是漏掉了这一层。

8.5 反汇编脚本 imm 模式 bug

自写 dis65816.py 一度把 imm 寻址误设为 2 字节操作数，导致所有 LDA #$xx 等立即数指令反汇编错位，后续指令全部错乱。修复：imm 应为 1 字节操作数。

8.6 模板位置初次算错

机械师模板最初被标在 file 0xB7C3C，与实际 0xB7C3A 差 2 字节，导致解析出的字段全部错位。最终以”模板1 起点 + 15 字节步长”重新推导出三模板位置。

8.7 修改模板导致红坦克剧情黑屏

第一次尝试直接修改模板数据，主角建号后满值正常，但推进到红坦克剧情时黑屏死机（CPU 卡在存档亮度闪烁循环 $96:F246）。根因：剧情脚本重读模板数据，满值导致计算溢出。解决方案：改代码不改模板，在 WRAM 层面覆盖值。

8.8 错误推测槽位间距（0x1C0）

最初假设三个角色槽位间距为 0x1C0（$7E8000、$7E81C0、$7E8380），在三槽位版中写入 $7E81C6 后，导致红坦克消失（写入了坦克数据区）。通过 Lua 快照对比确认实际间距为 0x100（$7E8000、$7E8100、$7E8200）。

8.9 格斗家模板靠结构推断

模板3 是唯一没有逐字节实证的定位（当时还没遇到格斗家加入）。证据链是：连续排列 + 结构同构 + 职业标识 03。最终通过运行时扫描确认槽位为 $7E8200。

8.10 旧存档中的角色不会自动刷新

模板修改只影响新加入/重新初始化。如果使用旧 savestate 加载，已存在的角色仍是原值，需新开档（或运行期 Lua 改 WRAM）验证。

8.11 校验脚本读错文件

验证补丁时一度打开的是未打补丁的 0.6.SMC，打印出的模板1 还是原值，险些误判补丁未生效。解决：每次读文件前先打印文件路径 + 目标区域前 N 字节，确认读的是正确的文件。

9. 总结与心得

  1. “值变化”不等于”写入”：初始化写 0 是最容易被去重逻辑漏掉的写入，全量捕获才能建立完整的写入时间线。

  2. 先摸清写入时间线，再选补丁点：金币在帧 10580 被初始化归零、帧 14652 才被玩家拾取，这中间是安全窗口。选”最后一次初始化写入之后、玩家操作之前”的点位，补丁才不会被覆盖。

  3. 函数复用是破解的双刃剑：新游戏/读档共用 $96:F8B9，既是”打一处补丁即可”的幸运，也是”读档也会触发”的隐患。判断清调用顺序，隐患就变成特性。

  4. LoROM 映射 + 磁碟机头是 SFC 破解的入场券：0x200 头偏移和高速库/慢速库换算必须一次算对，否则后面全盘皆错。

  5. 改代码不改数据，更安全：直接修改模板数据看似简单，但若游戏逻辑在后续事件中重读模板，会导致崩溃。改为注入代码在运行时覆盖 WRAM，将修改与游戏数据彻底隔离。

  6. 运行时快照对比是最可靠的定位手段：反汇编难以定位的槽位、数据表，通过 Lua 脚本在模拟器中对比”加入前/加入后”的 WRAM 快照，能精确锁定变化点。

  7. 保留”角色标识”和”攻守派生”字段：职业标识（02/01/03）决定角色种类，攻守由腕力/体力派生，修改这些字段要么破坏角色，要么过度影响平衡。只改 LV/技能/HP 即可达到”满级”效果。

  8. 最小改动 + 可验证：金币阶段只改 4 字节跳转 + 23 字节 stub；角色阶段扩展 stub 至 111 字节；每步都用 diff 确认改动范围，用快照对比验证效果。

  9. 存读档一致性靠”复制覆盖”而非”绕过”：利用读档例程 MVN $7E,$70 的整块覆盖，让存档数据天然压过模板值。
