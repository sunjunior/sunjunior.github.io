3. MAME 目录结构

MAME 的配置文件搜索路径由 inipath 控制。默认 inipath 为 $HOME/.mame/ini。

3.1 关键陷阱：plugin.ini 位置

MAME 的 plugin.ini 读取路径是 inipath 目录，而不是 $HOME/.mame 根目录。如果误放根目录，inputmacro 插件完全不会被加载，但游戏本身运行正常。这会导致”游戏正常、宏不生效”的假象，且日志无任何报错。

验证方法：启动时加 -verbose，查看日志中是否有 Starting plugin inputmacro...。

修复：mv ~/.mame/plugin.ini ~/.mame/ini/plugin.ini

7. 关键技术要点

7.1 delay 与 duration 的配合

delay: 2, duration: 1 的效果：先空等 2 帧 → 激活输入 1 帧 → 进入下一步。这相当于在方向切换之间插入了一个空白间隔，避免前后方向重叠，让游戏的方向检测器能清晰分辨每个输入。

7.2 set_value 的一帧延迟

field:set_value() 在帧处理期间写入，游戏在同一帧读取时还看不到更新。duration: N 实际生效为 N-1 帧。建议 duration ≥ 2 或结合 delay 使用。

7.3 指令窗口与动作时长

乾坤波动功共 8 段方向，如果每段用 duration: 8，总时长约 1.1 秒，游戏的方向输入缓冲窗口可能放不下，开头的方向会被丢弃，导致宏被识别为较短的指令（如 ↓↘→+A 气功波）。

解决方案：压缩每段到 1 帧，配合 delay: 2 间隔，总时长约 0.5 秒，既保证方向清晰可辨，又不会超出缓冲窗口。

9. 踩坑记录

坑 1：plugin.ini 位置错误

现象：游戏正常、宏不生效，日志无插件报错。

原因：plugin.ini 放在了 ~/.mame/plugin.ini，但 MAME 从 inipath（~/.mame/ini/）读取。

验证：-verbose 日志中没有 Starting plugin inputmacro...。

坑 2：插件退出时覆盖配置文件

现象：手动修改了 .cfg 文件，重启游戏后修改被还原。

原因：inputmacro 插件在游戏退出时执行 save_settings，将内存中的宏写回 JSON 文件，覆盖了磁盘上的修改。

预防：修改配置文件前，确保没有 MAME 进程在运行。

坑 3：宏步骤太长导致输入缓冲溢出

现象：8 段方向的宏（如 ←↙↓↘→←→）只触发了前半段的指令（如 ↓↘→+A 气功波）。

原因：游戏的方向输入缓冲窗口有限，动作太慢导致开头方向被丢弃。

修复：压缩每段到 1 帧，配合 delay 间隔保持总时长在缓冲窗口内。

坑 4：SIGKILL 导致日志缓冲丢失

现象：-verbose 日志在 pkill -9 后只剩前几十行，看起来像卡住了。

原因：SIGKILL 不会刷新 C 标准库的 stdout 缓冲。

修复：正常退出（ESC）而非 SIGKILL。

坑 5：窗口模式下 Lua 探针 GC 问题

现象：emu.add_machine_frame_notifier 注册的帧回调在 ~70 帧后停止调用。

家里那台电动自行车，平时在小区充电桩充电——桩是按时长计费的（比如 2 元/3 小时），回老家在插座上充是包月，商场快充又按度数计费。同样是「充满一次电」，三种场景的成本差异巨大，而我完全说不清自己的车每公里到底花多少钱、百公里耗几度电、电池用了两年还剩几分健康度。

油车的油耗记录有「小熊油耗」这样成熟的应用，但电动自行车领域一直没有趁手的工具。市面上的充电类 App 要么绑定特定运营商的桩，要么只有记金额没有算电耗。于是决定自己写一个：VoltTrack，一款纯本地的电动自行车电耗记账 App。本文记录从需求梳理、算法设计到工程实现、发布安装的完整过程。

项目已开源：github.com/sunjunior/volttrack，本文全部代码与交付件（含可下载的签名 APK）均可在仓库及其 Releases 页面获取，协议 MIT。

需求梳理：MVP 只做核心闭环

先明确用户故事：记录每一次充电（金额、时长、电量），自动算出百公里电耗、每公里成本、续航预测和电池健康度。据此划定 MVP 四个模块：

  1. 车辆与电池档案——车辆信息 + 电池组（支持更换历史，同一时刻只有一块「生效电池」）；
  2. 充电记账与日志——三种计费模式的记账向导 + 记录列表（可删除）；
  3. 电耗分析与算账——百公里电耗、每公里成本、续航预测、SOH 电池健康度、续航达成率；
  4. 辅助工具——充电费用计算器（对比「按时长档位」与「按度计费」两种桩，算出哪种更省）。

社区分享、云同步、保养提醒这些后置——MVP 阶段它们只会稀释核心价值。

核心算法：把「充电」变成「事件流」

这是整个应用最有技术含量的部分。难点在于：充电记录里往往没有度数（小区桩按时长计费，你只知道充了 2 小时花了 4 块钱），而且不是每次充电都骑到没电，「这一箱电骑了多远」没有天然的边界。

事件流 + 里程窗口

设计上把每次充电当作事件流中的一条记录，其中带里程的记录（顺手记一下当前里程表读数）充当锚点。相邻两个锚点 A→B 构成一个「窗口」：

几个容易忽略的口径细节（都踩过坑）：

  • 区间取 [t_A, t_B)：起点 A 的充电归属本段骑行，终点 B 的充电归属下一段，保证每条记录只归属一个窗口、不重不漏；
  • SOC 取「到达电量」（即各记录的 socBeforePct），而不是「充后电量」；
  • 两锚点都填了到达电量才启用 ΔSOC 校正，否则退化为 E_ride = Σ充入度数——数据不完整时宁可用粗口径，也不拒绝服务。

用设计文档里的样例验证一下：48V20Ah 电池（0.96 kWh），在里程 1000km 处充 0.72 度（SOC 30%→100%），骑到 1060km 处剩 45%：

0.96 度/百公里，正好在电动自行车 0.8～1.5 的合理区间——公式闭环。

三种模式的度数推算

「充电充了多少度」按模式各有推算优先级：

模式 推算优先级
按度/金额 手输度数 → 金额 ÷ 单价
按时长 功率(W) × 时长(h) ÷ 1000 × 效率系数（默认 0.85）
家用插座 有前后 SOC → ΔSOC × 容量 ÷ 效率（反推）→ 手输估算

其中充电效率系数 0.85 是关键参数：充电器不可能把市电 100% 灌进电池，发热、浮充都有损耗。按时长模式下 300W 充 2 小时，实际入电池的是 0.51 度而不是 0.6 度。

SOH 与续航预测

  • 电池健康度 SOH：只取「低电量（≤10%）→ 充满（≥95%）」的完整充电事件，实际充入 ÷ 理论容量。随用随充的碎片化补电会污染估算，必须设门槛；
  • 续航预测：当前SOC × 容量 × 0.9（保守系数） ÷ 加权平均电耗；
  • 续航达成率：满电→低电窗口的平均实际续航 ÷ 电池档案里的官方续航——这是感受电池衰减最直观的指标。

工程实践：子代理驱动开发（SDD）

这次实现采用了一种有意思的工作流：计划先行 + 子代理驱动。先把 15 个任务写成带完整代码骨架的实现计划（每个任务都有失败测试→实现→提交的 TDD 步骤），然后每个任务派给一个全新的 AI 子代理执行，任务完成后由另一个独立子代理做「规格合规性 + 代码质量」双维度审查。

几个数据点：

  • 15 个任务全部通过任务级审查，其中 3 个任务审查发现了测试缺口，由修复子代理补齐（还做了变异测试验证——故意把实现改错，确认新测试真的能抓到）；

踩坑记录

  • flutter doctor 报 license status unknown：新版 Android cmdline-tools 的 sdkmanager --licenses 输出变了，flutter 解析不到期望的确认文案。换装旧版 cmdline-tools 12.0 后正常；
  • drift 内存库测试挂起：addTearDown(db.close) 会因 drift 内部的 pending timer 让 widget 测试超时，把 await db.close() 挪到测试体内即可；
  • riverpod 2.6 的 AsyncValue.guard 返回 Future：不能同步 return 进 Provider 体，需改用 try/catch 手工构造 AsyncValue；
  • drift 生成类遮蔽核心模型：Batteries 表生成的数据类叫 Battery，和 core 里的领域模型 Battery 同名，消费方一律用 drift 类型，容量计算收敛到一个 extension 上避免五处复制；
  • 荣耀手机 adb 连不上：荣耀新机型 USB 厂商 ID 是 339b，不在 android-udev 包的规则表里（只收录了老华为 12d1），需要自定义 udev 规则授权；另外荣耀在「仅充电」模式下不暴露 ADB 接口，要切到「传输文件」模式。

4.2 步长之谜与 $B196（关键辨析）

字段并非统一 2 字节步长：16 位字段（体力/法力/力量/体能）步长 2（基址+2X），1 字节字段（等级/敏捷/精神）步长 1（基址+X）。若误把敏捷当成 2 字节，记录块就会出现”假空洞”。

破解这个谜的关键证据链：

  1. 记录块完美打包：64 字节无缝填满，反推敏捷/精神必须是步长 1（若步长 2 会与体能 $0538+2X 重叠）。
  2. 升级成长块（prg 0x5B2C1）里，16 位字段用 ADC $0514,X / STA $6964,X / STA $0538,X（步长 2），1 字节字段 ADC $0534,X（步长 1）——同一 X 前后语义不同。
  3. JSR $B196 是换算桥：升级成长块和状态面板在访问单字节字段之前都调用 $B196，把 X 从”双字节步长（角色×2）“换算成”单字节步长（角色）“。

由此确认状态面板”一屏多栏、左→右 = 哪吒/小龙女/杨戬/姜太公”正是 X=0/1/2/3。

4.4 银两机制

银两是 24 位二进制小端，$0501 低位、$0502 中位、$0503 高位：60000 = $EA60 = $0501=$60, $0502=$EA。

银两初始为 0 的来源有两层：

  1. 引导批量清零：开机例程（prg ~0x0130 起）用 Y 索引循环把 RAM 和电池 WRAM 清成 0，$0501-$0503 自然为 0。
  2. 新游戏初始化（prg 0x037C2）：原本对银两没有任何显式写入——银两初始值完全靠”开局前无人改过它”来保证。

侧面佐证：ROM 中存在两处调试遗留代码（prg 0x106F2 与 0x1D281），把银两设置为 $0F423F = 999999 后 RTS，但没有任何调用点——开发期用来测试商店的死代码，恰从反面证明”游戏靠写内存改银两、不靠硬编码”。

9. 踩坑与经验总结

  1. 多源交叉验证 > 单一证据：初始化 + 升级 + 入队 + 社区金手指多路互证，才能确定宽度混排的记录块。
  2. “完美打包”是解析记录块的利器：连续字段总宽度必须无缝填满整个块，出现”假空洞”说明某字段宽度猜错了。
  3. bank 切换游戏必须定基址：用”内部交叉引用自洽”而非猜测窗口，差一个窗口就是 0x2000 的偏移。
  4. 共享代码区要查子程序入口：整体重排前必须全 ROM 扫 JSR/JMP 引用，否则会破坏入口指令边界（本次旧版就踩过）。
  5. 跨 bank 引用有假阳性：JSR $B801 可能指向其它 bank 在 $A000 的同地址代码；用”该地址在原版是否是指令起点”判定真伪。
  6. 补丁后必须重跑模拟器/反汇编追寄存器：A=$03 的致命假设就是被这步抓出来的。
  7. 字节预算问题的本质是代码而非数值：16 位存储完全支持 >1000；卡住的是”初始化代码没写那些字节、又没空闲”，需新增指令。
  8. 空闲区要全 ROM 扫描引用：看着是 $00 的空洞可能是 66 处指针引用的数据表。
  9. 单字节字段有硬上限：敏捷/精神钳 $FF=255，这是游戏机制，改 ROM 也突破不了。
  10. 冗余指令/开机清零覆盖的写是腾挪金矿：等级清 $0504/$0505 等冷启动本就为 0，删掉不损失功能。
  11. ROM 补丁 ≠ 旧存档：补丁只改初始化，读旧 state 不会重跑；需要时用 Lua 临时改 RAM。
  12. 最终防线是全量字节差异审计：逐字节对比确认改动面=预期补丁集，杜绝杂散写入。

8. 踩坑与经验总结

  1. FME-7 的 bank 映射复杂性：不同于 MMC3 的 16KB bank，FME-7 使用 8KB bank 粒度，且 $E9 的高位可能有特殊含义（RAM 模式等）。反汇编时务必确认正确的 bank 映射。

  2. 存档对比的噪声问题：直接对比两个 savestate 会引入大量噪声（游戏世界状态变化）。实时监控脚本比存档对比更精确，能捕捉到伤害发生的瞬间。

  3. SBC 寻址模式多样：前 3 处伤害代码用 SBC #imm（立即数），第 4 处用 SBC $zp（零页寻址）。静态扫描 SBC #imm 会遗漏 SBC $zp，需要动态写跟踪来补全。

  4. emu.getKeyState() 在 Mesen2 中的局限性：键盘键被映射到手柄后，Lua 的 getKeyState() 可能无法正常检测。改用 emu.getInput(0) 检测手柄按键更可靠。

  5. emu.loadSavestate 必须在回调中调用：loadSavestate 只能在 addMemoryCallback（exec/write/read）内调用，不能在 addEventCallback 中直接调用。常用技巧：在 NMI 入口 $E1D0 设置 exec 回调。

  6. POWER 显示值与存储值的关系：显示 POWER ×10 = 存储值（80000 显示 = 8000 存储）。这个缩放关系意味着 16 位值已足够存储（最大 65535 ×10 = 655350），不需要 3 字节。

8. 遇到的问题

8.1 初始内存残留脏数据

新游戏复位后金币地址上不是 0，而是上次运行的残留值（如 1457251158），差点把残留值当成”游戏内实际金币”去追来源。解决：先完整跑一遍新游戏流程，看金币何时归 0，再追写入。

8.2 写回调去重漏掉”重复写 0”

第一次写监控只记录”值变化”，初始化零填充写 0 时金币本来就是 0，被直接跳过，导致找不到初始化写入点。解决：改为记录窗口内所有写入（不判变化），虽然日志量大，但完整无遗漏。

8.3 LoROM 高速库/慢速库镜像换算

一开始用 文件偏移 = CPU库 * 0x8000 换算，把 $96:F9C9 算到了 4MB 文件之外，报 IndexError。实际 LoROM 4MB 下正确公式是 (CPU库 & 0x3F) * 0x8000 + 0x200 + (地址 - 0x8000)。

8.4 磁碟机头偏移

发现文件带 512 字节 GAME DOCTOR SF 3 头后，所有 file offset 都要再加 0x200。初期的地址换算错误正是漏掉了这一层。

8.5 反汇编脚本 imm 模式 bug

自写 dis65816.py 一度把 imm 寻址误设为 2 字节操作数，导致所有 LDA #$xx 等立即数指令反汇编错位，后续指令全部错乱。修复：imm 应为 1 字节操作数。

8.6 模板位置初次算错

机械师模板最初被标在 file 0xB7C3C，与实际 0xB7C3A 差 2 字节，导致解析出的字段全部错位。最终以”模板1 起点 + 15 字节步长”重新推导出三模板位置。

8.7 修改模板导致红坦克剧情黑屏

第一次尝试直接修改模板数据，主角建号后满值正常，但推进到红坦克剧情时黑屏死机（CPU 卡在存档亮度闪烁循环 $96:F246）。根因：剧情脚本重读模板数据，满值导致计算溢出。解决方案：改代码不改模板，在 WRAM 层面覆盖值。

8.8 错误推测槽位间距（0x1C0）

最初假设三个角色槽位间距为 0x1C0（$7E8000、$7E81C0、$7E8380），在三槽位版中写入 $7E81C6 后，导致红坦克消失（写入了坦克数据区）。通过 Lua 快照对比确认实际间距为 0x100（$7E8000、$7E8100、$7E8200）。

8.9 格斗家模板靠结构推断

模板3 是唯一没有逐字节实证的定位（当时还没遇到格斗家加入）。证据链是：连续排列 + 结构同构 + 职业标识 03。最终通过运行时扫描确认槽位为 $7E8200。

8.10 旧存档中的角色不会自动刷新

模板修改只影响新加入/重新初始化。如果使用旧 savestate 加载，已存在的角色仍是原值，需新开档（或运行期 Lua 改 WRAM）验证。

8.11 校验脚本读错文件

验证补丁时一度打开的是未打补丁的 0.6.SMC，打印出的模板1 还是原值，险些误判补丁未生效。解决：每次读文件前先打印文件路径 + 目标区域前 N 字节，确认读的是正确的文件。

9. 总结与心得

  1. “值变化”不等于”写入”：初始化写 0 是最容易被去重逻辑漏掉的写入，全量捕获才能建立完整的写入时间线。

  2. 先摸清写入时间线，再选补丁点：金币在帧 10580 被初始化归零、帧 14652 才被玩家拾取，这中间是安全窗口。选”最后一次初始化写入之后、玩家操作之前”的点位，补丁才不会被覆盖。

  3. 函数复用是破解的双刃剑：新游戏/读档共用 $96:F8B9，既是”打一处补丁即可”的幸运，也是”读档也会触发”的隐患。判断清调用顺序，隐患就变成特性。

  4. LoROM 映射 + 磁碟机头是 SFC 破解的入场券：0x200 头偏移和高速库/慢速库换算必须一次算对，否则后面全盘皆错。

  5. 改代码不改数据，更安全：直接修改模板数据看似简单，但若游戏逻辑在后续事件中重读模板，会导致崩溃。改为注入代码在运行时覆盖 WRAM，将修改与游戏数据彻底隔离。

  6. 运行时快照对比是最可靠的定位手段：反汇编难以定位的槽位、数据表，通过 Lua 脚本在模拟器中对比”加入前/加入后”的 WRAM 快照，能精确锁定变化点。

  7. 保留”角色标识”和”攻守派生”字段：职业标识（02/01/03）决定角色种类，攻守由腕力/体力派生，修改这些字段要么破坏角色，要么过度影响平衡。只改 LV/技能/HP 即可达到”满级”效果。

  8. 最小改动 + 可验证：金币阶段只改 4 字节跳转 + 23 字节 stub；角色阶段扩展 stub 至 111 字节；每步都用 diff 确认改动范围，用快照对比验证效果。

  9. 存读档一致性靠”复制覆盖”而非”绕过”：利用读档例程 MVN $7E,$70 的整块覆盖，让存档数据天然压过模板值。

6. 阶段一：无限生命补丁（遇敌死亡不减少命，但仍需重开本关）

破解的难点不在”改哪”，而在”找到哪”。本阶段按真实排查顺序展开：现象 → 定位生命数据 → 定位扣命代码 → 动态验证 → 方案选型 → 落补丁 → 复验。

6.1 现象与破解思路

现象：遇敌死亡后 HUD 命数 -1，减到 0 即 GAME OVER 回标题。

思路：所谓”扣命”在 6502 上就是一段确定的数据操作——某条指令把”生命数”这一内存字节减 1。因此破解拆成两步，缺一不可：

  1. 数据定位：生命数存在哪个内存地址？（找出”什么在变”）
  2. 代码定位：是谁把它减 1？（找出”谁在改”）

只用静态手段不够：反汇编能列出”所有可能改这个地址的指令”，但静态存在 ≠ 实际执行；只用动态手段也不够：内存监听要先知道听哪个地址。所以是静态扫描 + 动态验证双管齐下，互相印证。

6.2 数据定位：快照差分锁定 $007C

进入真实可玩关卡（进入方法见 §5.1，这是本作最坑的一步）后，先快照全 RAM，再人为触发一次死亡，再快照，对两张快照做差分——变化的字节就是”死亡事件相关状态”。

差分结果：生命数 = 零页 $007C（初始 5，死亡后 5→4）。同时顺带摸清了玩家实体布局：

RAM 含义

$0500 玩家对象，bit7=存在（$80）
$0501 / $0502 玩家 X 低 / 高
$0503 玩家 Y

死亡时序（实测）：清零 $0500 强制死亡 → 约 30 帧后扣命才执行 → $7C 5→4。扣命不是瞬时的，说明死亡有一个”结算阶段”。

6.5 方案选型：为什么是 NOP 掉 DEC，而不是改别的

候选方案对比：

方案 改动 效果 评价
a. 改 $C120 BEQ 跳转 永远跳过 GAME OVER 不 GAME OVER，但命照扣 不彻底
b. DEC $7C → EA EA 扣命失效 $7C 恒 5，GAME OVER 天然不可达 ★ 采用
c. 初始生命设很大 改 $C032 的 A9 05 治标不治本，早晚扣光 不干净

选 b 的三个理由：

  • 同位替换、无需搬移：C6 7C（DEC 零页）是 2 字节，EA EA（NOP NOP）也是 2 字节，同长度原位替换，不改变后续任何跳转目标；
  • 保留后续判定、逻辑最干净：$C11E LDA / $C120 BEQ 原样保留——因为 $7C 恒等于 5，BEQ（判 0）永不成立，GAME OVER 分支（$C129）静态上还在、运行上永远不可达，误伤最小；
  • 只掐”扣”不碰”加”：初始化（$C032）、+1 道具（$C145）、奖励关 +3（$C15C）全部保留，正常奖励机制不受影响。
文件偏移 PRG 偏移 CPU 地址 原字节 新字节 效果
0xC12C 0xC11C $C11C C6 7C EA EA 扣命失效，生命恒为 $05

7. 双保险：Mesen 作弊码

7.1 原理

Mesen 的 NesCustom 作弊码格式为 AAAA:VV（地址:值），实现方式是拦截对指定地址的读取，一律返回设定值。配合”从源头 NOP 掉扣命写”的 ROM 补丁，即便将来发现漏网的分支，作弊码也能兜底。

作弊码：007C:05（生命数读取恒为 5）。

7.2 读取路径的坑（重要）

Mesen Lua 对同一地址存在两条读取路径，结果可能不同：

API 路径 是否经过作弊码
emu.read(addr, emu.memType.nesInternalRam) 直接读 RAM 缓冲 否（绕过）
emu.read(addr, emu.memType.nesMemory) (= 8) 走 DebugRead → 内存管理器 是

实测：作弊码生效时，游戏读 $7C 恒为 $05，而 nesInternalRam 读到的是真实 RAM 值（被扣到 $04）。因此：

  • 验证作弊码是否生效要用 nesMemory；
  • 观察真实生命要用 nesInternalRam（两者对照即知”作弊层是否真的在兜底”）。

11. 阶段二：优化为遇敌不死 + 原地复活（Respawn In Place，4 秒无敌）

11.1 目标与破解思路

§9.5 已确认阶段一的补丁行为是”死后重开本关”。本阶段实现更友好的玩法：玩家阵亡后不重开本关，在当前画面原地复活（保留死亡时的位置与关卡状态），并给予约 4 秒无敌时间（复活瞬间的敌人不会立刻再杀死你）。

11.3 补丁设计与 Handler 逻辑

  • Hook：CPU $D1B6（文件偏移 0xD1C6）6 字节改为 4C 71 EB EA EA EA（JMP $EB71 + 3×NOP）。

Handler 逻辑（X = 对象索引，来自 $D1B6 进入时的 LDX）：

玩家分支共 37 字节，敌人分支 6 字节，总计 43 字节。

  • CPX #$00 区分玩家与敌人：$D1B6 进入时 X = 对象索引（0=玩家）。玩家分支恢复”存在”，敌人分支保留”清除”——否则敌人也会原地复活、永远打不死；
  • $0500 = $80：把对象状态从”死亡（被清零）“恢复为”存在（bit7）“，这是”复活”的实质；
  • 清 $050C-$0511：死亡动画残留的相位/位移数据在复活后无意义，统一清零，避免脏状态（$0510 是死亡相位计数器）；
  • $0512 = $20：坑 2 的修复，见 §11.4；
  • $0515 = $FF：无敌计时器 ≈ 4.27 秒，见 §11.5。

11.4 两个关键坑（都靠真实复现逼出来的）

坑 1：handler 必须放在固定 bank 3。 最初把 handler 塞进当前代码区尾部（会参与 bank 切换的 bank），结果是：玩家死亡 → JMP 进 handler → 途中 MMC1 切换 PRG bank → handler 字节立刻变成另一 bank 的数据 → 直接花屏/崩溃。改成固定 bank 3 的 $FF 区后消失。同理 hook 本身必须落在 bank 3（$D1B6 天然在 bank 3，$C000-$FFFF），所以 JMP $EB71 两段都永不被切走。

12. 阶段三：修复复活后 BGM 缺失

阶段二引入了新 bug：复活后 BGM 永久消失。这是三阶段里最难的一环——它逼着我们真正吃透这个游戏的 MMC1 bank 切换与音乐子系统。按”现象 → 音乐系统逆向 → 失败实验复盘 → 自动续播为何不可行 → 最终方案 → 验证”展开。

12.1 现象与破解思路

现象：阶段二的”原地复活”补丁让 BGM 在复活后永远消失。

为什么消失：原版只在”Game Over → 重新加载当前关”的流程里才会重启 BGM（$C01A → $F185 #26 → 切到 bank 2 的 $8DEA → JSR $F7A2 播放 9 号轨道），而原地复活完全绕过关卡重载，自然没有重启音乐的地方。

思路：在 handler 里主动补一次”播放 BGM”。但”JSR 一个播放函数”看似简单，其实踩了两个雷：bank 映射与bank 栈平衡。要做得对，必须先逆向清楚三件事：

  1. 9 号轨道（BGM）的数据在哪、怎么指向它；
  2. 播放入口是哪个、内部做了什么；
  3. 为什么从主循环上下文直接调用会坏。

12.4 失败实验：为什么 JSR $F7AF 会崩

第一次尝试在 handler 里写 LDA #$09; JSR $F7AF（48 字节版 “Respawn Music”），结果复活流程陷入无限循环（Mesen 实测：f15046 之后一直 RESPAWN，无法继续）。复盘有两条根因，一条是 bank 映射，一条是 bank 栈：

  1. 读错 bank：$F7E6 用 $3D/$3E=$9E00 查轨道表时，bank 2 没有映射在 $8000（游戏主循环跑的是 bank 0/1 的数据），读到的是垃圾 → $45=$0000（正常应为 $ADB4）。
  2. bank 栈失衡：$F7AF 尾部的 $F146 pop 了一个没人 push 过的 bank 栈槽位，把垃圾写进 CPU 栈返回地址 → 返回后 PC 跑到未知位置 → 崩溃/循环。

12.5 为什么”只设 $3A“也救不了（自动续播不可达）

或许有人会想：直接写 $3A = 9 让”正在播放曲目号”等于 9，游戏会不会自动续播？答案是不会。全 ROM 搜索证实：$F7CC 的 3 个调用点（$F9A4 / $FA29 / $FB17）全部来自活动槽位的步进完成路径（$F93D / $F9DF / $FACC 的 BCS）。槽位全空时这 3 个点根本执行不到。所以原地复活时只把 $3A=09 设为”想播 9 号”，永远不会触发播放——必须显式调用播放入口。

12.6 最终修复：换对入口 $F7A2（共 2 字节）

核心改动：JSR $F7AF → JSR $F7A2

handler 的”播放音乐”段从 LDA #$09; JSR $F7AF 改成 LDA #$09; JSR $F7A2。$F7A2 内部会替我们完成：

  1. push 当前 bank → 切到 bank 2；
  2. 播放 9 号轨道（$44=9，因 $3A!=9 故 DEC $44→8 → $F7E6 查表得到 $ADB4）；
  3. 轨道数据首字节 01 → init_song → $3A=$44+1=9；
  4. pop bank 栈 + 恢复原 bank → 干净地返回。

整条链自洽，无需手工设 $3A。

13. 综合关键技术结论

阶段一（无限生命）：

  1. 生命地址 $007C：零页一字节，初始 5，死亡递减，归零进 GAME OVER。
  2. 唯一扣命点 $C11C：全 64KB PRG 仅 1 处 DEC $7C（比蝙蝠侠的 5 处简单得多），NOP 掉即无限生命。初始化/奖励写点全部保留。
  3. NOP 的粒度：只 NOP 掉 DEC 一条，保留其后 LDA/BEQ 判定——生命恒 5，GAME OVER 分支天然不可达。
  4. 进入真实关卡是最难的环节：本作标题/菜单/关卡牌是多级输入状态机，需要 $7C==5（菜单确认）+ $0500 bit7（玩家生成）双 RAM 状态判定，逐级注入输入。
  5. endFrame 里 PC 采样不可用：恒为 NMI 等待点 $EED5，必须改用 RAM 状态判定。
  6. 输入注入必须放 inputPolled 回调，直接 setInput 会被每帧覆盖。
  7. 作弊码读取路径分叉：验证作弊必须走 nesMemory，原始 RAM 读取会绕过。
  8. testRunner 不自动加载作弊文件：无头验证用 emu.addCheat 显式注入。
  9. --timeout=0 会瞬间停模拟器，脚本根本跑不起来，这是最常见的假”失败”。

阶段二（原地复活）：

  1. 死亡会重开本关而非原地续命（阶段一行为）：死亡 → $C11C DEC → JMP loc_C04B_loop → 关卡牌脚本 → 重新加载当前关；阶段一只消除 Game Over 与扣命，不改变”死后重打本关”机制。
  2. 死亡终结点只有一个 $D1B6：玩家与敌人的”死亡动画结束 → 对象清除”都汇聚于此，接管它即可拦截一切死亡。
  3. hack 代码必须放固定 bank 3：MMC1 bank 切换会把”散落在可切换 bank 里的 handler”瞬间换成别的字节，必须占用 $C000-$FFFF（固定 bank）的空闲区。
  4. 复活后不能动 = 输入门控问题：sub_C1A8 只在 16px 对齐或 $0512 bit5 置位时才把方向输入写进 $050B；死亡击退会打破对齐，复活 handler 必须显式置 $0512=$20，否则玩家冻结。
  5. 原地复活自带无限生命：扣命只发生在关卡重载循环 $C11C，原地复活不重载关卡 → 永不扣命，无需叠无限生命补丁。
  6. 死亡判定要写 (state & $A0) == $A0：本作死亡态可能是 $A0 或 $A4，只判 == $A0 会漏检。
  7. 无头模式下截图用 emu.getScreenBuffer()：emu.takeScreenshot() 在 --testRunner 下无视频渲染器会静默失效；getScreenBuffer() 返回 ARGB 缓冲可正常 dump（respawn_screen.lua）。

阶段三（BGM 修复）：

  1. bank 映射是 MMC1 游戏改动的第一前提：任何跨 bank 调用都要先确认目标 bank 在不在 $8000。本次 TBL[0000,...] 即”bank 2 没映射”的直接证据。
  2. $F7A2 才是 play_music 的完整入口，$F7AF 只是半截——它依赖调用方已经做过 $F129（push + 切 bank）。直接 JSR $F7AF 会 bank 栈失衡，$F146 把垃圾写进 CPU 返回地址 → 复活循环崩溃。
  3. 自动续播 $F7CC 救不了原地复活：它的 3 个调用点全在”活动槽位步进完成”路径，槽位全空时永远执行不到。想播歌必须显式调播放入口。
  4. NMI 音乐处理自带 bank 2 映射（$F8E2 JSR $F138），但游戏主循环上下文没有——handler 里的音乐调用必须自己负责 push/pop。
  5. $F7A2 用 A=9 播放 9 号轨道：$3A!=9 → $44=9 DEC→8 → $F7E6 查表得 $ADB4 → 数据首字节 01 → init_song 设置 $3A=9。整条链自洽，无需手工设 $3A。
  6. 修复共 2 字节：0xEBA8: AF→A2（换入口）+ 0xEB84: 28→26（修 BNE 目标）。
  7. 验证签名与”原版死亡→重开”完全一致：$3A=09/$44=08/$45=$ADB4/p1bgm=80，BGM 复活后持续播放至 AFTER+100，无崩溃。
  8. 写回调里拿不到 PC（emu.getCpuState() 返回 nil），必须用 RAM 状态判定；APU 写入时间线（music_trace2.lua）则可在 endFrame 里配合 getCpuState 记录。

蝙蝠侠（NES / FC）无限生命 Hack 技术文档

发表于 2026-08-02 更新于 2026-09-03

目标游戏：Batman (U) (Sunsoft, 1989) 目标：修改 NES ROM，使玩家在游戏中永远不会掉血（无限生命 / Infinite Health） 交付物：打补丁的 ROM、IPS 补丁、Mesen2 作弊码（双重保险） 日期：2026-08-01

1. 背景与目标

《蝙蝠侠》是 Sunsoft 于 1989 年推出的 FC/NES 横版动作游戏。玩家操控蝙蝠侠闯关，生命值（体力）随被敌人攻击而减少，归零即死亡。

本次任务的破解目标非常具体：

  1. 找到控制生命值的 RAM 地址。
  2. 定位所有”扣血”的代码位置。
  3. 修改 ROM，使扣血逻辑失效（无限生命）。
  4. 提供可直接使用的交付物：
    • 已打补丁的 ROM 文件；
    • 标准 IPS 补丁（可分享、可校验）；
    • 一套不依赖改 ROM 的 Mesen 作弊码作为”双保险”。

最终成果：玩家无论如何挨打，生命值始终保持满格 $08。

2. ROM 与游戏信息

项目 值
文件名 Batman (U).nes
文件大小 262,160 字节
MD5 62da40d0eafa92d8e4e17612bfd6ff7f
iNES Header 4E 45 53 1A 08 10 41 00 ...
格式 iNES，Mapper 4（MMC3），垂直镜像
PRG ROM 0x08 × 16KB = 128KB（0x20000 字节）
CHR ROM 0x10 × 8KB = 128KB（0x20000 字节）

关键地址约定

  • PRG 偏移：指相对 PRG 数据起始（文件偏移 = PRG 偏移 + 16 字节 iNES 头）。
  • MMC3 采用银行切换（bank switching），CPU 地址空间 $8000-$FFFF 由多个 bank 映射。同一条指令在不同时刻可能处于不同的 CPU 地址上，因此以 PRG 偏移为唯一基准。
  • 攻击/命中标记：零页 $00CC 的第 7 位（$80）在每次被击中时置位。

核心思想是两条腿走路：

5. 详细分析过程

5.1 定位生命值地址

通过”受伤后观察 RAM”的差分方法定位生命值：

  1. 进入游戏（见 §8 输入注入方法）。
  2. 快照零页 + RAM（$0000-$07FF）。
  3. 让蝙蝠侠被击中一次，再次快照。
  4. 差分找出变化字节。

结果：$00B7 为生命值，满血 = $08，受伤逐级递减（8 → 7 → 6 ...），归零死亡。同帧内 $00CC 第 7 位置位（命中标记）。

7. 双保险：Mesen 作弊码

7.1 原理

Mesen 的 NesCustom 作弊码格式为 XXXX:YY（地址:值），实现方式是拦截对指定地址的读取，一律返回设定值。配合”从源头 NOP 掉扣血写”的 ROM 补丁，即便将来发现漏网的分支，作弊码也能兜底。

作弊码：00B7:08（生命值恒为满格）。

7.2 读取路径的坑（重要）

Mesen Lua 对同一地址存在两条读取路径，结果可能不同：

API 路径 是否经过作弊码
emu.read(addr, emu.memType.nesInternalRam) 直接读 RAM 缓冲 否（绕过）
emu.read(addr, emu.memType.nesMemory) (= 8) 走 DebugRead → 内存管理器 是

实测：作弊码生效时，CPU 执行读与 nesMemory 读取均返回 $08，而 nesInternalRam 读到的是原始 RAM 值（作弊前被扣到 $07）。因此：

  • 验证作弊码是否生效要用 nesMemory；
  • 观察真实血量要用 nesInternalRam（两者对照即知”作弊层是否真的在兜底”）。
